# Decision log

What decree does is in the [reference](reference/README.md). The construction plan for the 0.5 rewrite (the implementation spec, the 0.4.2 inventory and two spikes) has done its job and was removed; its last version is in `docs/` at commit `32223bb`. Evidence below is linked by commit hash.

## D1: Machines follow SCXML

**Context.** decree 0.4 routed each message with a global LLM prompt, and a routine was a bash script with hooks around it. Control flow was hidden in prompts and scripts, could not be validated, and could not be drawn. A workflow engine needs states, nesting, entry and exit actions and well-defined transition semantics; inventing them invites subtle bugs and forces every user, human or AI, to learn a new model.

**Decision.** Machines follow W3C SCXML 1.0 (Recommendation, 2015): its terms, its key names, its transition semantics (Appendix D), for a strict subset of its features. Every difference is listed in [SCXML subset](reference/machines.md#scxml-subset); extensions are marked as such in [Keys](reference/machines.md#keys).

**Consequences.** Anyone who knows SCXML or Harel statecharts knows how a machine behaves. Features outside the subset (`<parallel>`, `<history>`, `cond`, executable content) fail validation with the SCXML name and the decree alternative. Where SCXML leaves a choice to the platform, the reference records decree's. Evidence: `a0079ea` (first plan), `691ae4c` (SCXML conformance fixes queued).

## D2: YAML is the only syntax

**Context.** SCXML is defined in XML. decree's users write machines by hand and with AI agents next to markdown messages and bash scripts; XML is verbose there, and two syntaxes would double the parser, the tests and the docs.

**Decision.** Machines are YAML 1.2 documents, parsed with `serde_norway`. There is no XML input or output.

**Consequences.** Machines are short and readable. YAML 1.1 tools read bare `yes`, `no` and `on` as booleans; decree reads them as strings, which matters because `yes` and `no` are `check` events. Inline maps need quoted questions and descriptions when they contain `, ` or `?`. Evidence: `a0079ea`; the `serde_yaml` to `serde_norway` switch in `759fa59`.

## D3: No SCXML library

**Context.** The Rust SCXML crates either only parse XML (`harel`) or simulate a chart without exposing the exit and entry sets (`scxml`). decree needs exactly those sets, to run `onentry` and `onexit` scripts in order and record each step, and its subset of the Appendix D algorithm is small.

**Decision.** decree implements its subset of the algorithm itself, on a flattened arena of the machine that the interpreter, the validator and the graph exporter share.

**Consequences.** No dependency to track, and the picture (`decree graph`) can never drift from the behaviour. The conformance burden is decree's own; the SCXML fixtures in `tests/fixtures/scxml/` carry it. Evidence: `a0079ea`, `759fa59`.

## D4: A router is a machine

**Context.** A `choose: model` decision has to ask some model. The spike first decided that a router is a command named in `config.yml`, which reads a rendered prompt or a JSON request on stdin and prints a reply. That kept decree free of HTTP clients, but put prompts, retries and budgets in configuration that could not be seen, validated or drawn like the rest of the workflow.

**Decision.** A router is an ordinary machine. decree writes `request.json` in a child run's folder, runs the router machine as that child run, and reads and validates `reply.json` ([Model](reference/runs.md#model)). This supersedes the spike's command design (its R1, R2, R3, R6 and R7 as first recorded) and the `routers:` and `default_router` keys of `config.yml`.

**Consequences.** Routers are replaceable and visible like any machine: their own runs, logs, events and graphs. Any backend and any language fit. decree contains no model code. A router can itself escalate between models. Evidence: `759fa59` (questions table changed to "a router is a machine"), `8074a50` and `aa4139b` (implemented), `docs/spikes/router.md` at `32223bb` (both versions of the record).

## D5: Each `choose: model` names its router, or uses the machine named `router`

**Context.** Different decisions suit different backends: a local classifier for document types, a large model for code review. The spike first chose named `routers:` plus `default_router` in `config.yml`; [D17](#d17-no-configuration-file) later removed the configuration file.

**Decision.** `choose: model, router: <machine>` picks a router. Without `router:`, the machine named `router` is used, and `decree init` writes it. `decree check` fails V16 if a `choose: model` names no router and there is no `machines/router/machine.yml`.

**Consequences.** The default is a naming convention, not a setting, so it is visible in `machines/`. Evidence: `759fa59` (router per state), `235d7e5` and `0652778` (`default_router` replaced by the machine named `router`).

## D6: The prompt lives in the router's script

**Context.** The spike's first record had decree render one chat prompt for every chat backend. With routers as machines ([D4](#d4-a-router-is-a-machine)), a prompt inside decree would bind every router to one shape, and typed-choice models take no prompt at all.

**Decision.** decree writes a structured request. The default router's script renders the prompt from it ([The default router](reference/runs.md#the-default-router)), and the reference documents that prompt.

**Consequences.** Changing a prompt is a script edit, never a decree release. Typed-choice routers map the request onto their own API. Evidence: `759fa59`, `aa4139b` (the 0.4.2 router call moved into `ask_claude`).

## D7: `min_confidence` turns a weak pick into `unsure`

**Context.** Typed-choice models such as TypeSafe Jev report a confidence, and acting on a guess is worse than asking. The options were to record confidence only, to fall back to a default event, or to produce a declared event.

**Decision.** `min_confidence` on `choose: model`: below it, or with no confidence reported, the state's event is `unsure`, an ordinary event the machine must handle (V8). Escalating to a person is a transition from `unsure` to a `choose: person` state. There are no bands in the invoke; a `confidence` check after `unsure` splits further when wanted.

**Consequences.** The threshold sits where the decision is made, and escalation shows in the machine and its graph. Confidence is the router's own number, so a threshold is calibrated per router ([Model](reference/runs.md#model)). Evidence: `759fa59`, `aa4139b`.

## D8: Asking a person is `choose: person` plus a reply message

**Context.** The spike first leaned to a final state such as `needs_review` that a human continues with `decree retry --state`. That needs someone to know decree's commands, and leaves no record of the answer.

**Decision.** `choose: person`: the state's `ask` script tells someone, the run pauses with a wait id, and a reply message (`to:` and `event:`) delivers one option ([Replies](reference/messages.md#replies)). This is SCXML's external event, and the AWS Step Functions callback pattern with the wait id as the task token.

**Consequences.** decree never knows there is a question or who answers; any tool that can write a file can reply. Wrong replies become failed `invalid_message` runs and leave the waiting run unchanged. Evidence: `759fa59` (design), `8074a50` (the invoke), `8f9634b` (replies).

## D9: What the router request holds

**Context.** A router needs enough to decide, and no more: secrets must stay out of prompts, and the input must be explainable. The first record had decree cut the input and body to a router's `max_input_bytes`.

**Decision.** The request holds the machine and state with their descriptions, the question, the options with descriptions, `min_confidence`, the input state's output, the message body and the run's history ([Model](reference/runs.md#model)). A script chooses what the model sees by what it prints. Trimming to a model's budget is the router's job.

**Consequences.** Secrets stay out by design, not by redaction. `input` and `message_body` stay separate, so a router can pass structured context (Jev's `state` takes any JSON). The request is versioned (`v: 1`), so fields such as attachments can be added without breaking routers. Evidence: `759fa59`, `8074a50`.

## D10: Self-hosting is a router machine

**Context.** Users want local models: SGLang, vLLM, Ollama, or a small classifier such as GLiNER2.5-Decide that runs on CPU. Running model servers is a large problem of its own.

**Decision.** A self-hosted backend is a router machine whose script talks to a server the user runs. [Router machines](routers.md) shows TypeSafe Jev, GLiNER2.5-Decide behind a small long-running server, a self-hosted LLM and a cheap-model-first router. Running a model server is outside decree ([Long-running services](services.md)).

**Consequences.** decree stays small. A model loads once in its own service, not per decision. Evidence: `759fa59`, `aa4139b`.

## D11: Every decision is auditable

**Context.** Model decisions must be checkable after the fact: for audit, for calibrating thresholds, and for a future replay.

**Decision.** Each router call is its own child run with its logs, `request.json` and `reply.json`. Every `check` and `choose` produces a `decision` event; for a model it records the router, the child run, the pick (even when the event is `unsure`), the reason, the confidence and the probabilities ([events.jsonl](reference/runs.md#eventsjsonl)).

**Consequences.** Thresholds can be checked against outcomes in Grafana. A replay can feed recorded picks back ([D33](#d33-q7-no-decree-replay-yet)). Evidence: `759fa59`, `aa4139b`.

## D12: AI and people decide only where a machine says `choose`

**Context.** In 0.4 it was hard to tell where an AI made a decision. The spike considered expression strings and extra model primitives (Jev's Score and yes/no) for conditions.

**Decision.** AI and people appear only in `choose: model` and `choose: person` states; deterministic decisions are `check` states with typed conditions, not expression strings. Graph edges say who decided: `(check)`, `(model)`, `(person)`.

**Consequences.** It is always clear when an AI is involved. Typed conditions keep YAML readable and let `decree check` catch mistakes (V10). Model-backed conditions are not part of decree. Evidence: `759fa59`, `8074a50`.

## D13: No detection of AI inside scripts

**Context.** A script may call a model itself, as the `develop` scripts do. decree could try to detect that.

**Decision.** Not pursued.

**Consequences.** What a script does internally is the script's business. Only decisions that pick an edge are decree's, and those are `choose` states ([D12](#d12-ai-and-people-decide-only-where-a-machine-says-choose)). Evidence: `759fa59`.

## D14: The graph is Mermaid text in Markdown

**Context.** `decree graph` prints Mermaid. That renders on GitHub, GitLab, VS Code and Obsidian, but a user in a terminal sees text. The spike weighed shelling out to a renderer (mermaid-cli, merman-cli), building merman into decree, a self-contained HTML page, a mermaid.live link, DOT, an XState export and terminal rendering, against four criteria: show nesting, notes and who decides each edge; work offline; add little to install; open in one command. Renders of the mock with mermaid-cli and merman-cli matched; mmdr did not.

**Decision.** decree writes Mermaid `stateDiagram-v2` (and a `flowchart LR` system graph) inside Markdown files in `.decree/graph/`, committed with the project. Users view them in VS Code 1.121+, GitHub, GitLab or Obsidian, or paste a diagram into mermaid.live ([Viewing](reference/graph.md#viewing)). No image rendering, no DOT, no terminal rendering, no XState export (Stately Studio needs an account to view). A clickable graph that links to logs is a separate product built on decree.

**Consequences.** decree stays a small single binary, and the graph is byte-for-byte deterministic and testable. decree's contract for tools built on it: stable state ids in the diagrams, and `machine`, `state` and `run_id` on every event. Evidence: `a0079ea`, `docs/spikes/graph.md` and its renders at `32223bb`.

## D15: `onentry` and `onexit` run once per visit

**Context.** 0.4.2 had five hooks (`beforeAll`, `afterAll`, `beforeEach`, `afterEach`, `onDeadLetter`), and its git-stash hooks restored a baseline before the final retry. SCXML runs entry and exit content on each entry and exit of a state, not per retry.

**Decision.** `beforeAll` is root `onentry`, `afterAll` root `onexit`, `beforeEach` and `afterEach` a state's `onentry` and `onexit`, and `onDeadLetter` the `onentry` of `failed`. They run once per visit; `attempts` re-runs only the invoke. The git-stash hooks became `git_baseline` (root `onentry`, records `HEAD` once) and `snapshot` (a working state's `onentry`, a checkpoint each visit). Restoring the baseline before the final attempt is dropped: a machine that wants a clean retry loops back through a state.

**Consequences.** Hooks are visible in the machine and its graph. A run that ends `failed`, including after a failing `onentry`, runs `failed`'s `onentry` exactly once; 0.4.2 skipped `onDeadLetter` after a `beforeEach` failure, and 0.5 reverses that on purpose. Evidence: `b1d5613`, `446dce7`.

## D16: Delete with the last caller

**Context.** The rewrite removed 22 pieces of 0.4.2 (the global router prompt, fuzzy routine matching, the routine registry, the outbox, the dead-letter directory, hooks, three script resolvers and more) while the new code was built beside them. Deleting a symbol whose callers are still alive breaks the build; keeping dead code around leaves shims.

**Decision.** Every deletion starts with a grep of its symbol. A symbol is deleted by the change that removes its last caller, and that change also deletes whatever it leaves without a caller. No compatibility shims; the one exception is `routine:` as an alias of `machine:`, because migrations are immutable and existing projects have pending migrations that carry it.

**Consequences.** The tree builds at every step and ends with no dead code. A 0.4 project is upgraded once by `scripts/migrate-0.4-to-0.5.sh`, not by the binary. Evidence: `aa4139b` (the rule), `8ab1a72` (the bulk deletion).

## D17: No configuration file

**Context.** 0.4's `config.yml` held the router command, the default routine, `max_retries`, the emit depth, the log size and shared routines. After [D4](#d4-a-router-is-a-machine) and [D5](#d5-each-choose-model-names-its-router-or-uses-the-machine-named-router), what was left were defaults that hid behaviour outside the machines, and a strict-keys version still had to be kept in step with the migration script.

**Decision.** There is no configuration file ([No configuration file](reference/README.md#no-configuration-file)). The router is the machine named `router`; every message names its machine; `attempts` defaults to 1 per script invoke; the emit depth limit (10) and the log cap (2 MiB) are fixed; shared machines and scripts are symlinks. The daemon interval is a flag. A leftover `.decree/config.yml` is an error naming `scripts/migrate-0.4-to-0.5.sh`.

**Consequences.** A project is machines, scripts and messages, and everything that affects a run is in them. Evidence: `dc2184a` (strict `config.yml`, superseded), `235d7e5` and `0652778` (removed).

## D18: C1: clippy fixes in test files

**Context.** The 0.4.2 baseline failed `cargo fmt --check` and had 21 clippy errors in `src/`. Once `src/` was clean, clippy found 3 `useless_conversion` errors in `tests/integration_test.rs`, but the clean-up was allowed to touch only formatting in tests.

**Decision.** Clippy fixes in `tests/` are allowed; the three were rewritten to `cargo_bin_cmd!("decree")`.

**Consequences.** `cargo clippy --all-targets -- -D warnings` passes and is a gate for every change. Evidence: `759fa59`.

## D19: C2: SIGTERM stops decree and its script

**Context.** 0.4.2 registered SIGINT twice and SIGTERM never, though a comment said it forwarded SIGTERM. SIGTERM killed decree by default and left the routine running in its own process group.

**Decision.** decree handles SIGINT and SIGTERM alike: it stops the running script's process group, appends an `interrupted` event with `cause: "signal"`, and exits (130 for `process`).

**Consequences.** `systemctl stop` and `docker stop` stop a run cleanly, and the stop is in the record. Evidence: `759fa59`.

## D20: C3: SIGKILL after a 10 s grace

**Context.** Both 0.4.2 executors sent SIGTERM to the group and then waited for the child with no deadline.

**Decision.** decree sends SIGTERM to the script's process group, waits up to 10 s for every process in it to exit, then sends SIGKILL, as `docker stop` does ([Execution](reference/scripts.md#execution)).

**Consequences.** A script that ignores SIGTERM cannot hang decree. Evidence: `759fa59`.

## D21: C4: one executor for every script

**Context.** Hooks, the precheck and the AI router command ran through `bash` with `.output()`: no process group, no timeout, not stopped on a signal.

**Decision.** One executor runs every script (invokes, `onentry`, `onexit`, `ask`), directly with no `bash` wrapper. Hooks became `onentry` and `onexit` ([D15](#d15-onentry-and-onexit-run-once-per-visit)), the precheck an ordinary first state, and the router command a router machine ([D4](#d4-a-router-is-a-machine)).

**Consequences.** Every script gets the same environment, log, timeout, signal handling and `script` event. Evidence: `759fa59`, `aa4139b`, `8ab1a72`.

## D22: C5: the inbox is first-in, first-out

**Context.** 0.4.2's `process` took the alphabetically last inbox file (or the deepest in the current chain) and the daemon took the last: last-in, first-out.

**Decision.** decree claims the inbox file with the lowest byte-order filename; emitted and cron messages are named by their time-ordered id, so they run first-in, first-out ([Lifecycle](reference/messages.md#lifecycle)).

**Consequences.** Order is predictable. A step that must finish before its parent continues belongs in the same machine ([D34](#d34-q8-emitted-messages-run-first-in-first-out)). Evidence: `759fa59` (claim), `cb22c9d` (0.4.2 selection deleted).

## D23: C6: the daemon runs the same pipeline as `process`

**Context.** 0.4.2's daemon had its own pipeline: it never ran migrations and handled messages differently from `process`.

**Decision.** `daemon` calls the same functions as `process`, adding a cron tick and a sleep ([cli.md](reference/cli.md)). A failed or interrupted inbox run does not stop it; a failed, interrupted or waiting migration blocks later migrations only.

**Consequences.** One pipeline to test. Evidence: `8f9634b`.

## D24: C7: deletions are checked with qualified names

**Context.** "Zero hits" for each deleted symbol cannot hold for leaf names such as `run`, `error`, `init` or `log`, which match code 0.5 keeps; and `routine` must keep matching as the `machine:` alias.

**Decision.** Deletions are verified with qualified patterns (`routine::levenshtein`, `fn run_precheck`, `HookType`, …).

**Consequences.** The checks are meaningful and pass. Evidence: `759fa59`, `8ab1a72`.

## D25: C8: no `max_retries` alias

**Context.** 0.4.2's routine configuration accepted `max_retries` as an alias of the state's attempt count (now `attempts`), which no design document mentioned.

**Decision.** No alias: it went with the routine configuration. Retries are the script invoke's `attempts`.

**Consequences.** One name. A 0.4 `config.yml` is not read at all ([D17](#d17-no-configuration-file)). Evidence: `8ab1a72`.

## D26: C9: `init` never touches an existing `.decree/`

**Context.** Without a terminal, 0.4.2's `init` proceeded over an existing `.decree/`; with one, it asked.

**Decision.** `init` asks nothing. It refuses an existing `.decree/` and exits 2; flags replace the prompts.

**Consequences.** `init` is safe in scripts and CI. Evidence: `759fa59`.

## D27: Q1: the `processed.md` ledger

**Context.** Migrations must run once, in order, with their history in git, but migration files are immutable.

**Decision.** The committed `processed.md` lists the migrations that ran. It is written before the final state's `onentry` scripts, so a `commit` there includes it ([Migrations](reference/messages.md#order-files-run-in-order-at-each-start)).

**Consequences.** A fresh clone knows which migrations ran; `runs/` is never committed. Evidence: `759fa59`.

## D28: Q2: no commands configuration

**Context.** 0.4.2's `config::CommandsConfig` named the AI commands for routing and interactive use.

**Decision.** Replaced by the router machine ([D4](#d4-a-router-is-a-machine), [D5](#d5-each-choose-model-names-its-router-or-uses-the-machine-named-router)) and by the AI calls in the scripts `init` writes; `ai_interactive` is gone. The first answer, a `default_router` key, was superseded by [D17](#d17-no-configuration-file).

**Consequences.** Which AI is called is visible in scripts. Evidence: `aa4139b`, `0652778`.

## D29: Q3: every 0.4 hook maps to `onentry` or `onexit`

**Context.** 0.4.2 had five hook types.

**Decision.** All five map, as [D15](#d15-onentry-and-onexit-run-once-per-visit) lists.

**Consequences.** No hook concept remains. Evidence: `b1d5613`.

## D30: Q4: `init` writes the decree skill

**Context.** 0.4 had a `skill` command and a `sow` skill.

**Decision.** `decree init` writes a rewritten decree skill to `.claude/skills/decree/` or `.github/skills/decree/`, never overwriting an existing file. The `skill` command and the `sow` skill are gone.

**Consequences.** AI agents learn messages, machines and scripts from the project. Evidence: `43c9158`.

## D31: Q5: one run at a time per process

**Context.** Parallel runs would complicate locking, logs and GPU use.

**Decision.** One run at a time per process. The run lock only guards against two processes.

**Consequences.** A daemon never asks for two GPU services at once ([Long-running services](services.md)). Evidence: `a0079ea`. Several processes in one project folder, each running its own machines, are [D69](#d69-a-process-runs-the-machines-it-is-given).

## D32: Q6: routers are commands, not HTTP clients

**Context.** A router could call an HTTP API with schema-constrained output.

**Decision.** No HTTP in decree. decree validates replies itself; a router's script calls whatever it likes.

**Consequences.** No HTTP dependency; any backend fits through a script ([D4](#d4-a-router-is-a-machine)). Evidence: `a0079ea`.

## D33: Q7: no `decree replay` yet

**Context.** Re-running a run with its recorded router choices would make model decisions reproducible.

**Decision.** Deferred. `events.jsonl` and the router runs store what it needs ([D11](#d11-every-decision-is-auditable)).

**Consequences.** It can be added without changing the record. Evidence: `a0079ea`.

## D34: Q8: emitted messages run first-in, first-out

**Context.** A run can emit several follow-up messages.

**Decision.** They run first-in, first-out by filename ([D22](#d22-c5-the-inbox-is-first-in-first-out)). A step that must finish before the parent continues belongs in the same machine, as a state or a sub-machine.

**Consequences.** Emits are fire-and-forget. Evidence: `759fa59`.

## D35: Q9: free-form messages are routed by a machine

**Context.** 0.4.2's global router sent free-form messages to a routine.

**Decision.** An ordinary machine does it: a `choose: model` state picks an option, and the target state's script runs `decree emit` for the chosen machine (`mock/.decree/machines/triage/machine.yml`).

**Consequences.** Routing is a visible, replaceable machine, not a global prompt. Evidence: `759fa59`.

## D36: Q10: a killed run waits for `decree retry`

**Context.** A run stopped by a signal or a crash could be continued automatically, as durable-execution engines do.

**Decision.** No. Signals and crashes both leave the run `interrupted`; only `decree retry` continues it. A kill may be deliberate, and decree cannot tell.

**Consequences.** Scripts must be safe to re-run; continuing re-runs root and ancestor `onentry` scripts. Evidence: `759fa59` (interrupts), `b1d5613` (`decree retry`).

## D37: Q11: one flat `scripts/` directory with per-machine overrides

**Context.** 0.4.2 had three script resolvers and nested routine directories.

**Decision.** One flat `scripts/` directory shared by all machines, with optional `scripts/<machine>/` overrides ([Resolution](reference/scripts.md#resolution)).

**Consequences.** Generic scripts are written once; an override is visible in the `script` event's `path`. Evidence: `759fa59`.

## D38: Q12: the router contract is `request.json` and `reply.json`

**Context.** A router could take a chat prompt, a typed choice (Jev), or both.

**Decision.** A router is a machine that reads `request.json` and writes `reply.json` ([D4](#d4-a-router-is-a-machine)). Prompts, models and retries live in it.

**Consequences.** Chat models and typed-choice models both fit. Evidence: `759fa59`, `aa4139b`.

## D39: Q13: graphs are viewed in existing tools

**Context.** A user outside an IDE or a website still needs to see a graph.

**Decision.** As [D14](#d14-the-graph-is-mermaid-text-in-markdown): Markdown files with Mermaid, opened in VS Code, GitHub or Obsidian, or pasted into mermaid.live. No renderer in decree.

**Consequences.** See D14. Evidence: `a0079ea`.

## D40: Q14: a person answers with a reply message

**Context.** A run waiting for a person should not need someone to run `decree retry`.

**Decision.** As [D8](#d8-asking-a-person-is-choose-person-plus-a-reply-message): a `choose: person` invoke plus reply messages. decree never knows it is a question.

**Consequences.** See D8. Evidence: `759fa59`.

## D41: Q15: a machine can invoke another machine

**Context.** Workflows compose: a release runs a feature, then a deploy.

**Decision.** `invoke: { machine: <name> }`, SCXML's child state machine. The child is a separate run with a `parent` reference, and the root final state it reaches is the parent state's event ([Sub-machines](reference/runs.md#sub-machines)). Routers are invoked the same way.

**Consequences.** Each machine stays small and has its own runs and graph. V20 forbids cycles. Evidence: `759fa59`, `6a35eaf`, `aa4139b`.

## D42: Q16: scripts do not run inside tmux

**Context.** Running scripts in tmux would make them easy to watch.

**Decision.** No: decree needs exact exit codes, separate stdout and stderr, and no terminal. Live visibility comes from `decree status` and `decree tail`; tmux stays a personal dashboard ([Long-running services](services.md)).

**Consequences.** Scripts are plain processes. Evidence: `b1d5613` (`decree tail`).

## D43: Delete finished runs on request, never automatically

**Context.** Run folders were never removed, so `runs/` grows by every run's events, logs and replies (about 64 KB for a mock migration run). Deleting a folder is not free of meaning: a failed migration's folder is what keeps `process` from starting it again, and a parent run may still read its child's results. A project that ships `events.jsonl` and the script logs to Loki ([observability.md](reference/observability.md)) already keeps its history there. Prior art: `docker system prune --filter until=<duration>` and `git gc --prune=<date>` delete on request with an age cut-off; AWS Step Functions keeps execution history for a fixed period and then deletes it.

**Decision.** `decree prune --older-than <age> [--dry-run]` deletes the folders of finished runs whose `run_finished` event is older than `<age>`, and nothing else ever deletes a run ([cli.md](reference/cli.md)). The age is required, so a bare `decree prune` deletes nothing. It keeps runs that are not finished, migrations that ended in `failed`, and children of unfinished parents, and it takes the run lock before deleting. No archive: it would only move the growth.

**Consequences.** Retention is the log store's job, and the local `runs/` is a working copy; a project that ships nothing keeps every run until someone prunes. `decree status <id>` and `decree retry` cannot reach a pruned run. Evidence: migration 70.

## D44: One shape per machine key

**Context.** The machine format had places where one idea took several shapes. `invoke` named its kind three ways: a bare string was a script, `check:` and `machine:` were keys, and `choose: model` and `choose: person` were values, each with its own sibling fields. Where a check's text came from was implicit: `{ matches: re }` read the `input:` state named beside `check:`, or, without one, whichever script ran last, and `matches` was both a subject and an operator. A check produced `yes` or `no` where a reader expects true and false. The attempt count (now `attempts`) and a script's `timeout_s` sat on the state while a person's `timeout_s` sat inside `invoke`. And the examples wrote prose inside flow maps, where an unquoted `?` or `, ` breaks YAML. People and models had to guess which shape a key took. Prior art for naming a kind by its key: serde's externally tagged enums (`{ variant: value }`, a map with one key), and GitHub Actions steps, which are a `uses:` step or a `run:` step by the key that is present.

**Decision.** One shape per key, explicit over implicit ([Invoke](reference/machines.md#invoke-the-states-function)):

- `invoke` is a map with exactly one key, which names the kind: `script`, `check`, `model`, `person` or `machine`. `invoke: <name>` is short for `invoke: { script: <name> }`, and a bare name under `script` or `machine` is short for `{ name: <name> }`.
- A check's events are `true` and `false`. YAML 1.2 reads `true:` and `false:` as booleans; decree reads a boolean key in `transitions` as that event name, so no quotes are needed.
- A condition has exactly one subject and one operator. `output: <state>` is the subject that reads a state's script output, and `matches` is only an operator. A `model` reads the state named by its `output`, or nothing: there is no fallback to the most recent script.
- Script settings (the attempt count, now `attempts`, and `timeout_s`) sit inside the script invoke, as a person's `timeout_s` sits inside `person`.
- Machines write decision invokes and prose in block style.

No old shape is accepted: `choose`, `input`, a bare `matches`, a state-level attempt count or `timeout_s`, and `{ machine: x, params }` each fail V19 with a message that names the new shape. Nothing old is read or translated. This supersedes the syntax in [D5](#d5-each-choose-model-names-its-router-or-uses-the-machine-named-router), [D8](#d8-asking-a-person-is-choose-person-plus-a-reply-message) and [D12](#d12-ai-and-people-decide-only-where-a-machine-says-choose) (the decisions stand; `choose: model` is now `model:` and `choose: person` is now `person:`), and the input fallback in [D9](#d9-what-the-router-request-holds).

**Consequences.** A reader knows an invoke's kind from its one key and a condition's text from its named `output`, so a machine reads the same to a person and a model, and a JSON Schema can describe each kind on its own (migration 72). Every machine, recorded check event and doc example changed once, before 0.5 is released. A model state that names no `output` gets an empty `input`, so its prompt holds only what the machine names. Evidence: migration 71.

## D45: JSON Schema for shape, `decree check` for meaning

**Context.** The machine format was described only in prose, so a person learned a misspelled key from `decree check` after saving, and a model writing a machine had to infer the contract from examples. Prior art: JSON Schema (draft 2020-12) is the standard way to describe a JSON or YAML document; the YAML language server (VS Code's YAML extension by Red Hat, and others) applies a schema named in a `# yaml-language-server: $schema=<path>` comment, and SchemaStore publishes schemas in that form for GitHub Actions workflows, Docker Compose files and many other YAML formats. Models are held to JSON Schemas for structured output.

**Decision.** decree ships two schemas, `machine.schema.json` and `message.schema.json`, compiled in from `src/templates/schema/` as their single source. `decree schema` writes them to `.decree/schema/`, `decree init` writes them, and `decree check` warns when they are missing or stale, as it does for `.decree/graph/`. Every machine starts with `# yaml-language-server: $schema=../schema/machine.schema.json`. The schema describes everything about one file's shape: keys, types, required keys, each `invoke` kind and condition, name patterns and ranges, with `additionalProperties: false` everywhere as V19, and a description and examples on every key. What needs other files or the whole graph stays with `decree check`, which remains the authority ([Schema](reference/machines.md#schema)). The schema never accepts a machine that `decree check` rejects for its shape; `validation_test.rs` holds it to every case. It uses only keywords that draft-07 tools also understand, plus `$defs`, so older editors read it too.

**Consequences.** Editors complete keys and underline mistakes as you type, a model reads one precise contract, and any JSON Schema validator checks a machine without decree. There are two descriptions of the format to keep in step, the parser and the schema; the test table catches drift. The `jsonschema` crate is a dev-dependency only, so decree itself does not validate against the schema. Evidence: migration 72.

## D46: No 0.4 compatibility, and examples by topic

**Context.** decree 0.5 kept three things for projects coming from 0.4: `scripts/migrate-0.4-to-0.5.sh`, an error for a leftover `.decree/config.yml` that named the script, and `routine:` read as an alias of `machine:` so that immutable migrations written for 0.4 still ran. Every project this repository knows of is on 0.5, no pending migration uses `routine:`, and processed migrations are never read again. Separately, `mock/` was one project that showed every feature at once: the reference quotes it and the replay tests run its recorded runs, but one project with nine machines is hard to browse, and its name said "not real".

**Decision.** Everything 0.4 goes: the upgrade script and its fixtures, the `config.yml` error, the `routine:` alias (a message with only `routine:` fails M1, M2 or M3 like any message without `machine:`; `routine` is an ordinary unknown key), and the tests that compared the built-in machines with 0.4.2. `tests/examples_test.rs` keeps the words out of `src/`, `docs/reference/`, `README.md`, `tests/` and `examples/`. `mock/` became the `feature` example (every building block, its recorded runs and queue; since migration 92 the fixture `tests/fixtures/feature/`, and `examples/project/` the example), an escalation-ladder example with its recorded run (since migration 91 the fixture `tests/fixtures/escalation/`) and `examples/observability/` (Alloy, Loki and Grafana). A machine two examples need is a copy in each, held byte-identical to its template. This supersedes the alias in [D24](#d24-c7-deletions-are-checked-with-qualified-names) and the upgrade path in [D16](#d16-delete-with-the-last-caller) and [D17](#d17-no-configuration-file).

**Consequences.** One way to name a machine, and no code for a version nobody runs. A 0.4 project upgrades from git history (the script's last version is in the commit before migration 73). Each example shows one topic, with its own `.decree/` that passes `decree check` and reproduces its graph, and every recorded run in every example is replayed by `tests/replay_test.rs`. Evidence: migration 73.

## D47: Typed routers for routing, untyped models for the work

**Context.** A `model` decision is answered by a router machine, and the docs did not tell two kinds of router apart. A **typed** router cannot answer outside the options: a classifier such as Fastino's GLiNER2.5-Decide picks one of the labels it is given and its confidence is its own score; constrained decoding (Ollama's `format` with a JSON Schema, vLLM's guided decoding, SGLang's `select`) holds a language model's output to the reply's shape; TypeSafe Jev picks among its criteria. An **untyped** router asks a chat model or coding agent (`claude -p`, Copilot, OpenCode) for free text: its script must find a JSON object in the reply and check it, it can fail with no JSON or a pick that is not an option (the event is then `error`), and its confidence is self-reported, the least reliable kind. Prior art for the constraint: Ollama's structured outputs and OpenAI-style `response_format` take a JSON Schema and decode against it.

**Decision.** Use a typed router for routing decisions, the cheap, frequent and bounded ones, and reach for GLiNER2.5-Decide first: it runs locally on CPU and costs no fee. Use an untyped model for the work itself, and for judgments that need reasoning over a lot of context. decree adds `reply_schema` to every `request.json`: a JSON Schema (draft 2020-12) for `reply.json` whose `event` is an enum of the options, so a typed router passes it to a constrained decoder unchanged ([Model](reference/runs.md#model)). decree still validates every reply itself. [Router machines](routers.md) opens with the two kinds, and the flagship example, `examples/route-by-complexity/`, routes by complexity: GLiNER decides whether a change is small enough for a local model served by Ollama, or needs Claude, and a local attempt that fails the tests goes to Claude once. The GLiNER server is one file, `examples/route-by-complexity/gliner/decide_server.py`; `local_router` in the escalation-ladder example became `gliner_router`, the same machine as in the new example.

**Consequences.** A routing decision costs milliseconds of CPU and always names an option, and its `min_confidence` is set against a measured score; Claude runs only where the classifier says a change needs it, or where local work failed. A request is larger by its schema, which untyped routers ignore. GLiNER's docs show a score for the picked label only, so `gliner_router` replies have no `probabilities`, and the escalation ladder's recorded run changed to match. Evidence: migration 74.

## D48: Scripts name their event in `$DECREE_EVENT_FILE`

**Context.** An invoke named its event on the last non-empty line of stdout, as `{"event": "<name>"}`. stdout is also the script's log, so whatever a script happened to print last could become its event: the default router printed the model's JSON reply last, and every bare-JSON reply was read as the router script's own event and failed, until migration 67 added a plain `picked <option>` line after it. Every script that ran a model or a tool with free output needed the same workaround line. GitHub Actions had the same problem with `::set-output` workflow commands on stdout and retired them for `$GITHUB_OUTPUT`, a file whose path the runner passes in an environment variable.

**Decision.** decree does the same. Before each attempt of a script invoke it creates an empty `runs/<id>/.event` and sets `DECREE_EVENT_FILE` to its path; a script names its event by writing the name to it (`echo pass > "$DECREE_EVENT_FILE"`). After the script exits, decree reads the file only on exit 0, trims surrounding whitespace, and deletes it. An empty or missing file is `done`. `onentry`, `onexit` and `ask` scripts get an empty `DECREE_EVENT_FILE`, since they produce no events. stdout and stderr are only logs and are never parsed. The `transition` event's `source` for a named event is `script` instead of `stdout`; `events.jsonl` stays at `v: 1`, as the format is not released ([Events from an invoke](reference/scripts.md#events-from-an-invoke)).

**Consequences.** A script prints what it likes, and nothing it prints can change the path of the run. Naming an event is one redirect in any language. The `picked <option>` line in routers stays as a log line. Recorded runs keep their logs, which still show the old JSON lines. Evidence: migration 79.

## D49: One duration format

**Context.** Machines took seconds as integers (`timeout_s: 604800`), while `decree prune` took an age with a unit (`--older-than 30d`) and `decree daemon --interval` took bare seconds. Three spellings for one idea, and `604800` has to be worked out to be read as a week. Prior art: Kubernetes fields and Go's `time.ParseDuration` write a number followed by its unit (`90s`, `10m`, `12h`).

**Decision.** One format everywhere: a whole number followed by one unit, `s`, `m`, `h` or `d` (`90s`, `10m`, `12h`, `7d`), with no fractions, no combinations (`1h30m`) and no bare numbers ([Durations](reference/machines.md#durations)). One parser reads a machine's `timeout`, `decree prune --older-than` and `decree daemon --interval`; a bad duration fails V16 in a machine and exits 2 on the command line. `timeout_s` became `timeout` in the `script` and `person` invokes; `timeout_s` fails V19 naming `timeout: <n>s|m|h|d`. `events.jsonl` keeps `duration_ms` and `timeout_at`, and scripts get no new variables.

**Consequences.** `timeout: 7d` reads as it means, and a string that one place rejects every place rejects. A duration in between units is written in the smaller one (`90m`, not `1h30m`). Evidence: migration 80.

## D50: A versioned schema for every file

**Context.** Only machines and message frontmatter had schemas ([D45](#d45-json-schema-for-shape-decree-check-for-meaning)). `events.jsonl`, which dashboards and pipelines consume, and `request.json` and `reply.json`, which routers in any language read and write, were described only in prose, and nothing tested the code against that prose: writing the events schema found a `run_finished` table lost from the reference and a child run's claim event writing `"file": null`. The schemas carried no version, so a breaking change could not be told from a mistake. Prior art: Kubernetes puts an API's version in its path (`apps/v1`); Semantic Versioning 2.0.0 lets major version zero change anything; Keep a Changelog 1.1.0 lists every change by release.

**Decision.** decree ships a JSON Schema (draft 2020-12) for every file it reads or writes: `machine`, `message`, `events` (one line, a `oneOf` per `type`), `request` and `reply` (the general shape; each request's `reply_schema` stays exact). They live in `src/templates/schema/v1/` and `.decree/schema/v1/`; `decree schema` removes anything else in `.decree/schema/` and `decree check` warns about it. The events, request and reply schemas are closed, so decree's tests, which validate every recorded file and every line the property test writes, catch an undocumented field. Within `v1` changes are additive only; a rename, a removal or a change of meaning is `v2`, a new directory and a new `v`; decree 0.x may still change `v1`, and `CHANGELOG.md` lists every change ([Versioning](reference/README.md#versioning)). A child run's claim event now leaves `file` out instead of writing `null`.

**Consequences.** A router or a pipeline in any language can validate what it reads and writes without decree, and the reference, the schemas and the code are held to each other by tests. Consumers must ignore fields and event types they do not know, since the closed schemas describe the current decree, not every future `v1`. Machines point at `../schema/v1/machine.schema.json`. This supersedes the location in D45. Evidence: migration 81.

## D51: JSON output for every report, and SARIF for `decree check`

**Context.** decree's commands printed text for people, so CI systems and AI agents scraped it: a model reading `decree check` split lines on `: ` to find the file and rule, and a pipeline reading `decree status` parsed indentation. Machine errors were visible only in a job log, not beside the line in a pull request. Prior art: `kubectl -o json`, `gh --json` and `cargo --message-format json` put a format flag on the command and keep the text the default; SARIF 2.1.0 is the OASIS standard for static analysis results, read by GitHub code scanning (through `github/codeql-action/upload-sarif`), GitLab and Azure DevOps.

**Decision.** Every command that reports something takes `--format <text|json>`: `check`, `status` (with and without an id), `emit`, `event`, `retry`, `prune`, `graph`, `schema` and `process --dry-run`. With `json` it prints one JSON document on stdout; errors stay on stderr and exit codes do not change. A command that fails before it has a report prints nothing on stdout. Each document has a JSON Schema in `.decree/schema/v1/cli/<command>.schema.json`, written by `decree schema` and versioned as the other files ([D50](#d50-a-versioned-schema-for-every-file)). `decree check` keeps each error's parts apart (rule, file, line or state path, message), so the text line, the JSON error and the SARIF result come from one value. `decree check --format sarif` prints a SARIF 2.1.0 log: the `decree` driver with one rule per row of the Validation table, a result per error with its rule, file (relative to the project root) and line when the error names one, and a result per warning with no rule ([Machine-readable output](reference/cli.md#machine-readable-output)). `process`, `daemon` and `tail` produce streams, `init` and `help` are for people, and `status --cron` stays text, so they take no `--format`. The official SARIF schema is not vendored: the OASIS repository's terms are the OASIS IPR Policy, not an open-source license, so the tests check the fields decree writes instead.

**Consequences.** A model or a CI job reads decree's output with a JSON parser and validates it against a published schema; text output is unchanged. Machine errors appear inline in pull requests. An error inside a state (`V4` on `work`) names the state, not a line, so its SARIF result points at the file only; giving states lines would need YAML positions decree does not keep. JSON keys come out in alphabetical order. Evidence: migration 82.


## D52: Traces as files and environment variables, not an exporter

**Context.** Enterprises trace work with OpenTelemetry, and a decree run is naturally a trace: a tree of timed steps, into which child runs, router calls and the scripts' own calls to services and models nest. `events.jsonl` held the timings but no trace or span ids, so a trace backend could not show a run, and a script's own instrumented calls started traces of their own. An exporter would put network code, retries, batching, credentials and an OpenTelemetry SDK dependency inside decree, and would lose spans whenever the endpoint was down. Prior art: W3C Trace Context (`traceparent`, `tracestate`) is the standard context format; OpenTelemetry's environment variable carrier passes it to child processes as `TRACEPARENT` and `TRACESTATE`; the OTLP file exporter format (one OTLP/JSON request per line) is read by the Collector's `otlp_json_file` receiver; and `otel-cli`, which traces shell scripts, reads and sets `TRACEPARENT` the same way.

**Decision.** decree writes the trace in standard formats and leaves the shipping to the OpenTelemetry Collector ([Traces](reference/observability.md#traces)). Every run has a trace id, taken from its message's `traceparent` frontmatter key when valid, else 16 random bytes from `/dev/urandom`; span ids are 8 random bytes. The run, each script execution, each decision and each wait is a span, written when it ends to `runs/<id>/traces.jsonl` as one OTLP/JSON `ExportTraceServiceRequest` per line, appended like `events.jsonl`. Every event carries `trace_id`, and each event that starts or ends a span carries its `span_id`, so a span's times are its events' times and the trace is derived from the record by the one writer of `events.jsonl`. Scripts get `TRACEPARENT` naming their own span (and `TRACESTATE`); child runs get `traceparent` in their `message.md`, and `decree emit` copies `TRACEPARENT` into the message it queues. A span open when the process is killed is not written; the recovery that appends `interrupted` writes the run span with `ERROR`. `decree retry` starts a new run span linked to the previous one. The fields are additive, so `events.jsonl` stays `v: 1`.

**Consequences.** No network code and no new dependency: the files are the buffer, a Collector ships them to any backend, and the trace survives an endpoint that is down. A script instrumented with any OpenTelemetry SDK, and any upstream system that writes `traceparent` into a message, joins the same trace without decree knowing about it. Spans have millisecond precision, the precision of the events. Two invariants are tested: every span in `traces.jsonl` is named by exactly one event, at its times, and every event of a run has one trace id. Evidence: migration 83.

## D53: `decree process --retry` continues a run

**Context.** decree never continues a failed or interrupted run by itself ([D36](#d36-q10-a-killed-run-waits-for-decree-retry)), and a failed or interrupted migration blocks later ones. Continuing took two commands: `decree retry <id>` made the run `pending`, and the next `decree process` ran it. The common case is "continue the migration that is blocking the queue", so a person had to find its id, remember a second command, and then run `process` anyway. The failure message named `retry` with the id, but not the `process` that has to follow.

**Decision.** `decree retry` is removed; continuing a run is a flag on the command a person was going to run anyway: `decree process --retry [<id>] [--state <s>]` ([Retry](reference/cli.md#retry)). Without an id it continues the migration that blocks the queue, the earliest pending migration whose run is `failed` or `interrupted`; with an id, any run. It writes the same `transition` with `source: "retry"`, with the same default state and `--state` rules, and the same `process` then continues the run and everything queued after it. Every message that suggests continuing a run prints the exact command: ``Fix the cause, then run `decree process --retry`.`` for a blocked migration, `decree process --retry <id>` for a failed inbox run, and the same in `decree status`. `--retry` takes no `--dry-run` or `--format`, since `process` produces a stream; `retry --format json` and its schema went with the command.

**Consequences.** One command to remember, and the message that reports a failure is the command that continues it, copied as printed. The behaviour is unchanged: decree still never retries on its own, a retry keeps the run's folder and history, and `events.jsonl` still records `source: "retry"`, meaning a person continued the run. A script can no longer make a run `pending` without also processing the queue; nothing used that. Evidence: migration 85.

## D54: `decree skill` refreshes the skill

**Context.** [D30](#d30-q4-init-writes-the-decree-skill) removed 0.4's `skill` command when `init` began writing the skill. But `init` refuses an existing `.decree/` and never overwrites a file, so after upgrading decree nothing refreshed `.claude/skills/decree/`: a user copied the skill from decree's source tree by hand. `decree graph` and `decree schema` already rewrite the files decree owns.

**Decision.** `decree skill [--ai <claude|copilot|opencode>]` writes the skill the way `decree schema` writes the schemas: decree's own files (`SKILL.md`, `reference/*.md`) are overwritten through a temp file and a rename, a file in `reference/` that decree no longer ships is removed, and any other file in the folder is left alone. Without `--ai` it refreshes every skill folder that exists, else the one of the backend `init` would pick. `opencode` reads no skills, so for it the command writes nothing and exits 1. It prints each file, `unchanged` when already identical, and takes `--format json` ([D51](#d51-json-output-for-every-report-and-sarif-for-decree-check)). This supersedes the part of D30 that removed the `skill` command; `init` still writes the skill once and never overwrites it.

**Consequences.** Upgrading is: install the new version, then `decree skill` and `decree schema` ([Upgrading decree](reference/cli.md#upgrading-decree)). A user's notes beside the skill survive; an edit to `SKILL.md` itself does not, as it is decree's file. Evidence: migration 104.

## D55: Hosted schemas, found by path

**Context.** [D45](#d45-json-schema-for-shape-decree-check-for-meaning) and [D50](#d50-a-versioned-schema-for-every-file) had `decree init` write `.decree/schema/` and every machine start with `# yaml-language-server: $schema=../schema/v1/machine.schema.json`. decree validates with the schemas built into its binary, so the folder served only editors and AI agents, yet every project committed fourteen generated files and refreshed them after each upgrade, and every machine carried a line that did nothing without them. Prior art: SchemaStore is the catalog editors use to match files to schemas by path (Red Hat's YAML extension for VS Code and JetBrains IDEs read it by default), and GitHub Actions workflows, Docker Compose files and many other YAML formats are checked through it with no line in the file. A schema's `$id` is meant to be a stable URL.

**Decision.** The schemas' single source is `schema/` at the repository root, compiled into decree with `include_str!`, so the published files and the binary's are the same bytes; each `$id` is its raw GitHub URL on `main`, `https://raw.githubusercontent.com/jtmckay/decree/main/schema/v1/<path>`. A SchemaStore entry, `decree machine`, matches `**/.decree/machines/*.yml` and `*.yaml` to the machine schema ([editors.md](editors.md)); it is submitted once 0.5.0 is on `main`, so its URL resolves. `decree init` writes no `.decree/schema/` and no schema line, and its `.decree/.gitignore` lists `schema/`. `decree schema` is unchanged and optional: agents run it and read the local copy, and an offline editor can point at it through a `yaml.schemas` setting or the per-file line, which still works. `decree check` warns about the copy only when `.decree/schema/` exists. Messages and cron files are Markdown, whose frontmatter no editor checks, so `decree check` stays their checker. This supersedes the parts of D45 and D50 that had `init` write the folder and every machine carry the line.

**Consequences.** A project commits no generated schemas and a machine holds only its own content; an upgrade no longer leaves a stale schema warning in every project. Editors check machines with no setup once the SchemaStore entry is in, and until then a one-time setting does it. The `$id` URLs do not resolve until 0.5 is merged to `main`; during the beta the `v0.5` branch's raw URL serves the same files. An agent must run `decree schema` before reading a schema, which the skill says. Evidence: migration 105.

## D56: Ids to the microsecond, in the order they were made

**Context.** The inbox runs in filename order, and a filename is the message's id: the UTC second plus 6 hex chars from the sub-second nanoseconds XOR the process id. Messages queued in the same second therefore ran in an arbitrary order. A user's script queued image jobs, then speech jobs, so the GPU would switch models once; within one second the jobs interleaved, and the script had to sleep into the next second between the two batches. Prior art: RFC 9562 (UUIDv7) and ULID put the time first so ids sort by creation, and RFC 9562 section 6.2 adds clock precision below the millisecond (Method 3) and has a generator never repeat or go back in time (monotonicity).

**Decision.** An id is `YYYYMMDDTHHMMSS.ffffffZ-xxxxxx`: the UTC time to the microsecond, in ISO 8601 basic format with a decimal fraction, then the same 6 hex chars. Within one process, each id's time is later than the one before, even if the clock steps back. The hex chars only keep apart ids made by different processes at the same microsecond, whose messages were queued at once, so no order between them is wrong. Ids keep their human-readable form rather than becoming UUIDs, since they name run folders that people read.

**Consequences.** Messages queued one after another, by one script or by `decree emit` calls in sequence, run in that order. An id is 7 chars longer. Ids made before this change are still valid ids; one from the same second as a new one sorts after it, which matters only for messages queued across the upgrade. Migrations keep their file stem as id.

## D57: Gitignored `.env` files, one per machine if needed

**Context.** Migration 94 added `.decree/env`, a committed dotenv file of project settings with no secrets in it, and a script invoke's `env:` map for per-state values. Both broke a convention people already follow: a file named `.env*` holds local settings and secrets and is never committed, with `.env.example` as the committed template (Docker Compose, Vite, Next.js, dotenv libraries). A file named `env` was not recognisably either, a committed config file asked people to keep secrets somewhere else, and every machine's scripts got every variable, so a key one machine needed reached all of them. Prior art: Compose reads a project `.env` for every service and a service's own `env_file:` for that service only; Vite loads `.env` and then a more specific `.env.[mode]` over it.

**Decision.** `.decree/.env` replaces `.decree/env`: every script gets its variables, and the process environment wins over it, as with Compose's `.env`. A machine may name one more file with the root key `env_file: .env.<name>`, as a Compose service does: that machine's scripts get its variables over `.decree/.env` and over the process environment, since the file is the machine's own configuration. A child machine, a router or an emitted message runs with its own machine's file, so variables never pass from one machine to another. `decree init`'s `.decree/.gitignore` lists `.env*` and `!.env.example`; `env_file` must be named `.env.<name>`, directly in `.decree/`, so the gitignore always covers it (V14), and `.env.example` is never read. `decree check` checks every file for E1, warns about a missing `env_file` (a fresh clone has none) and about a `.gitignore` without `.env*` while one exists. The invoke `env:` map is removed: a value that differs per state is a two-line wrapper script that sets it and runs the shared one. decree still reads no setting of its own from these files, so commands that run no scripts do not read them.

**Consequences.** Secrets and local settings go in one place that git ignores, and a machine's secrets reach only its scripts. A project's documented settings move to a committed `.env.example`. Projects on an earlier beta rename `.decree/env` to `.decree/.env`, add `.env*` and `!.env.example` to `.decree/.gitignore`, and replace each invoke `env:` with a wrapper script; decree does not read `.decree/env` any more. Values that were committed for everyone, such as a shared service URL, are now per checkout unless the template supplies them.

## D58: `process` shows its runs, and logs do not mark stderr

**Context.** `decree process` and `daemon` printed nothing while a run went on, so a person ran `decree tail` in a second terminal to see a migration's agent work, and `tail` stopped when its run ended, so a queue of 31 migrations needed it restarted 31 times. A script's stderr lines carried a `[stderr] ` prefix in its log, which made an agent that writes almost everything to stderr (opencode) hard to read anywhere the log was shown. Log names repeated a script named as its state (`0004-gate-gate.log`). Prior art: a CI runner (GitHub Actions, GitLab) streams each step's output with a header and a result line, and `docker compose up` streams by default with `-d` or `--quiet-pull` to silence it; `cargo` keeps one progress line at the bottom of a terminal and none in a pipe; CI runners and `docker logs` show stdout and stderr interleaved and unmarked.

**Decision.** `process` and `daemon` print each run as `tail` would, behind a `▶ <id> · <machine>` header, and a line as it stops (`✓ <id> done in 7m 31s`); on a terminal only, a status line stays below the output with the run, the innermost machine and state, the elapsed time and `n/total` for this pass. A thread prints it from the run's files, told by the pipeline when each run starts and stops, so even a run shorter than a poll is printed whole and in order. `--quiet` restores the silent output for cron and CI. `tail` without an id follows each run in turn until stopped; `tail <id>` still follows one run. Logs are written unmarked, so `output` conditions and a router's `input` see the lines as the script wrote them. A log is `NNNN-<state>.log` when its script is named as its state. `decree status` also lists active runs in decree projects below it, and works above any project.

**Consequences.** Watching a run needs one command. A condition or router prompt that matched `[stderr] ` must match the bare line; the recorded runs in the examples and fixtures were rewritten to the new names and unmarked lines. Log shippers parse an optional script part (docs/reference/observability.md). Scripts that need stderr apart can write their own file.

## D59: Machines are read again before each run

**Context.** `process` and `daemon` loaded the machines once, at start, and `daemon` read only the `.env` files again on each pass. A user editing a machine while a daemon ran saw nothing change, and lost the most time of any beta issue finding out why: the edit did nothing until a restart, with no sign that the files on disk differed. A long `process` over a queue of migrations had the same problem. Prior art: nginx, Prometheus and HAProxy reload their configuration on a signal and keep the old one when the new one fails to parse; Kubernetes controllers, Docker Compose's `watch` and Vite pick up file changes as they happen. A server reloads between requests, never during one.

**Decision.** Before each run, `process` and `daemon` compare the machine files with those last loaded and, if any differ, load and check them again (V1–V21), as they do the `.env` files. Machines that pass replace the old ones for every later run, and `reloaded machines: <id>, …` names what changed. Machines that fail are not used: every machine stays as last loaded, as nginx keeps its old configuration, and the errors are printed once, with ``runs keep the machines last loaded until this is fixed. Run `decree check`.``. While they fail, each check loads them again, so a fix in a script file also counts. A run already going keeps its machine until it finishes, waits or is interrupted; one continued later uses the machine as it is then, as a restart did. No signal or `reload` command: a file edit is the signal, and decree has no long-lived configuration besides these files.

**Consequences.** An edit applies to the next run without a restart, in both commands. A machine edit that removes or renames a state a waiting run is in fails that run when it continues, as it did after a restart. Pending migrations are still validated once at start (rule 6); one added later that is invalid fails its own run. `daemon` gains `--retry [<id>] [--state <s>]`, as `process` has, so continuing a failed run does not need the other command.

## D60: A script may name `done`

**Context.** A script names its event in `$DECREE_EVENT_FILE`, and exit 0 with nothing written is `done`. `done` was reserved, like `error` and `unsure`, so a script that wrote `done` got `error`: an easy mistake, made by a user and by agents writing scripts, with nothing to gain from it. Prior art: a CI step that sets its outcome explicitly to the value it would have had is not an error (`exit 0` in a shell script, `core.setOutput` of a default in GitHub Actions).

**Decision.** A script that writes `done` gets `done`, the same as writing nothing. `error`, `unsure` and names starting with `done.` or `error.` stay reserved for scripts, since each would let a script raise what decree raises (a failure, a low-confidence decision, a compound state's completion). A `model` or `person` option still may not be `done`: an option is a choice among named outcomes, and a reply of `done` would read as the decision finishing.

**Consequences.** Scripts that write `done` work as their authors meant. `events.jsonl` records it like an empty file, with `source: "exit_code"`, so nothing downstream changes.

## D61: The environment is declared

**Context.** Work often needs the environment to change first: a test framework, a browser for end-to-end tests, a linter. Asked to "install X", an agent writes steps that run once: in a beta test one created a Python venv, which failed halfway on a missing system package and left a `.venv` without pip that its own existence check then accepted. Nothing recorded what the environment should hold, so another checkout could not repeat it and nothing noticed when it drifted. `develop`'s `precheck` checked only its AI's command. Prior art: Ansible declares state (`state: present`), checks before it changes and reports `ok` or `changed`, with `--check` to change nothing; `brew bundle check` against a Brewfile; asdf and mise's `.tool-versions`; GitHub's Scripts to Rule Them All (`script/bootstrap`).

**Decision.** `decree init` writes `lib/infra/`: `requirements`, one resource per line (`kind name version source`) in dependency order; `kinds/<kind>.sh`, each a `check` and an `install` function; and `run.sh check|apply`, which walks the lines. It writes one kind, `command`, since decree cannot know a system's package manager, and a requirements file listing the AI backend's command. It also writes the `infra` machine, `declare` → `apply`: the AI edits only the requirements, adding a kind only when none fits, and `apply` installs what is missing and checks each line again, so a separate verify state is not needed. A kind never uses `sudo`: a step only a person can do prints the command and fails, and the person retries. `develop`'s `precheck` becomes `run.sh check`. The files live in `lib/`, beside `ai.sh`, rather than in the project's own `script/`, which a project may already have.

**Consequences.** The first `infra` migration builds the environment and later ones add to it, each a reviewable diff of the requirements. A fresh checkout or CI runs `.decree/lib/infra/run.sh apply`, without decree. A run whose environment is short stops at `precheck`, naming the line, before the AI starts. This is not configuration management for machines or services: a project that needs that writes a kind that calls Ansible or Nix.

## D62: qa finds bugs and never fixes them

**Context.** `develop` checks the acceptance criteria a message states; nothing looked for what no one wrote down. In a beta test, an adversarial QA machine on Claude Haiku found every bug planted in a small app (stacked overlays, corrupt saved progress, an uncaught full disk, missing art) and two that were not planted, and each fix went through `develop`. Its triage over-split them (13 reports for about 6 causes) and called a test no code could pass a bug. Prior art: chaos engineering (Netflix's Chaos Monkey, steady-state hypotheses), property-based testing (QuickCheck, Hypothesis), strict expected failures (Python's `unittest.expectedFailure`, pytest's `xfail(strict=True)`, Playwright's `test.fail()`), and a separate QA role that reports bugs and does not fix them.

**Decision.** `decree init` writes `qa`, a straight line: `recon` (the attack surface) → `attack` (chaos tests in `QA_DIR`, each naming its wrench and invariant, random choices seeded) → `run` (the suite into `chaos.log`; a failing test is a finding, so only a suite that cannot start is an error) → `triage` → `report` (one `develop` message per bug report, `emits: [develop]`). Triage sorts each failure into a real bug, a wrong test or acceptable behaviour, marks a bug's tests with the framework's strict expected-failure marker so the suite passes and fails again once the bug is fixed, writes one report per root cause, and writes a `STOP` question when the docs do not settle a failure. The suite must then pass. `lib/qa/qa.sh` holds `QA_DIR` (`tests/chaos`) and `QA_RUN`, the suite's command, empty until the project sets it; `recon` fails before asking the AI while it is empty, as the gate says it is unconfigured. A guard hashes every file outside `QA_DIR` and `.decree/` (from `git ls-files`) before each AI step and fails the step, naming each file, if one changed; it restores nothing, so it never overwrites a person's work.

**Consequences.** qa needs git and a chaos suite command. A bug reaches `develop` as a failing test with the invariant it breaks, and a fix is done when the test passes unmarked; adding `QA_RUN` to the gate makes that automatic. `lib/qa/invariants.md` starts empty (qa then takes invariants from the docs and code), and `wrenches.md` lists eight general wrenches a project extends.

## D63: One commit per run, from a clean tree

**Context.** The built-in machines changed files and left them uncommitted. In a beta run, `qa` queued five bugs for `develop`; the first run's fix masked another bug (a broad `except`), failed, and left its change in the tree, and each of the next three runs found that change, could not tell it from its own work, and stopped to ask. A run's work could not be reviewed or reverted on its own. Prior art: Aider commits each change the agent makes with a message of its own; `npm version` and `cargo publish` refuse to run on a dirty work tree; the `feature` example's `commit` script, an `onentry` of `done` that commits the code and the `processed.md` line together.

**Decision.** `decree init` writes two shared scripts, and `develop`, `infra` and `qa` use both. `clean_tree`, a root `onentry`, fails the run before anything else runs unless git is on `PATH`, the project is a work tree and `git status --porcelain` is empty, naming what is uncommitted. It records that it passed in the run folder, so `decree process --retry`, which runs root `onentry` again, continues with the run's own changes. `commit`, an `onentry` of `done`, stages everything and commits it, titled with the message's first `# ` heading, with `decree run <id> (<machine>)` as the body; a run that changed nothing commits nothing, and a failed commit ends the run in `failed`, not `done`. `lib/infra/requirements` declares `command git`. A third, `stash`, an `onentry` of `failed`, puts the failed run's changes in a git stash named after the run (`decree <id>: <title>`) and prints how to continue: `git stash pop`, then `decree process --retry <id>`. It stashes only when `clean_tree` passed for the run, so a run that failed because of a person's own uncommitted changes leaves them alone. `router` changes no files and uses none of them.

**Consequences.** Each `done` run is one commit, and a migration's commit includes its `processed.md` line. A failed run's changes wait in a named stash, so the runs queued behind it start clean and one failure does not fail them all; `git stash list` shows what each failed run left, and `git stash show -p` its changes. A pop conflicts, as any stash does, when runs since changed the same code; the person resolves it, or drops the stash and queues the message again. A person's own uncommitted changes still fail every run at `clean_tree`, without asking an agent; for work alongside a person, a git worktree of the person's making keeps the two apart. People commit or stash their own changes before queuing work. A project that does not want the commits removes `commit` from the `done` states, and `stash` from `failed`.

## D64: A retry is the run's next attempt, with fresh visits

**Context.** `visits` counted every visit in a run and never reset. A machine that bounds its rounds with `check: { visits: …, less_than: … }` sent a retried run straight to its escalation, because the run had already used its rounds: a person's `decree process --retry` bought nothing. A beta project worked around it by counting rounds from `events.jsonl` since the last `retry` event. Three fixes were weighed: reset visits on a retry; a second subject, `visits_since: retry`; or `--retry --param` to raise the limit for one run. Prior art: GitHub Actions numbers each re-run of a workflow run (`run_attempt`, `GITHUB_RUN_ATTEMPT`), and a re-run starts its jobs afresh.

**Decision.** Each `decree process --retry` (or `daemon --retry`) starts the run's next attempt. The `retry` event records `run_attempt` (2 for the first retry; a run never retried has none, and is on attempt 1), and every script gets `DECREE_RUN_ATTEMPT`. `visits` count from the last `retry` event, which counts as the first visit of the state it enters. `DECREE_ATTEMPT` keeps its meaning, the attempt of one invoke inside a visit.

**Consequences.** A retried run gets all its rounds again, with no new syntax and no script that reads `events.jsonl`. A machine cannot count visits across retries any more; a retry is a person's decision, so a loop cannot retry itself forever. A script that should behave differently on a retry reads `DECREE_RUN_ATTEMPT`. Evidence: the beta project's `rounds_left.sh`.

## D65: A failed run keeps its changes and holds the queue

**Context.** D63's `stash` put a failed run's changes in a git stash so the runs behind it started clean. In beta use it caused three problems. The work was hidden: a retry started on a tree without it, and the agent did not know a stash existed. It took files that were not the run's work (`--include-untracked` took a project's own log). And it was not limited to the project folder: `git status` and `git stash push` ran on the whole repository, so in a decree project inside a larger repository a failed run stashed the other projects' changes too. Prior art: a CI system keeps a failed job's workspace for inspection; `git rebase` and `git merge` stop with the work in the tree and a marker file (`.git/MERGE_HEAD`, `rebase-merge/`) that blocks the next operation until `--continue` or `--abort`; a pidfile names the process that holds it on its first line.

**Decision.** `keep` replaces `stash` as `failed`'s `onentry` in `develop`, `infra` and `qa`. It leaves the changes where they are, prints them with the command that continues the run and the one that stashes the project folder instead, and writes `.decree/HOLD`, whose first line is the run's id. While `HOLD` exists, `process` and `daemon` start and continue no runs; `process` prints it and exits 1, and `daemon` prints it once and goes on polling. `decree process --retry` of the run it names removes it; deleting it releases the queue too. Like `stash`, `keep` does nothing when `clean_tree` never passed. `clean_tree`, `commit` and `keep` work on the project folder only (`-- .`). `clean_tree`'s message lists at most 20 paths and says how to find and continue the run that left them.

**Consequences.** A retry builds on the last attempt's work, which the agent sees in `git status`. Nothing runs on a tree that holds another run's work, so one failure stops the queue instead of failing every run behind it; that is the price of keeping the work in sight. A person who wants the queue to go on sets the changes aside (`git stash push --include-untracked -- .`) and deletes `HOLD`. `HOLD` doubles as a pause: a person can create it to stop the queue. Evidence: a beta project's `keep.sh`, and its stash of a sibling project's changes.

## D66: One AI helper with every backend, a capped limit wait and a nudge

**Context.** `lib/ai.sh` held one backend's `ai`, chosen at `init`. A beta project needed two (a local model through OpenCode for most rounds, Claude for a last one), so it wrote its own `ai`, `ai_claude` and `ai_agent`, and its `ai_claude` lost the base helper's usage-limit wait: Claude's "You've hit your session limit · resets 11:30am" exited 1, and `attempts: 3` used all three in under two minutes. A wait with no limit is no better for a weekly limit, which can be days away. The same project's local model wrote scratch files to `/tmp`; with OpenCode's default `"external_directory": "ask"`, `opencode run` rejects such a write and ends the session with no reply, so the project continued the session with a nudge. It also logged every Claude call to a table of its own. Naming the switch took three tries. `AI_AGENT` is set by Claude Code in the shells it starts, and every coding tool calls its sessions agents. beta.7's `DECREE_AI` broke the rule that `DECREE_*` belongs to decree: decree had to pass it through to scripts and allow it in `.env` files, and an agent reading a project's `.env` would take it for decree's own. The switch names what it picks, the command-line tool `ai` runs, as `decree init --ai` does: `AI_CLI`, with a data entry `ai_cli` for a child machine. Prior art: the base helper's own wait; `sysexits.h`'s `EX_TEMPFAIL` for "try again later"; OpenCode's permission config.

**Decision.** `lib/ai.sh` is one file for every backend: `ai_claude`, `ai_opencode` and `ai_copilot`, with `ai` calling, most specific first, the one the run's data entry `ai_cli` names (a message's or a parent's `params`), else the one `AI_CLI` names, else the one `init` chose: a run's choice beats the project's setting. `ai` empties the caller's event file, logs every call to `.decree/ai-use.md` (gitignored), and returns 0 when the call left a `STOP` file, so a script's `STOP` check names `stop` instead of an attempt failing. `ai_claude` waits for a usage-limit reset up to `AI_LIMIT_WAIT` (default `6h`) and resumes the session; past it, it writes `STOP` with the reset time. `ai_opencode` takes `OPENCODE_MODEL` and continues a session a rejected write ended, up to `AI_NUDGES` times (default 2). `decree init --permissions` writes OpenCode's `"external_directory": "deny"`, which keeps the session going, and `"share": "manual"` in place of the deprecated `autoshare`.

**Consequences.** A machine switches backends per state or per child run with no `ai.sh` of its own, and every backend keeps its own handling. A usage limit costs no attempts: a short one is waited out, a long one stops the run with a note saying when to retry. Every AI call in a project is in one table. `external_directory` covers OpenCode's file tools only, not shell commands, so the docs call it no sandbox; the prompt and `AGENTS.md` keep writes in the project. A project with its own `lib/ai.sh` keeps it: decree never rewrites `lib/`. Evidence: the beta project's `ai_claude` log, and an OpenCode 1.18.35 reproduction of both `ask` and `deny`.

## D67: The attention folder says what needs a person

**Context.** A beta user lost hours to runs nobody knew were blocked: beta.9 exited without a word, a run sat in a `person` state for 6.5 hours, and beta.10's message was the last line of a long log. D65's `.decree/HOLD` covered one case only, a failed run with changes in the tree, and the user had yet to see it help. What needed a person was spread over `process`'s output, `decree status` and the logs. Prior art: `processed.md`, decree's own one-file ledger of what is done; a CI system's list of failed jobs, each with its re-run button; `git rebase` stopping with a marker file and the commands that go on; and D65's `HOLD`, which holds even when it cannot be read.

**Decision.** decree keeps one markdown file per run that needs a person in `.decree/attention/<id>.md`: YAML frontmatter (`kind: run`, `run`, `machine`, `message`, `status`, `state`, `since`, `holds`; `attention.schema.json`), then what happened and the exact command that continues the run (`decree process --retry <id>`, or a `decree event` line per option). It writes the file when the run becomes `failed`, `interrupted` (a signal, or a crash found later) or `waiting` in a `person` state, and for a migration waiting for an interrupted child, and deletes it when the run becomes `active` or `pending`, finishes otherwise or is pruned; it does so as the status changes, never by rescanning, so a file a person deleted stays deleted. The folder supersedes D65's `HOLD`: `keep` writes the run's own `hold` file, its attention file then has `holds: true`, and while any file holds, `process` and `daemon` start and continue no runs, as `HOLD` did. `--retry` of the run removes its `hold` and its file; deleting the file drops the run, and decree then deletes its `hold`. A `.md` file there that cannot be read, has no frontmatter or does not match the schema holds the queue too; any other file is ignored. `process` ends with `<n> run(s) need attention: .decree/attention/`, and `decree status` starts with `Attention:`. The manual pause `HOLD` allowed becomes `decree stop` (migration 107), which writes a file of its own.

**Consequences.** One folder answers "what is waiting for me", in files a person, an editor or another tool can watch. The files are read-only: a reply still goes through `decree event` or a reply message, D40's one reply channel, so `decree event`'s refusal of a second queued reply to one wait still holds; a file that took answers would be a second channel with no such check. There is no hook: a `person` state's `ask` script already tells someone, and a killed run cannot run one, which is why a crash's file is written when `process` or `daemon` finds the stale lock. An unreadable `.md` file holds so that anything can halt the queue without knowing the contract, as `HOLD` did; decree never rewrites or deletes a file it did not write, so only deleting it releases the hold. A failed child run has a file only when it holds, since its parent takes the failure as `error`. Evidence: the beta user's report of beta.9 and beta.10.

## D68: A graceful stop is an attention file

**Context.** Ctrl-C (SIGINT) or SIGTERM was the only way to stop `process` or `daemon`, and it interrupts the run that is going, which then needs `decree process --retry`. A beta user wanted "finish this run, then stop". D67 made `.decree/attention/` the one place a person looks for what needs them, and replaced the other control file in `.decree/`, `HOLD`. Prior art: `nginx -s quit`, which finishes the requests in flight and then exits; Sidekiq's quiet signal, which takes no new jobs; and git's `MERGE_HEAD`, a marker file that blocks until it is removed.

**Decision.** `decree stop [-m <note>]` writes `.decree/attention/manual-stop.md`, with frontmatter `kind: manual-stop`, `since` and `holds: true` (the second shape of `attention.schema.json`) and a body that says what was done and how to resume. It holds the queue as any holding file does (D67): `process` and `daemon` check before a run starts or continues, so the run going now is not interrupted; it reaches a final state or waits. `process` then prints the file and exits 1; `daemon` prints it once and goes on polling. Deleting the file resumes, and a daemon needs no restart. A second `decree stop` leaves the file, so the first `since` stays. `--retry` leaves it too: the retried run waits as `pending`. decree writes nothing else for it: no other control file in `.decree/`, no pid list, no signal.

**Consequences.** One place to look still answers "why is nothing running", and the same act that releases any hold, deleting a file, resumes after a stop. A stop reaches every `process` and `daemon` of the project at once, wherever it was started, with no pid to find. A run that waits for a person stays waiting; the stop holds the reply's delivery until the file is deleted. Ctrl-C keeps its meaning: interrupt now. Evidence: the beta user's request.

## D69: A process runs the machines it is given

**Context.** A beta user wants several decree processes in one project folder, each handling its own machines: one runs `develop`, another `comfy`. Processes already stay apart: an inbox claim is an atomic rename, and a run has its `.lock` (D31). What was missing was a way to say which machines a process runs. Prior art: Celery's `--queues` and `--exclude-queues`, which give a worker the queues it consumes, or all but some.

**Decision.** `process` and `daemon` take `--machine <m>` or `--exclude-machine <m>`, each repeatable and each a comma-separated list; both together exit 2, and a name that is not a machine in `.decree/machines/` (or a built-in) is an error naming it. `DECREE_MACHINES` and `DECREE_EXCLUDE_MACHINES` set the same from the shell or `.decree/.env`; a flag beats both, the shell beats `.env`, and both from one place exit 2. They are the only `DECREE_*` keys `.decree/.env` may set; decree reads them itself and never passes them to scripts. A filtered process delivers replies and timeouts, continues `pending` runs, claims inbox messages and fires cron only for its machines; everything else stays where it is. A run belongs to the machine of its root run: the process that runs a parent steps its children, whatever their machine. Migrations keep one order for every process: when the first pending migration is for a machine a process does not run, that process starts no later migration and ends with ``Held back: migration <file> is for machine `<m>`, which this process does not run`` (exit 0).

**Consequences.** One folder serves several processes with no coordination beyond what was there: the claim rename and the run lock. Migrations stay one ordered history, so a migration for `b` waits for the process that runs `b`, however many `a` migrations queue behind it. There are no leases or heartbeats: a process that dies leaves its run's lock stale, which the next process that runs that machine finds and marks `interrupted`, as before; a lease would add clocks and renewal for nothing the lock does not already give. `.decree/.env` applies to every process in the folder, so different filters go by flag or shell. The built-in `develop`, `infra` and `qa` share the work tree through `clean_tree` and `commit`, so two processes must not run them at once in one checkout; that is the user's call, and a git worktree per process is the way. A holding attention file (D67, D68) holds every process, whatever its filter. Evidence: the beta user's request.

## D70: A message describes the outcome, not the steps

**Context.** A message is a spec for an agent. Migration 110 asked for a warning "with its own rule id, following the existing warnings", and the existing warnings had no rule ids: the step its author pictured did not fit the code, and the run stopped. A message that says *how* (which function, which file, in what order) ties the agent to one implementation; when the code differs, the run stops or the agent forces the plan. decree already works the other way for the environment: `infra` declares the desired state and `apply` reaches it (D61). Prior art: declarative configuration (Ansible, Terraform: desired state, not commands) and BDD's Given / When / Then, already decree's acceptance criteria.

**Decision.** decree's guidance on writing a message (the skill, its `reference/messages.md`, and [messages.md](reference/messages.md#writing-a-message)) has a rule beside "one concern per migration": describe the outcome, not the steps. An outcome is what a user or another program can observe, the public contract (command and flag names, file names, formats and locations, exit codes, messages printed), what must not change, and why. A step is which functions, modules or files to change, in what order, with which data structures; one is named only as a constraint, never as a suggestion. The test for a sentence: if a different correct implementation would fail it, it is a step. The body's shape is `## Overview`, `## Outcome`, `## Constraints`, `## Acceptance Criteria`. Every example message follows it, and `qa`'s triage writes each bug report as the broken invariant and the expected behaviour, with no fix.

**Consequences.** Only guidance and examples change: decree never reads a message's body, so a message with other headings, `## Requirements` included, is valid and runs as before. An outcome may still name a file when the file is the contract (its name, format or location) or a constraint ("the limit stays in `src/config.rs`"). Evidence: migration 110's `STOP`.

## D71: Migration names keep their order by padding, then a letter prefix

**Context.** Migrations run in byte order of filename (rule 3 of [Migrations](reference/messages.md#order-files-run-in-order-at-each-start)), which is simple and predictable. A project that numbers `1-`, `2-` … `99-` finds that `100-` sorts before `99-`: this repository did, and from migration 100 on every new migration drew `decree check`'s inserted-migration warning. A beta user names migrations with a letter and a number (`B17`, `C01`), which sorts after any digits. Prior art: Django names migrations `0001_initial.py`, and golang-migrate's `create -seq` pads to `-digits` (6 by default), so that byte order is numeric order.

**Decision.** Migration order stays byte order of filename; decree does not parse numbers out of names. The guidance on writing a migration (the skill, its `reference/messages.md`, and [messages.md](reference/messages.md#writing-a-message)) says: pad the number to the width the project will need (`001-`); a project that outgrows it continues with a letter prefix (`A01-`, then `B01-`), because letters sort after digits; and `decree check` warns when a new name sorts before one that already ran. That warning ends with the same hint: ``To keep the order, pad numbers to the width the project needs (`001-`) or continue with a letter prefix (`A01-`), which sorts after digits``.

**Consequences.** Order is still what `ls` shows, and no project's order changes. A person who meets the warning learns the fix there; a project already past `99-`, like this one, continues with `A01-` without renaming anything, since migrations are immutable. Uppercase letters sort before lowercase in byte order, so the hint uses uppercase. Evidence: this repository's migrations 100–113 and the beta user's naming.

## D72: Every inbox message gets a time id as it arrives

**Context.** The inbox runs first-in, first-out by filename, and `decree emit`, `decree event` and cron name each file by its id, the time to the microsecond (D56). A file a person or another tool wrote kept the name it was given, so it ran before or after the rest by the accident of its name: `01-hi.md` jumped ahead of everything emitted, `zz.md` waited behind it. A frontmatter `id` was honoured, so a copy of a run's `message.md` failed at claim, its `id` already having a run. Prior art: Maildir, where a delivered message is given a unique, time-based name on arrival (`new/<time>.<unique>.<host>`), so order never depends on what the sender called it.

**Decision.** A file in `inbox/` is queued when it is named `<id>.md` by an id of the form decree makes, its frontmatter `id` (if it parses) is that id, and that id has no run. Every other `*.md` file not starting with `.` gets an id the first time `process` or `daemon` sees it: a fresh one from that moment, so it runs after everything already queued, with files first seen together ordered by modification time, then name. decree drops the file's `id`, `state`, `trigger` and `arrived_as`, sets `id` first and `arrived_as` to the file's name, keeps every other key and the body, writes the file in place through a temp file, then renames it to `inbox/<id>.md`. Only queued files are claimed. One process renames at a time, holding `inbox/.lock` with the same `O_EXCL` and pid check as a run lock; another that finds it held renames nothing that pass. The claim event's `file` is the name the message arrived with. The key is `arrived_as` rather than `filename` (the `Content-Disposition` parameter for a sender's suggested name, RFC 6266), because a top-level `filename` is a likely key of a user's own, which decree would then overwrite.

**Consequences.** Order is the order of arrival, whatever the writer called the file, and a person can no longer choose a run id: `id`, `state`, `trigger` and `arrived_as` are decree's alone, as `state` already was. Copying a message (a migration, a run's `message.md`) into `inbox/` runs it again as a new run, and leaves the old run unchanged. `decree status` lists such a file by its new name once a pass has seen it; `--dry-run` renames nothing, so it lists the names as written. The file is rewritten before it is renamed, so a crash between the two leaves a file that is still not queued, and the next pass gives it an id again: no message is lost or run twice. A file a run is being claimed from is never renamed: a claim takes only queued files, and a run folder without `message.md` (a claim in progress) keeps its file queued. A file whose frontmatter does not parse is renamed unchanged and fails at claim as before, with no `arrived_as`. Tests and recorded runs that relied on a hand-picked `id` now queue as `decree emit` does, `inbox/<id>.md`. Evidence: the user's request (migration A02).

## D73: Migration runs get time ids like every other run

**Context.** A migration's run id was its file stem (`runs/01-rate-limit-upload/`), while every other run's id is the time it was made (D56, D72). So `runs/` and `decree status` sorted migration runs apart from the rest, and a migration's numbering (`99-`, `100-`, `A01-`) leaked into run order: `100-x` sorted before `20261001T…`, `A01-` after. The stem had one use, finding a migration's run, which a person does by name. Prior art: GitHub Actions, where a workflow's runs have ids of their own and are found by the workflow's file name (`gh run list --workflow ci.yml`); Flyway, whose `flyway_schema_history` gives each applied migration a row of its own (`installed_rank`) that records the `script` it ran, instead of naming the row after the file.

**Decision.** A migration's run has a time id, made as it starts, and its `message.md` records the file as `migration: <file>`; `migration` is decree's alone, like `id`, so a file in `inbox/` loses it (as it arrives, and at claim for a file queued under its id) and its run is not a run of that migration. A migration's runs are those that record it, and also a run folder named by its stem whose `message.md` has `trigger: migration`: run folders are the record and are never renamed, so the runs of every project from before keep working, this repository's own included. Its newest run is the latest time id, else that folder; it decides what it always did: a migration that has a run is not started again, and a newest run that is `failed`, `interrupted` or `waiting` blocks later migrations. Wherever a person names a run, `--retry` on `process` and `daemon`, `decree status <id>`, `decree tail <id>` and `decree event <id>`, a migration's file name or stem means its newest run; a name that is a migration's is read as one first. Everything that shows a migration's run shows its file beside the id, `<id> (<file>)`: status lines, `process` and `tail` lines, `Waiting:` lines, the `--retry` notice, `prune`, the attention file's `message`, and the built-in `commit`'s title, `<heading> (<file>)`. `prune` keeps a failed migration's run by the file its `migration:` names.

**Consequences.** One kind of run id: runs sort in the order they were made, migrations' included, so `decree status --all` lists an emitted run, a migration's run and a later emitted run in that order. A person still types `01-a`, and every line that shows a migration's run names its file, so nothing is lost by the id; scripts that read `DECREE_MESSAGE_ID` as the stem must read `migration:` from `DECREE_MESSAGE` instead, as the built-in `commit` does. Finding a migration's run reads each run's `message.md`, a small file, once per lookup. A crash between creating the run folder and writing its `message.md` leaves an empty folder that is no migration's run, so the migration starts again under a new id, which is right: it never ran. `message.schema.json` gains `migration` as an optional string, as do a run in `cli/status.schema.json` and `cli/prune.schema.json`. The examples' recorded runs and the test fixtures use time ids for their migration runs. Evidence: the user's request (migration A03).

## D74: `decree emit` reads a whole message

**Context.** `decree emit` read stdin as the body only. Given a whole message file (`decree emit --machine develop < .decree/migrations/01-a.md`), it nested the file's frontmatter inside the new body and needed `--machine` repeated, though the file named one. Since D72 and D73, copying a message into `inbox/` runs it again as a new run, but a script, or a person who wants the new id printed, had no one command for it. Prior art: `git am` and `sendmail -t`, which read a whole message on stdin and take its headers from it, and `kubectl apply -f -`, which reads a whole object, its kind and name included, from stdin.

**Decision.** Stdin that starts with frontmatter (a `---` line, as [Parsing and writing](reference/messages.md#parsing-and-writing) defines it) is a whole message: its frontmatter is the new message's and the rest is its body. The keys decree sets, `id`, `state`, `trigger`, `arrived_as` and `migration`, are dropped, as for a file placed in `inbox/` (D72, D73); every other key is kept. `--machine` replaces the frontmatter's `machine` and may be left out when it names one; each `--param` replaces that one param and keeps the rest. An emitting run's `parent` and `depth`, `trigger: emit` and a script's `TRACEPARENT` are set as for any emit. Frontmatter that does not parse, names no machine or an unknown one, or has `params` the machine does not accept is refused with the error `decree check` gives for the same file, at its stdin line (`stdin: line 1: no `machine` key`), and nothing is queued. Stdin without frontmatter is the body, byte for byte, as before, and needs `--machine`. The message guidance gains a "Run a message again" recipe: `decree emit < <file>`, or copying the file into `inbox/`.

**Consequences.** Rerunning a migration or any saved message is one command, and the copy is a new inbox run, never a run of that migration: the migration file and `processed.md` are untouched. A body that itself starts with a `---` line is now read as frontmatter, as it would be in a file in `inbox/`; such a body is emitted by putting an empty frontmatter (`---` twice) before it, or `--machine` and a first line that is not `---`. `decree emit` reads stdin before it checks the machine, since the machine may come from stdin; a script always gives it stdin. Evidence: the user's request (migration A04).

## D75: `max_depth` is a variable with a default

**Context.** `max_depth` stops a chain of emits and child runs from looping forever. It was the constant 10 since migration 63 removed `config.yml`, so a project whose real chains go deeper, a router under a child machine under an emitted follow-up several times over, could not run them at all. decree already reads two settings of its own as variables, `DECREE_MACHINES` and `DECREE_EXCLUDE_MACHINES` (D69). Prior art: `GIT_*` and `TF_*` variables configure a tool without a file; bash's `FUNCNEST` and Python's `sys.setrecursionlimit` bound recursion with a default that can be raised.

**Decision.** `DECREE_MAX_DEPTH`, a whole number of at least 1, sets `max_depth`; without it, or empty, it is 10. It comes from decree's own environment, else `.decree/.env`, as the machine filter does; `.decree/.env` may set it, and a machine's `env_file` may not, so one value holds for every machine of the project. The same limit applies to `decree emit`, a `machine:` child run and a `model` router run. Scripts get the value in effect as `DECREE_MAX_DEPTH`: decree strips every inherited `DECREE_*` from a script's environment, so without it an emit inside a run would fall back to `.decree/.env` and miss a limit given in the shell of the `process` or `daemon` running it. A value that is anything else (`0`, `ten`, `+5`) is refused before anything runs, naming the variable and the value: `process`, `daemon` and `emit` exit 1, and `decree check` reports E1 at its `.decree/.env` line, or exits 1 with the message for the shell's, which is in no file. A refused emit says how to change the limit; the event text, `max_depth <n> reached`, is as before. Finding a run's root (for `DECREE_ROOT_RUN_DIR`) follows `parent` until a run names none, refusing only a loop, where it stopped after 10 parents.

**Consequences.** Deeper chains run by setting one variable, and still stop: there is no unlimited value. A run recorded under one limit reads and continues under another; only new emits and child runs are checked, against today's limit. No configuration file is added. A decree started inside a script (a test suite run by a gate script) inherits `DECREE_MAX_DEPTH` from that script, so the outer project's limit beats the inner project's `.decree/.env`, as any shell variable would; a test that sets the inner limit removes the variable first. Evidence: the user's request (migration A06).

## D76: Bare `decree` prints a synopsis

**Context.** Bare `decree` was `decree process`. Someone who typed `decree` to see what the tool does started agents and commits instead, in the one command that changes the most. Prior art: git, cargo and docker print help when given no command, and run nothing.

**Decision.** `decree` with no command prints `src/templates/synopsis.md` byte for byte and exits 0, inside a project or not, and reads, writes and runs nothing. The synopsis is the README's quick start in short, written by the user: install or update, `decree init`, a script, a machine that runs it, a message for that machine, then the commands that check, graph and run it and show what ran. `decree process` is unchanged, and nothing runs it implicitly. A test runs the synopsis's steps 1 to 5 in an empty directory and finds the `hello` run `done`, and another fails when its install line differs from the README's or the one `decree upgrade` prints.

**Consequences.** Running the queue takes `decree process` by name, so a cron line, script or habit that ran bare `decree` now prints the synopsis and does nothing; it exits 0, so such a job does not fail loudly, and its log shows the synopsis instead of runs. `decree help` stays the full reference. Evidence: the user's request (migration A07).

## D77: A machine's files live with its scripts

**Context.** `.decree/lib/` and `$DECREE_LIB` (migration 94) were a place for what scripts share: bash functions, config and data. In practice almost everything there belonged to one machine: `lib/infra/` was `infra`'s, `lib/qa/` was `qa`'s, the newsletter's feeds were the newsletter's, the ComfyUI workflows were `comfy`'s. The one file several machines shared, `ai.sh`, was shared only by the built-ins. Plugins (A09) would each own paths in a folder every plugin writes to, and those paths could only conflict. decree already runs only the file a state names in `scripts/<machine>/` and ignores the rest (V12). Prior art: a Helm chart, an Ansible role and a Terraform module each carry their templates, defaults and files in their own directory, not in a folder shared with every other chart, role or module.

**Decision.** decree has no `lib/`: it does not define, create, export or check `.decree/lib/` or `DECREE_LIB`. A machine's helpers, config and data sit beside its scripts in `scripts/<machine>/`, and scripts reach them by path from the project root, their working directory, or from their own location. `decree init` writes `ai.sh` into the scripts directory of each built-in machine that asks AI (`develop`, `infra`, `qa`), infra's declared environment into `machines/infra/scripts/`, and qa's settings, invariants and wrenches into `machines/qa/scripts/`; a test keeps every copy of `ai.sh` identical, as for the shared scripts. Since a machine may now keep its own `requirements` beside its scripts, `infra`'s `run.sh` treats every `.decree/machines/*/scripts/requirements` as one list, `infra`'s own first, then the others in name order, and names the file of each line it reports; `declare` edits only `infra`'s. What a machine keeps between runs still goes in `$DECREE_STATE_DIR`. A project that wants a folder of shared code may keep one under any name; decree neither knows nor cares.

**Consequences.** A machine and everything it reads move together, which is what a plugin needs, and no two machines write the same path. `ai.sh` is three identical files in a new project; a project that changes one changes all of them, or points its scripts at one. A project that used `$DECREE_LIB` changes those paths, with no shim: the variable is gone, and `DECREE_LIB` in `.decree/.env` is a reserved `DECREE_*` key like any other. A machine whose scripts are symlinks into another's (docs/escalation.md's `gaps`) sources by path from the project root, which a symlink does not change. Evidence: the user's request (migration A08).

## D78: A machine is shared as one plugin file

**Context.** Sharing a machine meant copying `machines/<name>.yml` and every file its scripts need: all of `scripts/<name>/`, plus whichever flat `scripts/` files its states run. The sibling project existential built sharing on top of decree in shell with yq (`src/lib/plugin.sh`, `automation/lib/automations/plugin.sh`): a plugin is one markdown file whose frontmatter holds a machine and its files; an install writes them into `.decree/`, an export writes an edited installed machine back, and only the plugin file is committed. Every project that wanted that had to rebuild it. Prior art for the name and the shape: existential's plugins; Claude Code plugins, one bundle installed into the host's folders; and Home Assistant blueprints, one shareable automation file that a person imports.

**Decision.** decree owns the format ([plugins.md](reference/plugins.md)). `.decree/plugins/<name>.md` holds `name`, `machine` (without `name`), `scripts` (each file of `scripts/<name>/` by its path there) and `needs`, then a body for people; `schema/v1/plugin.schema.json` describes it. `process`, `daemon`, `check` and `graph` install every plugin that is new or changed before they read machines, writing only `machines/<name>.yml` and `scripts/<name>/`, so two plugins never write the same file; a deleted plugin's copy is removed. decree records each install as a copy of the plugin file under the gitignored `.decree/cache/plugins/`, and never overwrites an installed copy edited in place: an edit keeps running, and a plugin that changed over an edit is a conflict (`decree check` P3) with two ways out, `decree plugin export <name>` (keep the edit) or `decree plugin install <name>` (take the plugin's). `decree plugin export` writes the plugin from the installed copy, taking in the flat scripts the machine runs, deterministically, so installing and exporting gives the same bytes; `decree plugin import <file|->` checks a plugin, refuses missing `needs` or a taken name without `--force`, prints what it runs and installs it. Kept from existential: one file per plugin, `needs`, install as written with no model asked, export from the installed copy, and never overwriting an edit.

Left out, and why: existential's flows, `project:` tags, `endpoints:`, `handlers:` and `when:` belong to its own runtime, not to decree's machines; `cron:`, `store:` and `migrations:`, since a project's schedule, data and messages stay its own; and a shared folder every plugin writes into, which decree has had none of since D77, since such paths could only conflict. decree fetches nothing and runs no git command: `curl -fsSL <url> | decree plugin import -` imports from a URL, and git merges a conflicting plugin file.

**Consequences.** A machine is shared as one file, and a project can commit its machines as plugins only. Machines installed from a plugin behave exactly as hand-written ones. A plugin's flat scripts become copies in `scripts/<name>/`, where they already resolve first; the flat files stay, since decree never touches them. A project without `plugins/` works as before; one with `plugins/` gets a warning for each machine no plugin installed. `init`, the built-in machines and the examples move onto plugins in A10. Evidence: the user's request (migration A09).

## D79: Official plugins are built in and opt-in

**Context.** `decree init` wrote `develop`, `infra`, `qa` and `router` into every project as loose files in `machines/` and `scripts/`, needed or not, with the `--ai` backend baked into the router's script, `ai.sh`'s default and infra's `requirements`. The newsletter, ComfyUI and route-by-complexity machines could only be had by copying files out of the repository. A09 made a plugin file the way to keep and share a machine. The user wanted decree's own machines to be plugins too, with no network access and no version skew, none installed unasked, and a project committing `plugins/` and nothing installed from it, as existential's `.decree/.gitignore` already does. Prior art for the verbs: npm and cargo (`add` takes a published package into the manifest, `install` writes what the manifest names, `import` takes a file); for building the defaults in: `rustup`'s components and Helm's bundled starters ship with the tool that uses them.

**Decision.** The repository's `plugins/<name>.md`, one per machine, are the official plugins, compiled into decree with `include_str!`: `develop`, `infra`, `qa`, `router`, `newsletter`, `comfy`, `develop_by_size`, `gliner_router` and `llm_router`. `init` installs none and lists them; `decree plugin list` lists them, marked `added` and `differs`; `decree plugin add <name>...` copies them, and every official plugin they need, into `plugins/` and installs them, keeping one already there unless `--force`, which prints the lines it drops. No file names a backend: `ai.sh` and the router's `ask.sh` pick the run's `ai_cli` data, else `AI_CLI`, else the first of `claude`, `opencode` and `copilot` on `PATH`; `init --ai` still picks the skill and writes `AI_CLI` into `.env.example`. `init`'s `.gitignore` adds `machines/` and `scripts/`. A project's own edits to a plugin (`gate.sh`, `requirements`, infra's kinds, qa's invariants, wrenches and `QA_RUN`) live in its plugin file, not in a separate configuration folder: the project edits the installed copy and exports it, and `commit` runs `decree plugin export` (every plugin whose installed copy differs) before it commits, so what a run changes is committed with the run; a failed run exports nothing, and `keep` holds the queue on its edits. `examples/` keeps only what is not a plugin: the observability config, the GLiNER server, demo messages and the project walkthrough.

**Consequences.** A new project has only the machines it asked for, and a fresh clone has only `plugins/`. A decree upgrade can change an official plugin; `plugin list` shows which, and `plugin add --force` takes the new copy. Sharing a project's plugin shares its edits as well, which the user accepted. A file several plugins use is a copy in each (a test keeps them identical), since no plugin depends on another for code. Machine files installed from a plugin lose their comments, so the docs show the commented machines and tests compare them as YAML. An existing project converts by exporting each machine, adding the two `.gitignore` lines and `git rm -r --cached` of `machines/` and `scripts/`; decree never edits an existing `.gitignore`. Evidence: the user's request (migration A10).

## D80: `@reboot` fires when the daemon starts

**Context.** Some work should happen whenever the long-running process comes up: warm a model, check that services answer, catch up on what was missed while the host was down. A cron file fired only on a time schedule, so the sibling project existential worked around it with an `on-boot` flow and a `boot` machine. The user wanted a cron file to say "whenever the daemon starts". Prior art: Vixie cron (cronie and the BSDs) spells this `@reboot` in a crontab, and runs it once when the cron daemon starts, not when the kernel boots (crontab(5): "@reboot Run once, at startup").

**Decision.** A cron file whose `cron:` is `@reboot` is written to `inbox/` once each time `decree daemon` starts, before its first pass, through the same writer as every cron file (`trigger: cron`, keys copied, `cron` not), for the machines this daemon runs. It fires on every start, `--retry` included, and is queued even while the queue is held, so it runs once the hold is gone. It fires at no other time: not for a file added while the daemon runs, and never from `decree process`, which fires no cron file. decree keeps no record of past starts; "once" means once per `decree daemon` process. `decree check` accepts it as a cron expression, and `decree status --cron` shows `daemon start` in place of a next fire time, with `next: null` and `at_daemon_start: true` in `--format json`, which `--cron` gains for this. It is not spelled `daemon`, or with any new key: `decree daemon` is the cron daemon, so `@reboot` means here exactly what it means in a crontab, and anyone who knows crontab reads it without the docs; a second spelling would be one more word to learn for the same thing.

**Consequences.** A daemon a supervisor restarts after a crash queues its `@reboot` messages again each time, so a script that must not repeat its work checks its own result first, as every script should. A project that runs only `decree process` (from a system crontab, in CI) has no daemon start and never fires `@reboot`; a system crontab's own `@reboot` line can run `decree emit` for that. Evidence: the user's request (migration A11).

## D81: A reply queued before the deadline wins

**Context.** A run in a `person` state with a `timeout` can get a reply and reach its deadline at about the same time. Each `process` and `daemon` pass delivered timeouts before it read `inbox/`, so a reply queued a moment before the deadline lost whenever the pass came after it: the run took `error`, and the reply was rejected because the run was no longer waiting. Its `invalid_message` run then got an attention file with `machine: ''`, which decree's own reader rejects, and an unreadable attention file holds the queue, so one late-handled reply stopped the whole project until a person deleted the file. The A12 run (the `lease` plugin) found it: a client releasing a lease in the last second before it expires is routine. Prior art: in the AWS Step Functions callback pattern, which [D8](#d8-asking-a-person-is-choose-person-plus-a-reply-message) follows with the wait id as the task token, a `SendTaskSuccess` made before the task's `TimeoutSeconds` completes the task, even if the state machine has not processed it yet; only a token sent after the timeout fails with `TaskTimedOut`.

**Decision.** When a waiting run's `timeout_at` has passed, decree first delivers a reply to that wait (its wait id, or the run id meaning its current wait) whose id time is at or before `timeout_at`, in the order the replies were queued, until one is delivered; one that fails a check is rejected as before. Only when none is delivered does the run get the timeout. The time that decides is the reply's id, not the time decree delivers it: the id is the moment the reply reached the queue ([Frontmatter keys](reference/messages.md#frontmatter-keys)), which decree already records, while delivery time depends on when the next pass happens to run, how busy the queue is and whether a daemon was running at all; letting that decide would make the same reply win or lose by accident. A file written straight into `inbox/` counts from when decree gives it an id on arrival, since decree cannot know when it was written; a program that answers near a deadline queues its reply with `decree event`. A rejected reply's run, which has no machine of its own, gets an attention file with `holds: false` that names the machine of the run the reply was addressed to, so a person sees which machine it was about, and has no `machine` key when that run does not exist: an absent key, which `attention.schema.json` and the reader now allow, says "none" plainly, where a placeholder name like `unknown` could be a machine's real name. No new frontmatter key or event type.

**Consequences.** A reply sent in time is taken whatever the polling interval, and the result no longer depends on the order of the daemon's checks. A reply rejected for any reason is visible in `decree status` and `.decree/attention/` and never holds the queue. A tool reading attention files must allow `machine` to be absent, an additive change within `v1`. Evidence: the A12 run's reproduction (migration A11a).

## D82: The invoke that waits for a reply is `reply`

**Context.** The `person` invoke pauses a run until a reply message picks one of the state's transitions. decree has never known who replies ([D40](#d40-q14-a-person-answers-with-a-reply-message): "decree never knows it is a question"). The `lease` plugin (migration A12) uses the same invoke for a program: a lease client releases or renews with `decree event`, and the "ask" script tells the client that it holds the lease. Nothing there is a person or a question, and a name that says `person` makes the invoke look as if only people answer, which keeps it from being used for callbacks from programs. The user wanted it named for what it does. Prior art: BPMN 2.0's receive task, a task that waits for a message from an outside participant, person or system; and the AWS Step Functions callback pattern (`.waitForTaskToken`), which [D8](#d8-asking-a-person-is-choose-person-plus-a-reply-message) already follows with the wait id as the task token.

**Decision.** `invoke: { person: { question, ask, timeout? } }` is now `invoke: { reply: { question, notify, timeout? } }`, the SCXML invoke type `decree:reply`, and a transition taken from a reply has `source: "reply"`; the `decision` event's `kind`, the graph labels and notes, the messages, the schemas and the docs follow. Behaviour is unchanged. `reply` is decree's own word for the message that answers it (`to:`, `event:`, `decree event`, [Replies](reference/messages.md#replies), "waits for a reply"), so the invoke and its answer share one name. Not `receive`: BPMN's term, but decree already uses `received` for the event that delivers a reply, and the two would blur. Not `callback`: Step Functions' pattern name, but in most codebases a callback is code that runs, and here nothing runs; the run waits. Not `external`: true of every reply, but it says nothing of what the state does. The script is `notify`, not `ask`: it tells a person, a UI or a program that a reply is wanted, and does not always ask a question. Only the invoke is renamed, not the word "person": prose that means a human stays. The old spelling is not read: a machine that says `person:`, or `ask:` inside `reply:`, fails V19 with ``person: is now reply: (and its ask: is notify:)``, as every replaced shape does. D8, D12, D40 and the other decisions that name the `person` invoke keep their text, since they record what was decided at the time; read their `person` as `reply` and their `ask` script as `notify`.

**Consequences.** One invoke serves people and programs, and the docs no longer suggest a human is on the other end. The `v1` file contract changes in a way that is not additive (`machine`, `events`), which decree allows while it is 0.x; CHANGELOG lists what to rewrite. A project upgrades by renaming two keys in each machine that uses the invoke, which `decree check` points at. The script environment keeps its names (`DECREE_WAIT_ID`, `DECREE_QUESTION`, `DECREE_CHOICES`, `DECREE_RECEIVED`), since none of them names a person. Evidence: the user's request (migration A11b).

## D83: Leases are an official plugin, not core

**Context.** Several programs may want one constrained resource at once: a GPU, one LLM server, a paid API with a budget, asked for through decree-go-rest, `decree emit` or other machines. Setting the resource up for another mode (unloading one model and loading another) is slow, so it pays to serve every request for the mode already loaded before switching, as long as nobody waits too long. existential's `gpu_lease` plugin did this for one GPU, two hard-coded modes and strict arrival order. The user wanted the general version: the owner sets each resource's rules, the holder gets it for a limited time and gives it back, and the next holder is picked to keep swaps rare. Leases in decree's core were rejected on 2026-10-15 ([D69](#d69-a-process-runs-the-machines-it-is-given): a lease would add clocks and renewal for nothing the run lock does not already give). Prior art: etcd and Kubernetes leases (grant with a time to live, keepalive, revoke; a lease past its time holds nothing); Kafka's `linger.ms` (wait briefly for more work before switching); batch scheduling with setup times (serve the current setup first, with a bound so nothing starves), whose bound here is round-robin's time slice (quantum); and existential's `gpu_lease` (the run as the lease, a wake each poll, the swap step).

**Decision.** `lease` is an official plugin (`plugins/lease.md`, [D79](#d79-official-plugins-are-built-in-and-opt-in)) built only from machines, scripts, `$DECREE_STATE_DIR`, `decree event` and `decree status`. A lease is a run of machine `lease` with params `resource`, `mode`, optional `duration` and `holder`; its run id is the lease id, and it is held exactly while the run is in `held`. `decree event <id> release` ends it, held or in line; `renew` extends a held lease by its duration only while no other lease waits, judged at the reply's id time as decree judges a timeout ([D81](#d81-a-reply-queued-before-the-deadline-wins)). The rules are `machines/lease/scripts/resources`, `<name> <max_lease> <linger> <max_wait>`, shipped as `gpu 15m 5s 30m`. The next holder: the current mode first, oldest first; a linger in the mode when none of it waits; then the oldest lease's mode is swapped in by `machines/lease/scripts/swap/<resource>.sh <from> <to>`, a step with a timeout. `max_wait` is a time slice per mode, counted from the swap that put it in: once it is used up and a lease for another mode waits, the current mode gets no more grants and does not linger. It is a slice, not a bound on each lease's wait, because a bound per lease makes a mode just swapped in give way at once to a lease that waited through the previous mode, which swaps back and forth exactly when swaps are most costly; the slice guarantees each mode a stretch of work and still bounds a waiting mode at `max_wait` + `max_lease` + one swap. The store keeps the line, the holder with its expiry, the mode and when it was swapped in, each change under `flock`, so several decree processes never grant twice, and a holder past its expiry holds nothing whatever state its run is in. A waiting or held lease looks every second through a `reply` state's timeout, so the line moves without a daemon of its own.

**Consequences.** Nothing in decree changes for projects that do not add it. Every grant, swap, hold, release, expiry, cap and refused renewal is a `lease: <what> resource=… mode=… lease=…` line in the run's log, which the observability pipeline already collects. A lease needs `decree daemon` running, since `process` stops once every lease waits, and costs a few events a second while it waits or holds. The plugin needs `bash`, `flock` and `jq`, listed in its `requirements`. Evidence: the user's request (migration A12).

**Later.** [D87](#d87-what-can-be-leased-is-the-projects-and-the-registry-says-where-to-go) moved the rules and swap scripts into `state/` and made the plugin name no kind of resource; [D88](#d88-a-wait-can-end-at-an-instant-a-script-wrote) replaced its look every second with deadlines and a wake for the lease next to go; `decree event` is `decree reply`.

## D84: `develop` variants are separate machines

**Context.** The official `develop` plugin ships a gate that runs nothing until the project fills it in, and only `infra`'s requirements, which name what decree itself needs. Every Rust, Node or React project then wrote the same gate and declared the same tools by hand. The user wanted `develop` per ecosystem, as official plugins a project adds instead of `develop`. Prior art: GitHub's starter workflows and GitLab's CI templates, one per language, each a complete pipeline a project copies and edits rather than a generic one with switches; and the CI convention of installing with the lockfile's own manager (`npm ci`, `pnpm install --frozen-lockfile`, `yarn install --frozen-lockfile` or `--immutable`) so a gate fails on a lockfile out of step.

**Decision.** `develop_rust`, `develop_node` and `develop_react` are three official plugins, each `develop`'s machine (the same states, events and transitions; its own description) under its own name, spelled with `_` because machine names match `^[a-z][a-z0-9_]*$`. Each carries `develop`'s scripts, byte for byte, except its gate, the `conventions.md` its implement, fix and verify prompts are told to follow (the one line this repository's own `develop` already adds), the paths in those prompts that name its own scripts, and its `requirements` (`cargo`; `node` and `npm`), which `infra`'s `run.sh check` reads beside every machine's scripts, so no variant edits `infra`'s. Each `needs` `infra`. A test fails when a shared script differs. Separate machines, not one `develop` with a `stack` param or a gate that guesses the ecosystem: a project with a Rust API and a React front end adds both and points each message at one, each machine's gate and conventions stay a plain file the project edits and exports, and `develop`'s behaviour, and this repository's own `develop`, do not change. The Node gate reads `package.json`'s `scripts` with a small JSON scanner in `awk`, so it needs no `node` or `jq` to decide what to run; install is part of the checks (a failed install names `fail`, as `npm ci && npm test` would), and `develop_react`'s `build` is required (without it the gate names `fail`, which `fix` can address). A gate never installs tools or runs `sudo`; a missing tool or `package.json` is a non-zero exit that names it.

**Consequences.** Four copies of `develop`'s scripts ship, kept identical by a test, so a change to `develop` is made in each. A project in another ecosystem starts from `develop` and fills in its gate, as before. A project using pnpm or yarn adds that tool's line to the variant's `requirements`. Evidence: the user's request (migration A13).

## D85: A plugin carries any of decree's files, and installs only when asked

**Context.** D78 left `cron:`, `store:` and `migrations:` out of the plugin file and had `process`, `daemon`, `check` and `graph` install every new or changed plugin before reading machines; D79 made every file a plugin uses a copy in it, "since no plugin depends on another for code". Neither part was the user's call. The sibling project existential, trying 0.6.0-rc.1, has 104 plugin files: 26 carry a schedule, 24 shared code other plugins need, 6 one-time setup, 2 seed data, and many keys only existential reads. Its `plugin.sh` (416 lines of shell) re-implemented install, update, remove, edit protection and export for them, which 0.6 already does natively but for those keys. Its containers mount `machines/` and `scripts/` read-only, so a daemon there that installed a changed plugin would fail. The user: every plugin is opt-in and nothing forces an update; a plugin is a single file that may contain any of decree's primitives; installing is a manual step, and automating it is a cron machine of its own, offered as an opt-in official plugin; coupling between plugins must be explicit. Prior art: Compose and OpenAPI ignore and keep `x-` keys, so a tool on top keeps its data in the same file; `npm install` and `cargo install` change what runs only when run; existential's own `cron:`, `migrations:` and `store:` keys and their rules.

**Decision.** A plugin's frontmatter may hold `machine` (now optional), `scripts`, `cron`, `migrations`, `store`, `needs`, and any `x-` key, which decree ignores and export keeps ([plugins.md](reference/plugins.md)). `cron` files install into `cron/<name>/`, read by the daemon, `check` and `status --cron` one folder below `cron/`; with `machines/<name>.yml` and `scripts/<name>/` they are the installed copy, edit-protected and removed with the plugin, and `decree init`'s `.gitignore` adds `cron/*/`, so the project's own flat cron files stay committed. A migration is written to `migrations/` once, when no file of its name is there and `processed.md` does not list it, and never overwritten; one the plugin drops, or a deleted plugin wrote, that never started (unchanged, not in `processed.md`, no run) is removed, and one that started is history. A store seed is written to `store/<name>/` when absent and is never overwritten or removed. A plugin without a machine is a library: another plugin names it in `needs` and sources `.decree/scripts/<name>/<file>`. Only `decree plugin install`, `add` and `import` install. `install` with no name does what the automatic install did (new and changed plugins installed, deleted ones removed, edited copies kept, conflicts named) and exits 1 on a conflict; with names it installs those over any edit. `process`, `daemon` and `check` install nothing: they print, or warn about, each plugin `install` would install or remove, and `check` still reports P1–P3. `graph` only reads. The official plugin `plugin_install` runs `decree plugin install` from a `@reboot` cron file, for a project that wants installs on each daemon start.

**Consequences.** A plugin can share a schedule, its setup and its seed data, and existential's plugin files become decree plugins whose `x-exist-*` keys decree ignores; its `plugin.sh` shrinks to choosing and copying plugin files and running `decree plugin install`. A read-only container runs what the host installed. A pull or an edit to a plugin file changes nothing that runs until someone installs it, and `check` and `process` say so; a fresh clone runs `decree plugin install` once. A library's change reaches every plugin that sources it, which is what naming it in `needs` accepts. Installed migrations land in the project's committed `migrations/` and sort among its own by name. A built-in shared library ("blessed" scripts such as the copied `ai.sh`) is left for a later decision. Evidence: existential's feedback on 0.6.0-rc.1 and the user's decisions (2026-11-20).

## D86: Machines own their folders; `order` replaces migrations

**Context.** 0.6 is already a breaking release, and its layout grouped files by kind: `machines/<name>.yml`, `scripts/<name>/`, `cron/<name>/`, `store/<name>/` and `graph/<name>.md`, with flat `scripts/` and `cron/` shared by every machine. A plugin's installed copy was spread over four folders, and installing one meant reasoning about each. Migrations ran each file once, forever, by name: a file could never be edited, a mistake took a second file, and `processed.md` was a ledger no other tool shares. `decree process` and `decree daemon` did the same work at two different "starts", so `@reboot` meant something only to the daemon. `prune` was a command though it is a policy. The user asked for files grouped by domain, for declarative "this is how things should be" over "run this once", for ordered work as an ordinary state machine run at start, for two blessed scripts that queue a message only when it changed (one whose record git tracks), for `store` to be called `state` with `*.git.txt` files committed, for `process` to become `daemon --once`, for `prune` to become a plugin `init` adds, and for no plugin manifest (automatic installs stay the opt-in `plugin_install`). Prior art: Kubernetes and Terraform reconcile declared state rather than replaying steps; Flyway's repeatable migrations run again when their checksum changes; Rails engines and Django apps keep each component's code, config and data in one folder; XDG's *state* directory; cron's `@reboot`; SCXML's `srcexpr`, a child loaded from a document.

**Decision.** Each machine owns `.decree/machines/<name>/`: `machine.yml`, `scripts/` (the only place its scripts resolve), `cron/` (whose files default `machine:` to the folder), `state/` (`$DECREE_STATE_DIR`, declared under `state_files:`), `order/` and `graph.md`; the system graph is `.decree/system.md` ([README.md](reference/README.md#file-layout)). `init`'s `.gitignore` ignores `machines/**` but each `order/`, `graph.md` and `*.git.txt` file. A plugin installs into that folder, and its `order` and `state` keys are seeds written once; uninstalling keeps `state/`, `order/` and `graph.md`. A `machine` invoke may name a message file instead of a machine, `{ machine: { message: <file> } }`, run as the child with that file's machine, params and body. Migrations, `processed.md` and the `migration` trigger and key are removed. The official `order` plugin runs every machine's `order/*.md` from a `@reboot` cron file: one at a time in file-name order, each only once `inbox/` is empty, recording `<file> <sha256>` in that machine's `state/order.git.txt`; an edited file runs again, and a failed one stops the rest until the next start ([Order files](reference/messages.md#order-files-run-in-order-at-each-start)). It also carries `emit_if_changed.sh` and `emit_if_changed_git.sh`, which other machines source. `decree process` is `decree daemon --once`: start (fire `@reboot`), work until only a person or program can move a run on, sleeping through `reply` timers that need no one, then exit. `decree prune` is the official `prune` plugin, weekly from a cron file, with `PRUNE_OLDER_THAN`. `decree skill` is the official `skill` plugin, whose files `init` writes and whose `@reboot` run copies at each start where they differ. The shared `ai.sh` is the official `ai` library, which the plugins that ask AI need. `decree init` adds and installs `ai`, `order`, `prune` and `skill`; a project drops one by deleting its file. `decree install` is the one command that installs: with no argument, every plugin in `plugins/` as its file says, the step after a clone (git ignores what is installed, and commits `plugins/`); with names, those, seeding an official plugin into `plugins/` first; with a file, or `-` for stdin, that plugin; with no argument it never reads stdin, so it is safe in scripts and loops (as `kubectl apply -f -`). An official plugin is a starting file in `plugins/`, to edit or delete before it runs. `decree list` and `decree export` replace `decree plugin list|export`, `decree reply` replaces `decree event` (it only ever answered a `reply` wait), and `decree upgrade` offers to run the install line on a `y`. This supersedes D77's flat shared `scripts/`, D78's `machines/<name>.yml` and `scripts/<name>/`, D79's "`init` adds none" and every plugin carrying its own `ai.sh`, D54's `decree skill`, and D85's `migrations` and `store` keys and `cron/<name>/`; the records about migrations (D26, D27 and those after) describe the 0.5 design.

**Consequences.** Everything about a machine is in one folder, so installing a plugin replaces that folder but its state and order files, and a library is just a machine whose scripts others source by path. Ordered work is declarative: an order file says how things should be, is safe to run again, and can be fixed in place; its record is committed with its work. A CI job and a daemon start the same way. A project from 0.5 converts by moving files (the CHANGELOG lists each step) and writing `order.git.txt` from `processed.md`. Each daemon start makes an `order` run even when nothing is pending, and a project that wants none deletes the plugin. Evidence: the user's decisions (2026-11-20).

## D87: What can be leased is the project's, and the registry says where to go

**Context.** `lease` kept its rules in `machines/lease/scripts/resources` and its swap scripts beside them, shipped with a `gpu` resource and a GPU swap script. Since [D86](#d86-machines-own-their-folders-order-replaces-migrations), `scripts/` is the plugin's: git ignores it and `decree install` replaces it, so an owner's rules lived only in `plugins/lease.md`, which `decree list` then marked `differs`, and `decree install --official lease` on an upgrade threw them away. The shipped `gpu` made a general mechanism read as a GPU tool. Any mode string was accepted, so a typo waited for a mode never swapped in. Every plugin read its own `COMFY_URL` or `OLLAMA_URL`, and nothing said which server to use or what to lease first. The user asked for a way to set what can be leased, for `lease` to name no kind of resource, and for an opt-in registry that only says where to go: ask for a service, and it says where it is and where to get the lease, without taking the lease itself. Prior art: Consul and Kubernetes services (a catalog of named services and their addresses, with health checks, looked up by name, separate from any locking), DNS SRV records (where a service is, not how to use it), and Prometheus's file-based service discovery (a plain file the owner edits).

**Decision.** A file named `*.git.*` in a machine's `state/` is committed (it was `*.git.txt`), and owner-written settings live there, seeded once by a plugin's `state:` key. `lease`'s rules are `state/resources.git.txt`, `<name> <max_lease> <linger> <max_wait> [modes]`, seeded with only comments and a commented example, and its swap scripts are `state/swap/<resource>.git.sh <from> <to>`, run with bash; none is shipped. An optional `modes` column lists the modes a resource takes; a lease for another fails at once. An optional `holders` column (default 1) lets that many leases hold a resource at once, all in its current mode: a lease in the held mode joins without a swap while there is room, nobody is swapping and the mode's `max_wait` slice has not given way to a waiting mode; a lease in another mode waits until every holder is done. It is a readers–writer lock whose "readers" are per mode (prior art: `pthread_rwlock`, and Kubernetes' `ReadWriteMany` versus `ReadWriteOnce`), so a model server that serves several requests at once is not serialized, and the cost of a swap is still paid only between modes. A lease's status is a file in the machine's state folder, `state/status/leases/<id>.json` (its state from `waiting` to `released`, `expired`, `failed` or `cancelled`, its place in line, until when it holds), and each resource's is `state/status/resources/<resource>.json` (its mode, holders and line), each rewritten whole, through a rename, under the resource's lock after every change: decree-go-rest checks on a lease by reading one file, as a Kubernetes client reads an object's `status`. The official `registry` plugin, opt-in, keeps one table, `state/services.git.txt`: `<server> <service> <url> [lease]`, where `lease` is a resource of this project's `lease` machine or `<resource>@<address>` for another decree's. Its `check`, at each daemon start and every five minutes, sends each address one GET and writes `state/health.json`: an answer below 500 is up (the server is there and serving), a 5xx or none is down, with the code and when; `registry.sh resolve <service>` prints `<server> <url> <lease>` for each place, live ones first, and `url`, `env` and `list` (`--json`) look things up; it reads no other plugin's files: what one plugin takes from another is named in its `needs`. `lease` never reads the registry, and the registry never takes a lease.

**Consequences.** Upgrading `lease` or `registry` keeps the owner's settings, and they are committed with the project; `plugins/lease.md` stays the official copy and names no kind of resource. A client makes two steps, resolve then lease, and picks among the places itself, so the registry stays a lookup and leases can live in another decree. The registry's health is one computer's view and is not committed. Plugins can move from their own `*_URL` variables to `registry.sh env` or `url` one at a time; none is changed by this decision.

## D88: A wait can end at an instant a script wrote

**Context.** A `reply` wait ended only after a fixed `timeout` from when it started. `lease`'s `held` state needed to end at its lease's expiry, which a script decides (each resource's `max_lease`, a requested `duration`, a renewal from now), so it waited with `timeout: 1s` and looked again every second: one `turn` run, a handful of events and a log line per held lease per second, all to learn nothing had changed. A client of a lease already knows when it ends; the run should too. AWS Step Functions' Wait state takes its end either as `Seconds` or as `Timestamp`/`TimestampPath`, an instant read from the state's input; SCXML's `<send>` takes `delayexpr` for the same reason; Temporal's timers and Kubernetes' `activeDeadlineSeconds` are each a deadline fixed when they start.

**Decision.** A `reply` invoke takes `timeout_at` in place of `timeout`: `<file>`, a file in the run's folder holding an RFC 3339 instant, or `<file>#<JSON Pointer>` (RFC 6901), the instant at that place in a JSON file. decree reads it when the wait starts, after `notify` ran, and records it as the `waiting` event's `timeout_at`, as it does the deadline from `timeout`; from there the two are one mechanism, so a reply queued before the deadline still wins ([D81](#d81-a-reply-queued-before-the-deadline-wins)), and `daemon --once` sleeps until it when the wait has `attention: false`. Each entry to the state reads the file again. With no instant there (no file, no string at the pointer, not RFC 3339), the event is `error` at once and the transition's `error` says why: a run that cannot know its deadline does not wait forever. The path is a plain path in the run's folder, as for `machine: { message }`. `lease`'s `held` and `waiting` wait with `timeout_at: lease.deadline`, which its scripts write: for `held` the lease's expiry, for `waiting` the next instant time alone can change its turn (a holder's expiry, the end of the linger, the end of the mode's slice) when it is the lease the rules would pick then, else a backstop of a minute and up to 15 s more. A lease that leaves the line or the holders, or is granted, queues the reply `again` for the one lease the rules would pick next (or, while the resource lingers, pick when the linger ends), written into `inbox/` so one reaching a run that is executing is delivered once it waits: a waiting lease sleeps until it may go, as a condition variable's signal wakes one waiter, not a broadcast, so each change costs one turn however long the line.

**Consequences.** A held lease costs nothing until it is released, renewed or expires, and ends at its expiry within one daemon pass; a waiting one costs a turn when it is next to go and at most one every 60 to 75 s otherwise, so it neither fills its run folder nor keeps the `order` plugin, which waits for no other run to be executing, from going on. A client reads the lease's status once and knows until when it holds the resource. A refused renewal leaves `expires`, and so the deadline. A wake that reaches a lease just granted is taken by `held`'s `again`, which changes nothing, and a lease that ends deletes any wake still queued for it, so no wake is ever a rejected reply. Only the lease the rules would pick at a time waits for that time; the others wait for a wake or a jittered backstop, so a long line never turns all at once.

## D89: Machines run at once, each saying how many of itself

**Context.** One `decree daemon` stepped one run at a time: a three-hour `develop` run, a lease's callback to an address that never answers, or a slow router held up every other machine, though they share nothing. The user asked for each request to be handled as soon as it can, with a setting per machine, 1 by default, and for machines not to block each other. Prior art: AWS Step Functions' Map state `MaxConcurrency`, GitHub Actions' `concurrency` (and its `group`, which makes workflows share one slot), Kubernetes Jobs' `parallelism`, worker pools such as Celery's `--concurrency`, and the counting semaphore.

**Decision.** The daemon dispatches; each run executes in its own thread. A machine's root `concurrency` (a whole number, default 1) is how many of its runs may execute at once, counted across every process sharing the project with `flock`ed slot files in `.decree/cache/slots/`, which a dead process frees with it. A run executes from its claim or continuation until it finishes, waits or is interrupted: a run waiting for a reply, a timer or a child holds no slot, as the user agreed. A machine at its limit leaves its messages queued, in order, and its pending runs pending; the others go on. Machines naming one `concurrency_group` share its slots, so the official machines that edit the work tree (`develop` and its variants, `qa`, `infra`) are one `worktree` group with one slot, as one process at a time used to keep them. A child run takes a slot of its own machine, waiting while its parent keeps its own; a finished child gives its slot back before its parent continues, so waits for slots run only from parent to child, and V20 refuses invoke cycles and a child in its parent's group: no deadlock. A reply to a run executing now waits until the run stops, so replies to one run keep their order. Output of runs executing at once is prefixed with the end of each run's id.

**Consequences.** A slow machine no longer delays the others, and a lease's callback or a router call no longer stalls the daemon. Inbox order now holds within a machine, not across machines: a message for another machine can start, and finish, before an older one. `decree stop` holds new runs, but the runs executing when it is written finish their step. The `order` plugin's next file now also waits for no other run to be executing or pending, so "everything before it has been processed" still holds. `lease` puts each lease in line by when its message was queued, not when its first turn ran, since leases asked together now start together. `lease` allows 16 runs at once and the routers 4, since their runs are short and every machine's decisions go through them.

## D90: `decree install` writes the schemas and ends an upgrade

**Context.** [D55](#d55-hosted-schemas-found-by-path) made `.decree/schema/` an optional local copy that only `decree schema` writes, so an agent had to run it before reading a schema, and an upgrade's after-steps were a list: `decree install --official skill`, `decree schema` if the folder existed, `decree list`. Since [D86](#d86-machines-own-their-folders-order-replaces-migrations) `decree install` is already the one step after a clone or a pull, and a project's owner asked for it to be the step after an upgrade too, with the upgrade prompting for it.

**Decision.** `decree init` and every `decree install` that succeeds write `.decree/schema/` as `decree schema` does, quietly, since it is generated like a graph; it stays ignored by git. `decree upgrade`'s after-steps are `decree install` in each project (always), `decree list` and `decree install --official <name>`. After running the install line, in a project, it asks whether to run `decree install` in that project now (`[y/N]`) and runs `decree` from `PATH`, the new copy, there (`--yes`: without asking), then says to run it in each other project. `decree schema` stays, for writing the copy alone.

**Consequences.** A project's schemas are those of the decree that last installed into it, so after a clone or an upgrade an agent finds them without a step of its own, and the stale-schema warning of `decree check` goes away with the same `decree install` that finishes the upgrade. The new skill still takes `decree install --official skill`, since an official plugin's file in `plugins/` is the project's.

## D91: `decree retry` is a command of its own

**Context.** [D53](#d53-decree-process---retry-continues-a-run) made continuing a run a flag on the command a person ran anyway, `decree process --retry`, since `process` ran once and exited. Since [D86](#d86-machines-own-their-folders-order-replaces-migrations) and [D89](#d89-machines-run-at-once-each-saying-how-many-of-itself) the daemon is long-running and runs machines at once, so `--retry`, which acted only at a start, meant stopping the daemon to continue one run, or starting a second `daemon --once --retry` beside it. D53 came from a migration run, not from the project's owner, who asked for commands that are what one would expect. Prior art: Sidekiq's and Celery's retry and GitHub Actions' "Re-run" put a job back for the workers already running; `decree reply` already queues an answer for whichever daemon runs the run.

**Decision.** `decree retry <id> [--state <s>] [--format <text|json>]` makes an `interrupted` or finished run `pending`, under its run lock, with the same `retry` transition, default state, `--state` rules, run attempt and release of its `hold` and attention file as before, and prints where it continues. It runs nothing: a daemon that runs the run's machine continues it at its next pass, without a restart, and otherwise the next `decree daemon --once` does. `daemon --retry` and `--state` are removed. Every message that says how to continue a run names `decree retry <id>`; `--format json` prints `{ "id", "state" }` (`cli/retry.schema.json`).

**Consequences.** One way to continue a run, whether a daemon runs or not, and no restart. A person who uses `daemon --once` runs two commands, `decree retry <id>` then `decree daemon --once`, which `retry` says. A filtered process never refuses a retry: the run waits `pending` for a process that runs its machine.

## D92: `decree cancel` ends a run

**Context.** Nothing could end a run nobody would continue. A `waiting` run stayed waiting until a reply nobody would send, an `interrupted` one stayed listed until `prune` took its folder, and deleting an attention file only hid a run. Every job system has a cancel: GitHub Actions' "Cancel workflow", Temporal's workflow cancellation, Sidekiq's and Celery's revoke. The project's owner asked for the commands one would expect.

**Decision.** `decree cancel <id> [-m <note>] [--format <text|json>]` ends a `waiting`, `pending` or `interrupted` run, and every unfinished child run below it, in `failed`, under all their locks, deepest first: a `transition` with `event: cancel` and `source: cancel` (the note as `note`), then `run_finished` with `cancelled: true`. It runs no script, `onexit` included, as on a signal, since a script left to run could fail or hang, and a slot or a hold would then decide when a cancel takes effect. It deletes each run's `hold`, attention file and the replies still queued for it. A run's `failed` is kept, since every machine has that final state and a run that was cancelled did not reach its goal; `decree status` counts cancelled runs apart, as `cancelled`, and lists none. A parent waiting for a cancelled child takes `error`, as for a child that failed. An `active` or finished run is refused.

**Consequences.** A person can always end a run, and see that they did: the event names `cancel` and its note. A cancelled run is finished, so `decree retry` continues it, and a cancel is undone the same way a failure is. A plugin whose runs hold something outside decree (the `lease` plugin) must treat a finished run as gone, which `lease` already does for a crashed or interrupted holder; until its next check, its status file still shows the lease.

## D93: `decree pause` and `decree resume`

**Context.** [D68](#d68-a-graceful-stop-is-an-attention-file) named the graceful hold `decree stop`, though it stops nothing: the daemon keeps running and starts no run while `manual-stop.md` exists, and resuming meant knowing to delete that file. `stop` reads as "the process exits". The project's owner asked for commands that are what one would expect. Prior art: `docker pause` and `docker unpause`, which keep the container and freeze its work; Sidekiq's quiet; `kubectl rollout pause` and `resume`.

**Decision.** `decree pause [-m <note>]` writes `.decree/attention/pause.md` (`kind: pause`, was `manual-stop`), with the same rules as before: the runs going now finish their step, no run starts or continues, a second pause keeps the first `since`. `decree resume` deletes it, refusing a `pause.md` that `decree pause` did not write, and names any other file that still holds the queue. Both take `--format json` (`cli/pause.schema.json`, was `cli/stop.schema.json`). `decree stop` is gone. The file stays the mechanism, so a pause reaches every daemon of the project and deleting the file still resumes.

**Consequences.** The pair reads as what it does, and nobody needs the file's name to go on. Ctrl-C keeps its meaning: interrupt now, and the daemon exits.

## D94: No `decree schema`, no `daemon --once --dry-run`

**Context.** Since [D90](#d90-decree-install-writes-the-schemas-and-ends-an-upgrade), `decree init` and every `decree install` write `.decree/schema/`, so `decree schema` only did again what the step after a clone, a pull or an upgrade already does. `decree daemon --once --dry-run` listed the queued inbox messages and checked them, which `decree status` (the queued messages) and `decree check` (M2 for each one) already do. The project's owner asked for fewer commands, each one expected.

**Decision.** `decree schema` and `daemon --once --dry-run` (with `daemon --once --format`) are removed, with `cli/schema.schema.json` and `cli/daemon.schema.json`. `decree check` says `run `decree install`` for a stale local schema copy. `daemon` takes no `--format`: it produces a stream.

**Consequences.** One command writes the schemas, the one a project runs anyway. A script that read `daemon --once --dry-run --format json` reads `decree status --format json` (`queued.inbox`) and `decree check --format json` instead.

## D95: A run's hold holds its group

**Context.** [D65](#d65-a-failed-run-keeps-its-changes-and-holds-the-queue) had a failed run that left changes in the work tree hold the whole queue, and [D67](#d67-the-attention-folder-says-what-needs-a-person) made any holding attention file stop every run. Since [D89](#d89-machines-run-at-once-each-saying-how-many-of-itself) machines run at once, and those that share a resource say so with a `concurrency_group`: the official `develop` and its variants, `infra` and `qa` share `worktree`, the one tree `keep` protects. A `develop` run's leftover changes then stopped `lease`, `registry`, `prune` and every other machine that never touches the tree. The project's owner asked whether a hold should stop every run or only its own machine's. The `order` plugin needs none: a failed order file stops the files after it through its own record, not through an attention file.

**Decision.** A run's attention file with `holds: true` holds the runs that share its machine's slots: its `concurrency_group`, or the machine alone, the same slot key that already says which runs may not execute together. Those runs neither start nor continue (inbox messages stay queued in order; no `pending` run, reply or timeout is taken), and a child run of a held machine does not start, so its parent takes `error`. Every other machine goes on. A run's file whose machine is not loaded, `decree pause`'s file and a file decree cannot read still hold every run. `daemon --once` runs what it can, prints each holding file with what it holds and exits 1; `daemon` prints it once; `decree status` says `holds group `worktree``.

**Consequences.** A failed `develop` run no longer stops leases, service checks or pruning, and still keeps every machine that edits the tree off its changes. Machines that share a resource must say so with a group, as concurrency already asks. A parent outside the group, such as the `order` run, whose child would edit a held tree, fails that order file, and the next start runs it again.

## D96: An install always installs, and archives what it would lose

**Context.** [D85](#d85-a-plugin-carries-any-of-decrees-files-and-installs-only-when-asked) made `decree install` keep an installed copy edited in place: a plugin unchanged over an edit left the edit running, and a plugin changed over one was a conflict (P3) that `install` and `check` failed on until a person exported or forced it; `decree install <file>` refused a taken name and `decree install <name>` a machine written by hand, both without `--force`. The project's owner: an install should not get blocked by changes; it should move the existing machine code into an archive, in case the user wants to recover it, and always install, whether or not an existing install matches, as `npm install` does. Prior art: `npm install` and `pip install --official-reinstall` reinstall what is asked regardless of what is there; dpkg keeps a changed conffile as `.dpkg-old` rather than lose it; the owner asked that the archive be the plugin's export form, one file with the machine's cron files; pytest, ruff and mypy put a `.gitignore` of `*` in the folders they write, so a project whose own `.gitignore` predates them never commits them.

**Decision.** `decree install` never refuses over a change. With no argument it installs every plugin in `plugins/`, matching or not, and removes the copy of each deleted one; with names or a file it installs those, replacing a plugin file of the same name. Before it writes over or removes an installed copy that is not what its record says decree installed (edited in place, by a person or a run, or written by hand), it exports that copy as one plugin file, as `decree export` would (machine, scripts and cron files, with the current plugin file's body, `needs`, seeds and `x-` keys), to `.decree/archive/<name>/<UTC time>.md`, the time to the millisecond so the files sort by time; a plugin file it replaces with different bytes is archived the same way, as it was (`<time>.replaced.md` beside an archived copy it does not equal). The archive is then in the form decree shares a machine in: `decree install <that file>` restores it. Only a copy that cannot be a plugin file (a `machine.yml` that is not a YAML mapping, a script that is not text) is moved as it is into a folder, `<time>/`; a machine that is YAML but fails its checks is still exported. It prints each file, and its JSON gives it (`archived`). An unedited copy is not archived: its recorded plugin file installs it again. `.decree/archive/` holds a `.gitignore` of `*`, and decree never deletes it. P3 is gone; `check`, `daemon` and `decree list` (`edited`) say which copies the next install would archive. `--force` is renamed `--official`, after its one remaining meaning: take this decree's built-in copy of each named plugin, in place of the project's file (a name decree does not ship is refused). Nothing is forced any more, and the project's file stays the default, since a project keeps its settings for a plugin there. Only a plugin file that fails its schema, or a missing need, still stops an install. This supersedes D85's edit protection and the `conflict` state.

**Consequences.** A pull and an install, or a daemon restart with `plugin_install`, always runs the plugins as committed. An edit in place that was not exported is no longer kept running: it is in the archive, one `decree install <file>` from running again. That includes the edits a failed `develop` or `infra` run left in an installed copy for `decree retry`, which an install before the retry moves to the archive. `decree export` with no name still leaves a conflict (an edit whose plugin file changed since its install) unexported, since exporting would write the old version over the new file. The archive grows with each archived install until someone deletes it.

## D97: Cron files are installed once; `--official` alone updates the official plugins a project has

**Context.** [D96](#d96-an-install-always-installs-and-archives-what-it-would-lose) made every install rewrite a plugin's whole installed copy, its cron files with it, so a schedule a project changed in place, or a cron file it deleted to turn a job off, came back at the next install (each daemon start, with `plugin_install`), archived but no longer running. The project's owner: when a plugin is already installed, an install should not reinstall its crons unless asked; and `decree install --official` with no name should update the official plugins the project already has, not add the ones it does not. Prior art: dpkg installs a package's conffiles once and keeps the administrator's changes on upgrade; `npm update` updates only what a project already depends on.

**Decision.** A plugin's cron files are installed with it when decree has no record of installing it (a new plugin, a fresh clone), and after that are the project's: an install leaves `cron/<name>/` as it is, edited, emptied or not, even when the plugin's cron files change. `decree install --cron` (with no argument, names or a file) installs them again, archiving them first when they are not what was installed, as any edit. `check` and `daemon` warn while a plugin's installed cron files are not its file's, naming `decree export <name>` (keep them) and `decree install --cron <name>` (take the plugin's); they no longer count as an edit that an install would archive. Removing a plugin still removes its cron files, archiving them when edited. `decree install --official` with no name replaces the file of each official plugin already in `plugins/` that is not this decree's copy, archiving the old one, then installs every plugin; it adds no plugin, not even an official one a new copy `needs`, which `check` reports (P2) and `decree install <name>` adds.

**Consequences.** A project tunes or turns off a plugin's schedules in place and they stay; sharing that choice still takes `decree export`. A plugin update that adds or changes a cron file reaches an installed project only with `--cron`, which `check` points to. After a decree upgrade, `decree install --official` takes every official plugin the project has in one step.

## D98: No plugin installs on daemon start; the start command does

**Context.** [D85](#d85-a-plugin-carries-any-of-decrees-files-and-installs-only-when-asked) offered automatic installs as an opt-in official plugin, `plugin_install`, whose `@reboot` cron file ran `decree install` at each daemon start. Since [D96](#d96-an-install-always-installs-and-archives-what-it-would-lose) an install archives every edit in place, so with it each restart quietly archived the edits a failed run had left for `decree retry`. The project's owner would not expect a daemon to install, and preferred `decree install && decree daemon` where installing at start is wanted.

**Decision.** The `plugin_install` plugin is removed. decree installs only when `decree install` (or `init`) runs; `daemon` and `check` only report what an install would change. The docs and the skill recommend `decree install && decree daemon` for a deploy, a container or a service unit, and a git `post-merge` hook running `decree install` for a working copy. A project that has `plugins/plugin_install.md` keeps it as its own plugin (`decree list` marks it `own`) and may delete it.

**Consequences.** Installing is always a visible step in whatever starts decree, not a run hidden among the daemon's. Nothing official installs on a timer.


## D99: Official plugins are `decree_*` and never edited; a project extends one

**Context.** A project customized an official plugin in one of two places, both wrong for code. It edited the plugin's file in `plugins/` (a `gate.sh`, infra's `requirements`), which `decree list` marked `differs` and `decree install --official` replaced whole on an upgrade, the edit surviving only as lines on screen and a file in the archive; or it kept code in `state/` under a `*.git.*` name ([D87](#d87-what-can-be-leased-is-the-projects-and-the-registry-says-where-to-go): lease's rules and its swap scripts, which lease ran with bash), the one folder of a machine its runs and anything else that writes the project's data are expected to write. The sibling project existential mounts `plugins/` and `machines/` read-only in its containers and links each machine's `state/` into the user's workspace, so a swap script there let anything that writes the workspace run code in the automation container, past the only path code takes into that stack: a person reading a plugin file and accepting it. Whether a plugin was official was guessed from its name, so a project with its own `develop` had it replaced by an upgrade, and forked `develop`, `infra` and `qa` under other names to keep its own; decree did the same inside itself, with `develop_rust`, `develop_node` and `develop_react` three copies of `develop`'s scripts kept identical by a test ([D84](#d84-develop-variants-are-separate-machines)). `needs` let one plugin use another, always by its fixed folder name, but gave a project no way to change one and keep the change. The user wanted it plain which code is decree's and which the project's, and what runs (migration A14).

Prior art: reserved prefixes for a platform's own names (Kubernetes' `kubernetes.io/` and `k8s.io/` labels, `x-` against registered names, Python's `_` and dunder names, systemd's units under `/usr/lib/systemd/system/` against the administrator's under `/etc/systemd/system/`); read-only vendor files (`/usr` owned by the package manager, the administrator's changes in `/etc`, Debian's conffiles and `conf.d/`, systemd's drop-ins `<unit>.d/override.conf`); a file that names its base and holds only what it adds or replaces (Docker's `FROM`, Compose's `extends`, Kustomize overlays), the base never edited; a project recording where each dependency came from and pinning what it accepted, a change refused until a person takes it (Go's vendor directory and `go.sum`, npm's `package-lock.json` with `resolved` and `integrity`, Cargo.lock's `source` and checksums, pip's `--require-hashes`), decree's committed plugin file being that pin, and readable; HTTPS for transport, a pinned copy against a domain that changes hands and review against a publisher that ships something bad, signatures (apt, Sigstore) proving who published, not what is safe, and left out; and the Filesystem Hierarchy Standard's split, `/var` for variable data and `/usr` for programs, which a system may mount read-only, as systemd's `StateDirectory=` and the common `noexec` mount of data volumes follow.

**Decision.**

- **Official is the prefix.** Every official plugin's name starts with `decree_` (`decree_ai`, `decree_develop`, `decree_lease`, …), and only an official plugin's may: a plugin file whose `name` has the prefix but names no plugin this decree ships fails P1, listing the official ones. `decree list` marks a `decree_*` plugin `official` and every other `own`, whatever decree ships; `decree install lease` with no `plugins/lease.md` exits 1. 0.6 is unreleased: no alias from the old names.
- **An official plugin is never modified in a project.** `decree install` writes each official plugin's file and installed copy from this decree every time, archiving either when it is not this decree's copy and printing the lines that change, so after an upgrade it takes the new version of every official plugin the project has and adds none. `decree check` fails with P3 while one is not this decree's copy; `decree export` refuses one. Cron files, `state/` and `order/` are the project's and not covered. `decree install --official` is removed. Official scripts that a run would edit say to extend instead: `decree_develop`'s gate runs nothing, `decree_infra`'s `declare` refuses to run as itself, `decree_qa` reads `QA_RUN` from the machine running it.
- **`extends`.** A plugin may name another in `plugins/` as its base and hold only what it adds or replaces. It installs path by path on the base's files (a file replaces or adds, `null` removes, `machine` replaces whole, `needs` adds), under its own name, never the base's (P1), with the base installed in full beside it, so every plugin a project runs is in `plugins/` in full and installed in full under `machines/<name>/`. The base is a need (P2 when missing, seeded when official). A loop or a library base is P1. While an overlay is installed its base is installed without its cron files, which the overlay carries, so a schedule runs once; removing the overlay gives them back. A base that changes reinstalls every plugin on it. Export of an overlay writes only what differs from what its base installs, so installing then exporting gives the same bytes. No rule lets an overlay change part of a `machine`: a `machine` replaces the base's whole.
- **Meeting a need with another plugin.** A `needs` entry may be `{<need>: <plugin>}`. Install rewrites the names it covers in the installed machine (a `machine:` invoke, a `router:`, an `emits` list), which do not count as an edit, and every script gets `DECREE_NEED_<NEED>`, the plugin that meets each need. Official scripts find their own files through `DECREE_MACHINE` and reach another plugin only through `DECREE_NEED_*` (falling back to the need's own name for a machine no plugin file installs), which tests enforce, so they work in a plugin that extends them.
- **`source` and `decree install --update`.** A plugin may say where it is published, an `https://` URL and nothing else. `--update` fetches it with the system `curl` (HTTPS only, redirects only to HTTPS on the same host, a timeout; `DECREE_CURL` for tests), refuses a copy that fails the schema or names another `name` or `source`, prints the whole diff and writes it only after `y` on a terminal, archiving the old file; without a terminal it writes nothing. It is the only network call decree makes, and never runs from the daemon or a cron file.
- **`state/` holds data, never code.** Nothing in a machine's `state/` is run, sourced or loaded as code. `decree_lease`'s rules are `scripts/resources` and its swaps `scripts/swap/<resource>.sh`, in the project's own plugin that extends it, which leases go to; a lease on `decree_lease` itself fails. `decree check` warns about an executable or `#!` file in `state/`, about a script line that runs or sources a path there (a heuristic over the text), and about rc.1 and rc.2's `machines/lease/state/resources.git.txt` and `state/swap/`, quoting a `local_lease` plugin file that holds them. `decree_registry`'s `services.git.txt` is data and stays.
- **The develop variants extend `decree_develop`.** Each holds only its gate, `conventions.md` and `requirements`, and takes `decree_develop`'s machine whole, description included; `decree_develop`'s prompts follow a `conventions.md` when the machine has one. `decree_develop_by_size` differs in its machine and stays a plugin of its own. `decree_skill` writes to each folder `scripts/dirs` lists, so a project whose AI CLI reads skills elsewhere extends it.
- This repository's own `develop`, `infra` and `qa` are plugins that extend `decree_develop`, `decree_infra` and `decree_qa` with its edits (`develop` maps `decree_infra` to `infra`, `qa` maps `decree_develop` to `develop`), so `machines/develop/` keeps its name, its order files and `run-queue.sh`.

This supersedes [D87](#d87-what-can-be-leased-is-the-projects-and-the-registry-says-where-to-go)'s owner-written settings and swap scripts in `state/` (data stays there), [D84](#d84-develop-variants-are-separate-machines)'s copies of `develop`'s scripts in each variant, [D97](#d97-cron-files-are-installed-once---official-alone-updates-the-official-plugins-a-project-has)'s `--official` (its cron rule stands), and the guidance to edit an official plugin's file or installed copy and keep the edit with `decree export` in [D77](#d77-a-machines-files-live-with-its-scripts) (`declare` editing `infra`'s requirements), [D79](#d79-official-plugins-are-built-in-and-opt-in) (a project's edits to an official plugin in its file, `--force` to take a new copy), [D84](#d84-develop-variants-are-separate-machines) (a variant's `requirements` edited for pnpm or yarn), [D86](#d86-machines-own-their-folders-order-replaces-migrations) ("an official plugin is a starting file in `plugins/`, to edit or delete before it runs"; it may still be deleted) and [D96](#d96-an-install-always-installs-and-archives-what-it-would-lose) (an official plugin's edit kept by export).

**Consequences.** Which code is decree's is in a file's name, and an official plugin's file and installed copy are always this decree's, so `machines/` can be read-only and an upgrade is one `decree install`, every overlay reinstalled on its new base. A project changes an official plugin by writing a small plugin of its own, which an upgrade never touches, and can run its own `develop` beside `decree_develop`. Four copies of `develop`'s scripts no longer ship, and the test that kept them identical is gone. Code reaches a project only through plugin files a person reads: a URL's update is a diff a person accepts. An official script runs outside decree only with the `DECREE_NEED_*` variables decree sets, or their fallbacks. The `state/` rule is a convention decree states everywhere and warns about where it can see a breach; it is not enforced, since a script can always run what it reads. A plugin that relied on an official plugin's machine folder by name (`.decree/machines/ai/scripts/ai.sh`) is renamed with it; existential is not changed by this decision. Evidence: the user's request (migration A14).
