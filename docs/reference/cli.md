# CLI

decree has 16 commands, plus `--version` (`-v`). `decree` with no command prints a synopsis of the [quick start](../../README.md#quick-start) (`src/templates/synopsis.md`) and exits 0, inside a project or not; it reads, writes and runs nothing, and `decree daemon --once` runs the queue ([D76](../decisions.md#d76-bare-decree-prints-a-synopsis)). Every command takes `--no-color`; without it, colour follows `NO_COLOR` and whether the output is a terminal. Every command that reports something takes `--format <text|json>`, and `decree check` also `--format sarif` ([Machine-readable output](#machine-readable-output)).

Every command except `init`, `upgrade` and `help` works on the project whose `.decree/` is in the current directory or the nearest ancestor. Without one it fails with ``not inside a decree project (run `decree init` first)``. Errors are printed to stderr as `error: <message>`.

### Output

Unless `--quiet`, `daemon` prints each run as it goes, on stdout, as `decree tail` would: `▶ <id> · <machine>` as a run starts or continues, then its script output behind the same per-script headers, then one line as it stops: `✓ <id> <final state> in <time>`, `✗ <id> failed in <time>`, `⏸ <id> waiting in <state> after <time>`, or `■ <id> interrupted in <state> after <time>` (`45s`, `3m 12s`, `1h 02m`). On a terminal a status line stays below the output, `▶ <id> · <machine> · <state> · <elapsed> · <n>/<total>`: the innermost run's machine and state (a child run's, while the run waits for it), how long the run has gone on, and that it is the `n`th run this command has started, of `n` plus the inbox messages still queued. While several runs execute at once, each gets its `▶` header and its stop line as before, and every line of its output is behind `[<the last six characters of its id>] `, from the first time it prints beside another run to its end; the status line becomes `▶ <n> running · <machine> <state> <elapsed> · …`, one entry per run. Off a terminal (a pipe, a file, cron) there is no status line. Notices (a failed run's `decree retry` command, a plugin not installed) go to stderr, after the output of the run they are about. `--quiet` prints only those notices and the closing summary, as cron and CI want. Everything but the status line also goes to `.decree/process.log`, with `--quiet` too, so there is no need to `tee` the output: the run headers, the script output, the line each run stops with, and the notices. decree trims it to its last 2 MiB, behind a `[log truncated …]` line, as each run stops; `.decree/.gitignore` lists it.

Usage errors (an unknown command or flag, a missing argument, `--format` where it does not apply) exit 2.

Error formats:

- `daemon` validates every machine (V1–V21) before anything runs. If any fails, it prints each error as `decree check` does, then ``N machine error(s); nothing was processed. Run `decree check`.``, and exits 1. It then reads `.decree/.env` and every machine's `env_file` (E1): a malformed line is printed the same way, followed by ``N error(s) in .decree/.env; nothing was processed. Run `decree check`.`` (naming each file with an error), and it exits 1. Once running, it reads the machines and `.env` files again before each run ([Edits while running](#edits-while-running)).
- A waiting run is printed as:

  ```text
  Waiting: run <run id> in `<state>`: <the state's description, else its id>
    wait id <wait id>, options: <option>, <option>
    decree reply <wait id> <option>
  ```

  with one `decree reply` line per option.

## `--once` or not

`decree daemon` and `decree daemon --once` run the same pipeline, and each is a daemon start: it fires the `@reboot` cron files, so the [`order`](plugins.md#official-plugins) plugin runs each machine's order files. They differ in when they stop.

- `decree daemon --once` runs everything it can, waits through timers (a `reply` wait with `attention: false` and a `timeout` or `timeout_at`), then prints each run that waits for a person or a program and exits. Such a run stays `waiting` until a later start after its reply or deadline. It fires no scheduled cron file. Use it by hand, in CI, or from a scheduler that runs it again (`decree daemon --once --quiet` in a crontab).
- `decree daemon` keeps polling until stopped. It fires scheduled cron files, delivers each reply and `timeout` as it comes, and continues the run. For unattended work, anything with scheduled cron files, `reply` states or long `timeout`s, run it under a supervisor (a systemd service, a tmux session, a container) with `--quiet` if its output goes to a log.

Neither continues a `failed` or `interrupted` run by itself: `decree retry` makes it `pending`, and either continues it then ([Retry](#retry)).

### Several processes

Several `daemon` commands can share one project folder, each running its own machines, as Celery's `--queues` and `--exclude-queues` give each worker its queues ([D69](../decisions.md#d69-a-process-runs-the-machines-it-is-given)):

| Flag or variable | Effect |
| --- | --- |
| `--machine <m>` | Run only these machines. Repeatable; each value is a comma-separated list (`--machine develop,qa`). |
| `--exclude-machine <m>` | Run every machine but these. Repeatable, comma-separated. Not with `--machine` (exit 2). |
| `DECREE_MACHINES` | As `--machine`, comma-separated, from the shell or `.decree/.env`. |
| `DECREE_EXCLUDE_MACHINES` | As `--exclude-machine`. Not with `DECREE_MACHINES` from the same place (exit 2). |

A flag beats both variables, and the shell beats `.decree/.env`; an empty variable is unset. With `DECREE_MAX_DEPTH` ([Environment](#environment)) these are the only `DECREE_*` keys `.decree/.env` may set (E1 rejects every other, and a machine's `env_file` may set none); decree reads them itself and never passes them to scripts. A name that is not a machine in `.decree/machines/` or a built-in is an error naming it, exit 1.

- **What a filtered process does.** It delivers replies and timeouts, continues `pending` runs, claims inbox messages and fires cron files only for its machines; everything else stays where it is, untouched. A run belongs to the machine of its root run: the process that runs a parent steps its child runs, whatever their machine. A run `decree retry` made `pending` is continued only by a process that runs its machine.
- **What keeps processes apart.** An inbox claim is an atomic rename and a run has its [run lock](messages.md#run-lock), so two processes never take the same message or step the same run.
- **`.decree/.env` applies to every process in the folder.** Give different filters by flag or shell: `decree daemon --machine comfy` in one terminal, `decree daemon --exclude-machine comfy` in another.
- **The work tree is shared.** The official `develop` (and its variants), `infra` and `qa` share it through `clean_tree` and `commit`, so they are in one `concurrency_group`, `worktree`, with one slot: one of them runs at a time in a checkout, across every process sharing it ([Concurrency](machines.md#concurrency)). To run them side by side, give each process its own git worktree, with its own `.decree/`.
- **A hold holds everyone.** An attention file with `holds: true` ([Attention](#attention)) holds every process, whatever its filter.

### Environment

The variables decree reads itself, from its own environment (the shell) or `.decree/.env`; the shell beats `.decree/.env`, and an empty variable is unset. They are its only settings: there is no configuration file ([No configuration file](README.md#no-configuration-file)). Prior art: `GIT_*` and `TF_*` variables.

| Variable | Effect |
| --- | --- |
| `DECREE_MACHINES` | The machines `daemon` runs ([Several processes](#several-processes)). |
| `DECREE_EXCLUDE_MACHINES` | The machines `daemon` does not run ([Several processes](#several-processes)). |
| `DECREE_MAX_DEPTH` | `max_depth`: the deepest a message may sit in a chain of emits and child runs, a whole number of at least 1; default 10. A chain past it stops: `decree emit` refuses (`depth 11 exceeds max_depth 10 (set DECREE_MAX_DEPTH to change it): …`), and a `machine:` or `model` invoke starts no child, its event `error` with `max_depth 10 reached` ([Sub-machines](runs.md#sub-machines)). As bash's `FUNCNEST` and Python's `sys.setrecursionlimit`, it bounds recursion with a default that can be raised. Every script gets the value in effect as `DECREE_MAX_DEPTH`, so `decree emit` in a run uses the limit of the `daemon` running it. Any other value is refused before anything runs: `daemon` and `emit` exit 1 with ``DECREE_MAX_DEPTH in .decree/.env is `ten`: it must be a whole number of at least 1`` (or `in the environment`), and `decree check` reports it as an E1 error at its `.decree/.env` line, or exits 1 with that message for the shell's. |

### Stopping

Ctrl-C (SIGINT) or SIGTERM interrupts every run executing (machines run at once): it becomes `interrupted` and needs `decree retry`, and the daemon exits. To let the runs going now finish instead, pause ([Pausing](#pausing)), then stop the daemon once they have.

### Pausing

`decree pause` holds the queue and lets the runs going now finish ([D93](../decisions.md#d93-decree-pause-and-decree-resume)), as `docker pause` and `unpause` do, and Sidekiq's quiet: it writes `.decree/attention/pause.md`, which holds the queue like any holding file ([Attention](#attention)). The daemon keeps running. The run going now is not interrupted: it goes on until it reaches a final state or waits. Then `daemon --once` prints the file and exits 1, and one started while the file exists starts nothing; `daemon` prints it once and goes on polling. `decree resume` deletes the file: the next `daemon --once` runs the queue, and a running `daemon` goes on without a restart. The file is the whole of it, so a pause reaches every daemon of the project, and deleting the file resumes as `decree resume` does. `decree retry <id>` leaves `pause.md`: the retried run waits as `pending` until `decree resume`.

## Edits while running

`daemon` reads the machines and the `.env` files again before each run, and prints once each plugin that is not installed as its file says, installing nothing ([plugins.md](plugins.md#installing)), so an edit applies to the next run without a restart. A run already going keeps its machine until it finishes, waits or is interrupted; a run that continues later, after a reply, a `timeout` or `decree retry`, uses the machine as it is then, so a state it is in must still exist.

A machine edit that fails `decree check` (V1–V21) is not used: every machine stays as last loaded, and the errors are printed once, followed by ``runs keep the machines last loaded until this is fixed. Run `decree check`.``. Once the files pass, the next run uses them, and `reloaded machines: <id>, …` names the machines added, changed or removed. A malformed `.env` file likewise keeps the variables last read ([Environment](scripts.md#environment)). Scripts are read from disk each time they run, so a script edit needs no reload.

## Upgrading decree

`decree upgrade` prints the lines that do it, then offers to run the first, the README's `curl … | sh`, on a `y` (`decree upgrade --yes` runs it without asking). Install the new version, then run `decree install` in each project ([D90](../decisions.md#d90-decree-install-writes-the-schemas-and-ends-an-upgrade)): it writes the new version's JSON Schemas into `.decree/schema/v1/` (ignored by git; `decree check` warns while they are stale) and installs every plugin as its file says. After running the install line, `decree upgrade` offers to run the new copy's `decree install` in the project around the working directory. The official plugins are built into decree, so a new version may change them: `decree list` marks `differs` each one whose copy in `.decree/plugins/` is not the new version's (edited, or from the old version), and `decree install --official <name>` takes the new copy (with no name, of every official plugin the project has), printing the project's own edits it replaces (the old file goes to `.decree/archive/`), to put back and keep with `decree export <name>` ([plugins.md](plugins.md#official-plugins)). `decree install --official skill` takes the new skill, which the `skill` plugin's run at the next daemon start (`decree daemon --once` will do) writes; commit the skill.

## Retry

decree never continues a `failed` or `interrupted` run by itself ([Lifecycle](messages.md#lifecycle), step 6); `decree retry <id> [--state <s>] [--format <text|json>]` is how a person does, as Sidekiq's and GitHub Actions' retry put a job back in the queue for the workers already running ([D91](../decisions.md#d91-decree-retry-is-a-command-of-its-own)). It continues one run, in its own folder, keeping its history, whatever started it (an inbox message, cron, an `order` file or a child run).

The run must be `interrupted` or finished, a cancelled one included; a `waiting` run takes a reply instead ([`decree reply`](#cli)), or ends with [`decree cancel`](#cancel), and an `active` or `pending` one is refused, as is an unknown id, each with exit 1. Under the run's [lock](messages.md#run-lock), decree appends a `transition` event with `event: "retry"`, `source: "retry"`, `to: <s>`, `run_attempt`, the run's next attempt ([Run attempts](runs.md#step-loop)), and `decree_version`, the version of the decree retrying it, mirrors `state`, removes the run's `hold` and its attention file ([Attention](#attention)), and prints ``run <id> continues in `<s>`: a running `decree daemon` continues it, or run `decree daemon --once` `` (`--format json`: `{ "id", "state" }`). Default `<s>`: for an interrupted run, the state it was in; for a finished run, the `from` of the last `transition` that has one. `--state <s>` names another; it must be an atomic state of the run's machine. Visits count again from the retry, so a `check` on `visits` gives the run all its rounds again. The run is then `pending`: a `daemon` running its machine continues it at its next pass, with no restart, and otherwise the next `decree daemon --once` does, re-running root `onentry` and the `onentry` of every ancestor of `<s>` and of `<s>` ([Step loop](runs.md#step-loop), step 1).

## Cancel

`decree cancel <id> [-m <note>] [--format <text|json>]` ends a run nobody will continue, as GitHub Actions' and Temporal's cancel do ([D92](../decisions.md#d92-decree-cancel-ends-a-run)): one `waiting` for a reply nobody will send, one `pending`, or one `interrupted`. Under the [lock](messages.md#run-lock) of the run and of every unfinished child run below it (a child names its parent in `parent:`), it ends each in `failed`, deepest first: a `transition` with `event: "cancel"`, `to: "failed"`, `source: "cancel"` and the note as `note`, `state: failed` mirrored, then `run_finished` with `cancelled: true` ([runs.md](runs.md#eventsjsonl)). No script runs, `onexit` included, as on a signal: the work stops where it is, and a script that must clean up after a run checks for it, as the `lease` plugin drops a lease whose run is finished. Each run's `hold` and file in `.decree/attention/` are deleted, and so is every reply still queued in `inbox/` for it, which could only be rejected. It prints ``cancelled run <id> in `<state>` `` for each (`--format json`: `{ "cancelled": [id] }`, deepest first), and, when the run is a child, that its parent continues with `error`: a parent waiting for a child that ends in `failed` takes `error` as for any child that failed ([Sub-machines](runs.md#sub-machines)). `decree status` counts cancelled runs apart, as `cancelled`, and lists none of them. A cancelled run is finished, so `decree retry` continues it. A `pending` run is cancelled before a daemon continues it; an `active` one (a script of it runs now) is refused: let it reach a wait, or interrupt the daemon, then cancel it.

## Attention

decree keeps one markdown file per run that needs a person in `.decree/attention/` ([D67](../decisions.md#d67-the-attention-folder-says-what-needs-a-person)), and `decree pause` writes one more, `pause.md` ([Pausing](#pausing)). `.decree/.gitignore` lists the folder.

- **When.** `.decree/attention/<id>.md` is written when run `<id>` becomes `failed` (but by `decree cancel`), `interrupted` (a signal, or a crash that `daemon` finds later from a stale lock: a killed process writes nothing) or `waiting` in a `reply` state (unless its invoke has `attention: false`, a wait no person answers). A child run that ends in `failed` has a file only when it has a `hold`: otherwise its failure is its parent's event. The file is deleted when the run becomes `active` or `pending` (`decree retry`, a delivered reply or a `timeout`), finishes in a state other than `failed`, or is deleted by the official [`prune`](plugins.md#official-plugins) plugin. decree writes the files when a run's status changes, never by rescanning, so a file a person deleted stays deleted until the status changes again.
- **The file.** YAML frontmatter, valid against `attention.schema.json` ([Schemas](README.md#schemas)): `kind: run`, `run`, `machine` (the run's machine; for the failed `invalid_message` run of a rejected reply, which has no machine of its own, the machine of the run the reply was addressed to, and absent when that run does not exist), `message` (`inbox`), `status` (`failed`, `interrupted` or `waiting`), `state` (for a failed run, the state it failed from, which `decree retry` continues in), `since` (the `ts` of the run's last event, RFC 3339 UTC) and `holds` (`true` or `false`). Then markdown: a heading, the message's first heading; what happened and since when; the exact command, `decree retry <id>`; for a `reply` wait instead, the question, the options with their descriptions and one `decree reply <wait id> <option>` line per option; when the run holds, the text of its `hold`; when the run folder has a `leftovers` file (the built-in `clean_tree` naming the runs that may have left the changes it found, [Run-directory files](scripts.md#run-directory-files)), its text; and when the run folder has a `STOP` file (an agent's question, [Run-directory files](scripts.md#run-directory-files)), its text and `answer it in plan.md, delete STOP, then decree retry <id>`. The file `decree pause` writes has the second shape of the schema: `kind: pause`, `since` (when it was written) and `holds: true`, and no run fields; it always holds, and only `decree resume` (or deleting it) releases the hold.
- **Rejected replies.** A reply decree rejects ([Replies](messages.md#replies), step 4) is a failed `invalid_message` run, so it has a file, with `status: failed`, `state: failed` and `holds: false`: it is there to be seen, and never holds the queue, whatever the reason it was rejected ([D81](../decisions.md#d81-a-reply-queued-before-the-deadline-wins)). Delete it once read.
- **Read-only.** A reply goes through `decree reply` or a reply message ([Replies](messages.md#replies)), and a run continues with `decree retry`: editing a file answers nothing. decree never rewrites or deletes a file it did not write.
- **Holding.** A script that writes `$DECREE_RUN_DIR/hold` makes its run's file hold: when decree writes the file of a run with a `hold`, it sets `holds: true` and includes the text. The built-in `keep` script writes it when a run fails with changes in the work tree, so no other run starts on them ([D65](../decisions.md#d65-a-failed-run-keeps-its-changes-and-holds-the-queue)). A run's file holds the runs that share its machine's slots ([D95](../decisions.md#d95-a-runs-hold-holds-its-group)): its `concurrency_group` (the official `develop` and its variants, `infra` and `qa` share `worktree`, the tree `keep` protects), or the machine alone; it holds every run when its machine is not loaded. While such a file exists, `daemon` starts and continues none of those runs: no inbox message, `pending` run, reply or `timeout`; their messages stay queued, in order. Every other machine goes on. A child run of a held machine does not start: its parent takes `error`, as when no child could start ([Sub-machines](runs.md#sub-machines)). `decree pause`'s file, and any file decree cannot read, hold every run. `daemon --once` prints each holding file, with what it holds, and exits 1 once the rest has run; `daemon` prints it once and goes on polling. `decree status` says what each file holds (`holds the queue`, or `holds group `worktree``). `decree emit` and `decree reply` still queue. `decree retry` of that run removes its `hold` and its file, and the daemon continues it; a retry of another run leaves them, and that run waits as `pending`. To drop the run instead, stash its changes and delete its file: at its next check decree deletes the run's `hold`, and the queue goes on.
- **What counts.** Only `*.md` files directly in `.decree/attention/`; any other file or folder (an editor's swap file, `.DS_Store`, a subfolder) is ignored, holds nothing and is not listed. A `.md` file that cannot be read, or whose frontmatter is missing, is not YAML or does not match `attention.schema.json`, holds every run, so anything (a person, a script, another tool) can halt the queue by putting a `.md` file there, without knowing the contract. `daemon --once` and `status` name such a file with why it holds (`no frontmatter`, `invalid frontmatter: <error>`, `cannot be read: <error>`) and its first line. Only deleting the file releases its hold.
- **Where decree points to it.** `daemon --once` ends, after its per-run lines, with `<n> run(s) need attention: .decree/attention/` when the folder has files, and `decree status` starts with `Attention:` ([CLI](#cli)).

## Machine-readable output

CI systems and AI agents read `--format json` instead of parsing the text. `--format <text|json>` is on `check`, `status` (with and without an id, and with `--cron`), `emit`, `reply`, `retry`, `cancel`, `pause`, `resume`, `graph`, `upgrade`, `install`, `list` and `export`. `text` is the default and unchanged. With `json`, the command prints exactly one JSON document on stdout (pretty-printed; keys in any order), errors still go to stderr, and the exit code is the text mode's. A command that fails before it has anything to report (`emit` or `reply` refusing, `graph` with a broken cron file) prints nothing on stdout. `daemon` and `tail` produce streams, and `init` and `help` are for people, so they take no `--format`.

Each document has a JSON Schema, `schema/v1/cli/<command>.schema.json` in the decree repository and `.decree/schema/v1/cli/<command>.schema.json` once `decree init` or `decree install` writes it with the others; `install`, `list` and `export` share `cli/plugin.schema.json` ([Schemas](README.md#schemas)) and versioned the same way ([Versioning](README.md#versioning)). Paths are relative to the project root (`.decree/inbox/<id>.md`), except the files `check` names, which are relative to `.decree/`, as in its text.

| Command | Document |
| --- | --- |
| `check` | `{ "valid", "errors": [{ "rule", "file", "line"?, "state"?, "message" }], "warnings": [{ "file", "message" }] }`. One error per text line, in the same order: `rule` is `V1`…`V21`, `M2`, `M3`, `E1`, `P1` or `P2` ([Validation](machines.md#validation)), or `null` for an error no rule names, such as YAML that does not parse; `line` when the error names a line, `state` (a dotted path) when it is inside a state; `message` without the rule. `warnings` are what the text prints on stderr. Exit 1 when `errors` is not empty. |
| `status` | `{ "attention": [file], "counts": { "total", "active", "waiting", "pending", "interrupted", "finished" }, "runs": { "active": [run], "waiting": [run], "pending": [run], "interrupted": [run], "finished": { "<final state>": [run] } }, "queued": { "inbox": [file], "held": [file] } }`, `held` being the inbox files a hold keeps there ([Attention](#attention)). A run is `{ "id", "machine", "state" }`, plus `running` (`script`, `phase`, `state`, `pid`, `started_at`, `log`) for an `active` run, `wait_id` and `options` for a run waiting for a person, or `child` for a run waiting for a child run, and `held: true` for a `waiting` or `pending` run whose machine a file in `.decree/attention/` holds. A file is the frontmatter of a file in `.decree/attention/` plus its `path`, or `{ "path", "holds": true, "error" }` for one decree cannot read ([Attention](#attention)); those that hold the queue come first. |
| `status <id>` | `{ "id", "machine", "status", "state", "events" }`: the derived status, the current state (`null` before the first transition), and every line of `events.jsonl` parsed, each valid against `events.schema.json`. An unknown id is an error: nothing on stdout, `error: no run <id> in .decree/runs/` on stderr, exit 1, as in text. |
| `emit`, `reply` | `{ "id", "path" }`: the queued message and its file, `.decree/inbox/<id>.md`. |
| `retry` | `{ "id", "state" }`: the run made `pending` and the state it continues in. |
| `cancel` | `{ "cancelled": [id] }`: the runs ended, deepest child first, the one named last. |
| `pause`, `resume` (`cli/pause.schema.json`) | `{ "attention", "paused" }`: the file that holds the queue while paused, `.decree/attention/pause.md`, and whether it is paused now (`true` from `pause`, whether it wrote the file or it was there); `resume` adds `"resumed"`, whether it deleted the file. |
| `upgrade` | `{ "version", "install", "pinned", "cargo", "cargo_note", "releases", "after": [{ "command", "when"? }] }`: the lines the text prints, `<tag>` standing for a release tag; `after` is `decree install`, `decree list` and `decree install --official [<name>...]`, each with `when` saying when it is needed and what it does. |
| `install`, `list`, `export` (`cli/plugin.schema.json`) | One shape per `action`. `list`: `{ "action", "version", "plugins": [{ "name", "description", "official", "differs", "state" }], "unplugged": [name], "available": [{ "name", "description", "needs" }] }`, `state` being `installed`, `not installed`, `edited` or `invalid`. `install` (with names): `{ "action", "plugins": [{ "plugin", "file", "status", "needed_by", "changes": [{ "path", "change", "lines" }], "archived" }] }`, `archived` being the archive folder or `null`, `status` being `installed`, `added`, `needed` or `replaced`. `export` with no name: `{ "action", "exported": [name], "conflicts": [name], "dry_run" }`. `export`: `{ "action", "plugin", "file", "files": [{ "path", "lines" }], "needs" }`, the plugin file and each file it installs with its line count. `import` (a file or stdin): the same plus `"description"`, `"replaced"` and `"changes": [{ "path", "change" }]`, each file `added`, `changed` or `removed` from the file it replaced, `"added": [name]`, the official plugins it needs that it seeded, and `"archived"`. `sync` (`decree install` with no argument): `{ "action", "installed": [name], "removed": [name], "archived": [{ "plugin", "archive" }] }`. |
| `graph` | `{ "written": [path], "removed": [path] }`: the files written, and the stale ones removed. |

### SARIF

`decree check --format sarif` prints a [SARIF 2.1.0](https://docs.oasis-open.org/sarif/sarif/v2.1.0/errata01/os/sarif-v2.1.0-errata01-os-complete.html) log, the OASIS standard that GitHub code scanning, GitLab and Azure DevOps read, so machine errors show up inline in pull requests. It has one run, whose `tool.driver` is `decree` with its version, an `informationUri` (these reference docs) and one `rules` entry per V1–V21, M2–M3 and E1, each with its `id`, a `shortDescription` (the check in the [Validation](machines.md#validation) table) and a `helpUri` to that table. Each error is a `result` with `ruleId` (absent for an error no rule names), `level: "error"`, `message.text` (prefixed with the state path when the error is inside a state) and a `physicalLocation` whose `artifactLocation.uri` is the file relative to the project root (`.decree/machines/develop/machine.yml`), with `region.startLine` when the error names a line. Each warning is a result with `level: "warning"` and no `ruleId`. Exit 1 if there are errors, as in text and JSON.

A GitHub Actions job that uploads it to code scanning with [`github/codeql-action/upload-sarif`](https://github.com/github/codeql-action/tree/main/upload-sarif) ([Uploading a SARIF file to GitHub](https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/uploading-a-sarif-file-to-github)); `|| true` keeps the job going to the upload when there are errors, and the last step fails the job on them:

```yaml
name: decree check
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    permissions:
      security-events: write # upload results to code scanning
      contents: read
    steps:
      - uses: actions/checkout@v4
      - run: cargo install decree
      - run: decree check --format sarif > decree.sarif || true
      - uses: github/codeql-action/upload-sarif@v4
        with:
          sarif_file: decree.sarif
          category: decree
      - run: decree check
```

This repository's own [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) is a complete example: it checks the root project and every `examples/*/` project, prefixes each project's directory to its `uri`s and gives each its own category through `automationDetails.id`.

Code scanning on a private repository needs GitHub Code Security (or Advanced Security).
