# CLI

decree has 15 commands, plus `--version` (`-v`). `decree` with no command runs `decree process`. Every command takes `--no-color`; without it, colour follows `NO_COLOR` and whether the output is a terminal. Every command that reports something takes `--format <text|json>`, and `decree check` also `--format sarif` ([Machine-readable output](#machine-readable-output)).

Every command except `init`, `upgrade` and `help` works on the project whose `.decree/` is in the current directory or the nearest ancestor. Without one it fails with ``not inside a decree project (run `decree init` first)``. Errors are printed to stderr as `error: <message>`.

### Output

Unless `--quiet`, `process` and `daemon` print each run as it goes, on stdout, as `decree tail` would: `▶ <id> · <machine>` as a run starts or continues (`<id> (<file>)` for a migration's run, here and in every line below, [Naming a run](#naming-a-run)), then its script output behind the same per-script headers, then one line as it stops: `✓ <id> <final state> in <time>`, `✗ <id> failed in <time>`, `⏸ <id> waiting in <state> after <time>`, or `■ <id> interrupted in <state> after <time>` (`45s`, `3m 12s`, `1h 02m`). On a terminal a status line stays below the output, `▶ <id> · <machine> · <state> · <elapsed> · <n>/<total>`: the innermost run's machine and state (a child run's, while the run waits for it), how long the run has gone on, and that it is the `n`th run this command has started, of `n` plus the inbox messages and pending migrations still queued. Off a terminal (a pipe, a file, cron) there is no status line. Notices (a failed run's `--retry` command, a blocked migration) go to stderr, after the output of the run they are about. `--quiet` prints only those notices and the closing summary, as cron and CI want. Everything but the status line also goes to `.decree/process.log`, with `--quiet` too, so there is no need to `tee` the output: the run headers, the script output, the line each run stops with, and the notices. decree trims it to its last 2 MiB, behind a `[log truncated …]` line, as each run stops; `.decree/.gitignore` lists it.

Usage errors (an unknown command or flag, a missing argument, `--format` where it does not apply) exit 2.

Error formats:

- `process` and `daemon` validate every machine (V1–V21) before anything runs. If any fails, they print each error as `decree check` does, then ``N machine error(s); nothing was processed. Run `decree check`.``, and exit 1. They then read `.decree/.env` and every machine's `env_file` (E1): a malformed line is printed the same way, followed by ``N error(s) in .decree/.env; nothing was processed. Run `decree check`.`` (naming each file with an error), and they exit 1. Once running, both read the machines and `.env` files again before each run ([Edits while running](#edits-while-running)).
- An invalid pending migration stops them the same way: `N migration(s) are invalid; nothing was processed.` ([Migrations](messages.md#migrations-ordered-run-once-stop-on-error), rule 6).
- A waiting run is printed as:

  ```text
  Waiting: run <run id> in `<state>`: <the state's description, else its id>
    wait id <wait id>, options: <option>, <option>
    decree event <wait id> <option>
  ```

  with one `decree event` line per option; a migration's run is `<run id> (<file>)`.

## `process` or `daemon`

Both run the same pipeline; they differ in when they stop.

- `decree process` is one pass. It runs everything it can, then prints each waiting run and exits. A run that waits for a person, or for a `timeout`, stays `waiting` until someone runs `process` again after the reply or deadline. It fires no cron files. Use it by hand, in CI, or from a scheduler that runs it again (`decree process --quiet` in a crontab).
- `decree daemon` keeps polling until stopped. It fires cron files, delivers each reply and `timeout` as it comes, and continues the run. For unattended work, anything with cron files, `person` states or `timeout`s, run `daemon` under a supervisor (a systemd service, a tmux session, a container) with `--quiet` if its output goes to a log.

Neither continues a `failed` or `interrupted` run by itself: `--retry` on either does ([Retry](#retry)).

### Several processes

Several `process` or `daemon` commands can share one project folder, each running its own machines, as Celery's `--queues` and `--exclude-queues` give each worker its queues ([D69](../decisions.md#d69-a-process-runs-the-machines-it-is-given)):

| Flag or variable | Effect |
| --- | --- |
| `--machine <m>` | Run only these machines. Repeatable; each value is a comma-separated list (`--machine develop,qa`). |
| `--exclude-machine <m>` | Run every machine but these. Repeatable, comma-separated. Not with `--machine` (exit 2). |
| `DECREE_MACHINES` | As `--machine`, comma-separated, from the shell or `.decree/.env`. |
| `DECREE_EXCLUDE_MACHINES` | As `--exclude-machine`. Not with `DECREE_MACHINES` from the same place (exit 2). |

A flag beats both variables, and the shell beats `.decree/.env`; an empty variable is unset. These are the only `DECREE_*` keys `.decree/.env` may set (E1 rejects every other, and a machine's `env_file` may set neither); decree reads them itself and never passes them to scripts. A name that is not a machine in `.decree/machines/` or a built-in is an error naming it, exit 1.

- **What a filtered process does.** It delivers replies and timeouts, continues `pending` runs, claims inbox messages and fires cron files only for its machines; everything else stays where it is, untouched. A run belongs to the machine of its root run: the process that runs a parent steps its child runs, whatever their machine. `--dry-run` lists only what this process would run, and `--retry` of a run for another machine is refused, naming the machine.
- **Migrations keep one order.** When the first pending migration is for a machine the process does not run, it waits, starting no later migration, and ends with ``Held back: migration <file> is for machine `<m>`, which this process does not run``, exit 0.
- **What keeps processes apart.** An inbox claim is an atomic rename and a run has its [run lock](messages.md#run-lock), so two processes never take the same message or step the same run.
- **`.decree/.env` applies to every process in the folder.** Give different filters by flag or shell: `decree daemon --machine comfy` in one terminal, `decree daemon --exclude-machine comfy` in another.
- **The work tree is shared.** The built-in `develop`, `infra` and `qa` share it through `clean_tree` and `commit`, so two processes must not run them at once in one checkout; decree does not check this. Give each such process its own git worktree.
- **A hold holds everyone.** An attention file with `holds: true` ([Attention](#attention)) holds every process, whatever its filter.

### Stopping

Ctrl-C (SIGINT) or SIGTERM interrupts the run that is going: it becomes `interrupted` and needs `decree process --retry`. `decree stop` instead lets it finish ([D68](../decisions.md#d68-a-graceful-stop-is-an-attention-file)), as `nginx -s quit` finishes the requests in flight: it writes `.decree/attention/manual-stop.md`, which holds the queue like any holding file ([Attention](#attention)). The run going now is not interrupted: it goes on until it reaches a final state or waits. Then `process` prints the file and exits 1, and a `process` started while the file exists starts nothing; `daemon` prints it once and goes on polling. Delete the file to resume: the next `process` runs the queue, and a running `daemon` goes on without a restart. `decree process --retry <id>` leaves `manual-stop.md`: the retried run waits as `pending` until the file is deleted.

## Edits while running

`process` and `daemon` read the machines and the `.env` files again before each run, so an edit applies to the next run without a restart. A run already going keeps its machine until it finishes, waits or is interrupted; a run that continues later, after a reply, a `timeout` or `--retry`, uses the machine as it is then, so a state it is in must still exist.

A machine edit that fails `decree check` (V1–V21) is not used: every machine stays as last loaded, and the errors are printed once, followed by ``runs keep the machines last loaded until this is fixed. Run `decree check`.``. Once the files pass, the next run uses them, and `reloaded machines: <id>, …` names the machines added, changed or removed. A malformed `.env` file likewise keeps the variables last read ([Environment](scripts.md#environment)). Scripts are read from disk each time they run, so a script edit needs no reload. Pending migrations are validated when the command starts (rule 6); one added later that is invalid fails its own run.

## Upgrading decree

`decree upgrade` prints the lines that do it. Install the new version, then, in each project, run `decree skill`, and `decree schema` if the project has `.decree/schema/`. `decree skill` refreshes the decree skill that `init` wrote, and `decree schema` the local copy of the JSON Schemas in `.decree/schema/v1/`; when that folder exists, `decree check` warns until it is current. Commit the skill; the schema copy is ignored by git.

## Retry

decree never continues a `failed` or `interrupted` run by itself ([Lifecycle](messages.md#lifecycle), step 6); `decree process --retry` is how a person does, or `decree daemon --retry` to continue it and keep polling. It continues one run, in its own folder, keeping its history:

- `--retry` alone: the migration that blocks the queue, the earliest pending migration whose run is `failed` or `interrupted`, or `waiting` for a child run that is `interrupted` ([Migrations](messages.md#migrations-ordered-run-once-stop-on-error), rule 4). For that one it continues the interrupted child, the last in the chain of child runs the migration waits for; once the child finishes, its parent continues. With none: `nothing to retry: no migration is failed or interrupted`, exit 1.
- `--retry <id>`: run `<id>`, whatever started it (a migration, an inbox message, cron or a child run). A migration's file name or stem works too ([Naming a run](#naming-a-run)).

The run must be `interrupted` or finished; a `waiting` run takes a reply instead ([`decree event`](#cli)), and an `active` or `pending` one is refused, as is an unknown id. decree appends a `transition` event with `event: "retry"`, `source: "retry"`, `to: <s>`, `run_attempt`, the run's next attempt ([Run attempts](runs.md#step-loop)), and `decree_version`, the version of the decree retrying it, mirrors `state`, and prints ``run <id> continues in `<s>` `` (``run <id> (<file>) continues …`` for a migration's run). Default `<s>`: for an interrupted run, the state it was in; for a finished run, the `from` of the last `transition` that has one. `--state <s>` names another; it must be an atomic state of the run's machine. Visits count again from the retry, so a `check` on `visits` gives the run all its rounds again. The run is then `pending`, and the same `process` continues it, re-running root `onentry` and the `onentry` of every ancestor of `<s>` and of `<s>` ([Step loop](runs.md#step-loop), step 1), then everything queued after it. `--retry` takes no `--dry-run` and no `--format`. On `daemon`, `--retry` acts once, before the first pass; a daemon already running is stopped and started again with it, or left running while `decree process --retry <id>` continues the run (the [run lock](messages.md#run-lock) keeps the two apart).

## Naming a run

Every run has a time id, a migration's included ([Migrations](messages.md#migrations-ordered-run-once-stop-on-error), rule 1). Wherever a person names a run, `decree process --retry <id>`, `decree daemon --retry <id>`, `decree status <id>`, `decree tail <id>` and `decree event <id> <event>`, a migration's file name (`01-a.md`) or stem (`01-a`) works too, and means that migration's newest run: the latest time id among the runs whose `message.md` has `migration: <file>`, else a run folder named by the stem from before migration runs had time ids ([D73](../decisions.md#d73-migration-runs-get-time-ids-like-every-other-run)). A name that is a migration's is read as one first; any other is a run id. A name that is neither fails as an unknown id does.

Everything that shows a migration's run shows its file with it, `<id> (<file>)`: the run lines of `decree status` (and `"migration": "<file>"` beside `id` in `--format json`), `decree status <id>`'s `migration:` line (and its JSON `migration`), the `▶`, `✓`, `✗`, `⏸` and `■` lines of `process`, `daemon` and `tail` ([Output](#output)), `process`'s `Waiting:` lines and the `--retry` notice, `prune`'s lines (and its JSON `migration`), the `message` of its file in `.decree/attention/` ([Attention](#attention)), and the title of the commit the built-in `commit` script writes, `<heading> (<file>)`.

## Attention

decree keeps one markdown file per run that needs a person in `.decree/attention/`, as `processed.md` records what is done ([D67](../decisions.md#d67-the-attention-folder-says-what-needs-a-person)), and `decree stop` writes one more, `manual-stop.md` ([Stopping](#stopping)). `.decree/.gitignore` lists the folder.

- **When.** `.decree/attention/<id>.md` is written when run `<id>` becomes `failed`, `interrupted` (a signal, or a crash that `process` or `daemon` finds later from a stale lock: a killed process writes nothing) or `waiting` in a `person` state; and for a migration that blocks the queue by waiting for an `interrupted` child run ([Migrations](messages.md#migrations-ordered-run-once-stop-on-error), rule 4), under the migration's id, naming the child. A child run that ends in `failed` has a file only when it has a `hold`: otherwise its failure is its parent's event. The file is deleted when the run becomes `active` or `pending` (`--retry`, a delivered reply or a `timeout`), finishes in a state other than `failed`, or is deleted by `decree prune`. decree writes the files when a run's status changes, never by rescanning, so a file a person deleted stays deleted until the status changes again.
- **The file.** YAML frontmatter, valid against `attention.schema.json` ([Schemas](README.md#schemas)): `kind: run`, `run`, `machine`, `message` (the migration's file name, or `inbox`), `status` (`failed`, `interrupted` or `waiting`), `state` (for a failed run, the state it failed from, which `--retry` continues in), `since` (the `ts` of the run's last event, RFC 3339 UTC) and `holds` (`true` or `false`). Then markdown: a heading, the message's first heading; what happened and since when; the exact command, `decree process --retry <id>` (for a migration waiting for a child, the child's id); for a `person` wait instead, the question, the options with their descriptions and one `decree event <wait id> <option>` line per option; for a migration, `later migrations are blocked until it finishes`; when the run holds, the text of its `hold`; when the run folder has a `leftovers` file (the built-in `clean_tree` naming the runs that may have left the changes it found, [Run-directory files](scripts.md#run-directory-files)), its text; and when the run folder has a `STOP` file (an agent's question, [Run-directory files](scripts.md#run-directory-files)), its text and `answer it in plan.md, delete STOP, then decree process --retry <id>`. The file `decree stop` writes has the second shape of the schema: `kind: manual-stop`, `since` (when it was written) and `holds: true`, and no run fields; it always holds, and only deleting it releases the hold.
- **Read-only.** A reply goes through `decree event` or a reply message ([Replies](messages.md#replies)), and a run continues with `decree process --retry`: editing a file answers nothing. decree never rewrites or deletes a file it did not write.
- **Holding.** A script that writes `$DECREE_RUN_DIR/hold` makes its run's file hold the queue: when decree writes the file of a run with a `hold`, it sets `holds: true` and includes the text. The built-in `keep` script writes it when a run fails with changes in the work tree, so no other run starts on them ([D65](../decisions.md#d65-a-failed-run-keeps-its-changes-and-holds-the-queue)). While any file has `holds: true`, `process` and `daemon` start and continue no runs: no inbox message, migration, `pending` run, reply or `timeout`. `process` prints each holding file and exits 1; `daemon` prints it once and goes on polling until nothing holds. `decree emit` and `decree event` still queue. `decree process --retry` of that run (or `daemon --retry`) removes its `hold` and its file, then continues it; a retry of another run leaves them, and that run waits as `pending`. To drop the run instead, stash its changes and delete its file: at its next check decree deletes the run's `hold`, and the queue goes on.
- **What counts.** Only `*.md` files directly in `.decree/attention/`; any other file or folder (an editor's swap file, `.DS_Store`, a subfolder) is ignored, holds nothing and is not listed. A `.md` file that cannot be read, or whose frontmatter is missing, is not YAML or does not match `attention.schema.json`, holds the queue as if it had `holds: true`, so anything (a person, a script, another tool) can halt the queue by putting a `.md` file there, without knowing the contract. `process` and `status` name such a file with why it holds (`no frontmatter`, `invalid frontmatter: <error>`, `cannot be read: <error>`) and its first line. Only deleting the file releases its hold.
- **Where decree points to it.** `process` ends, after its per-run lines, with `<n> run(s) need attention: .decree/attention/` when the folder has files, and `decree status` starts with `Attention:` ([CLI](#cli)).

## Machine-readable output

CI systems and AI agents read `--format json` instead of parsing the text. `--format <text|json>` is on `check`, `status` (with and without an id), `emit`, `event`, `stop`, `prune`, `graph`, `schema`, `skill`, `upgrade` and `process --dry-run`. `text` is the default and unchanged. With `json`, the command prints exactly one JSON document on stdout (pretty-printed; keys in any order), errors still go to stderr, and the exit code is the text mode's. A command that fails before it has anything to report (`emit` or `event` refusing, `graph` with a broken cron file) prints nothing on stdout. `process` (without `--dry-run`), `daemon` and `tail` produce streams, and `init` and `help` are for people, so they take no `--format`; nor does `status --cron`.

Each document has a JSON Schema, `schema/v1/cli/<command>.schema.json` in the decree repository and `.decree/schema/v1/cli/<command>.schema.json` once `decree schema` writes it with the others ([Schemas](README.md#schemas)) and versioned the same way ([Versioning](README.md#versioning)). Paths are relative to the project root (`.decree/inbox/<id>.md`), except the files `check` names, which are relative to `.decree/`, as in its text.

| Command | Document |
| --- | --- |
| `check` | `{ "valid", "errors": [{ "rule", "file", "line"?, "state"?, "message" }], "warnings": [{ "file", "message" }] }`. One error per text line, in the same order: `rule` is `V1`…`V21`, `M1`…`M3` or `E1` ([Validation](machines.md#validation)), or `null` for an error no rule names, such as YAML that does not parse; `line` when the error names a line, `state` (a dotted path) when it is inside a state; `message` without the rule. `warnings` are what the text prints on stderr. Exit 1 when `errors` is not empty. |
| `status` | `{ "attention": [file], "counts": { "total", "active", "waiting", "pending", "interrupted", "finished" }, "runs": { "active": [run], "waiting": [run], "pending": [run], "interrupted": [run], "finished": { "<final state>": [run] } }, "queued": { "inbox": [file], "migrations": [file] } }`. A run is `{ "id", "machine", "state" }`, plus `running` (`script`, `phase`, `state`, `pid`, `started_at`, `log`) for an `active` run, `wait_id` and `options` for a run waiting for a person, or `child` for a run waiting for a child run. A file is the frontmatter of a file in `.decree/attention/` plus its `path`, or `{ "path", "holds": true, "error" }` for one decree cannot read ([Attention](#attention)); those that hold the queue come first. |
| `status <id>` | `{ "id", "machine", "status", "state", "events" }`: the derived status, the current state (`null` before the first transition), and every line of `events.jsonl` parsed, each valid against `events.schema.json`. An unknown id is an error: nothing on stdout, `error: no run <id> in .decree/runs/` on stderr, exit 1, as in text. |
| `emit`, `event` | `{ "id", "path" }`: the queued message and its file, `.decree/inbox/<id>.md`. |
| `stop` | `{ "attention" }`: the file that holds the queue, `.decree/attention/manual-stop.md`, whether this command wrote it or it was there. |
| `upgrade` | `{ "version", "install", "pinned", "cargo", "cargo_note", "releases", "after": [{ "command", "when"? }] }`: the lines the text prints, `<tag>` standing for a release tag; `after` is `decree skill`, then `decree schema` with `when` saying it is for a project with `.decree/schema/`. |
| `prune` | `{ "runs": [{ "id", "machine", "state", "finished" }], "bytes", "dry_run" }`: the runs deleted (or, with `--dry-run`, that would be), their final state and `run_finished` time, and their size in bytes. A run that could not be pruned is reported on stderr after the document, with exit 1. |
| `graph`, `schema` | `{ "written": [path], "removed": [path] }`: the files written, and the stale ones removed. |
| `skill` | `{ "written": [path], "unchanged": [path], "removed": [path] }`: the skill files written, those already identical, and the files removed from `reference/`. |
| `process --dry-run` | `{ "migrations": [item], "inbox": [item] }`, in the order `process` would take them. An item is `{ "file", "valid", "machine"? , "to"? }`: `machine` for a message that starts a run, `to` for a reply; an invalid one has neither, and its errors go to stderr with exit 1. |

### SARIF

`decree check --format sarif` prints a [SARIF 2.1.0](https://docs.oasis-open.org/sarif/sarif/v2.1.0/errata01/os/sarif-v2.1.0-errata01-os-complete.html) log, the OASIS standard that GitHub code scanning, GitLab and Azure DevOps read, so machine errors show up inline in pull requests. It has one run, whose `tool.driver` is `decree` with its version, an `informationUri` (these reference docs) and one `rules` entry per V1–V21, M1–M3 and E1, each with its `id`, a `shortDescription` (the check in the [Validation](machines.md#validation) table) and a `helpUri` to that table. Each error is a `result` with `ruleId` (absent for an error no rule names), `level: "error"`, `message.text` (prefixed with the state path when the error is inside a state) and a `physicalLocation` whose `artifactLocation.uri` is the file relative to the project root (`.decree/machines/develop.yml`), with `region.startLine` when the error names a line. Each warning is a result with `level: "warning"` and no `ruleId`. Exit 1 if there are errors, as in text and JSON.

A GitHub Actions job that uploads it to code scanning with [`github/codeql-action/upload-sarif`](https://github.com/github/codeql-action/tree/main/upload-sarif) ([Uploading a SARIF file to GitHub](https://docs.github.com/en/code-security/code-scanning/integrating-with-code-scanning/uploading-a-sarif-file-to-github)); `|| true` keeps the job going to the upload when there are errors, and the last step fails the job on them:

```yaml
name: decree check
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    permissions:
      security-events: write # upload results to code scanning
      contents: read
    steps:
      - uses: actions/checkout@v4
      - run: cargo install decree
      - run: decree check --format sarif > decree.sarif || true
      - uses: github/codeql-action/upload-sarif@v4
        with:
          sarif_file: decree.sarif
          category: decree
      - run: decree check
```

This repository's own [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) is a complete example: it checks the root project and every `examples/*/` project, prefixes each project's directory to its `uri`s and gives each its own category through `automationDetails.id`.

Code scanning on a private repository needs GitHub Code Security (or Advanced Security).
