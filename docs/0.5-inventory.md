## Conflicts

Things in the 0.4.2 code, the toolchain or the spec that contradict the spec or each other.

- **C1. Clippy findings in a test file (resolved).** Once `src/` is clean, `cargo clippy --all-targets -- -D warnings` reports 3 `clippy::useless_conversion` errors in `tests/integration_test.rs`: `Command::from(cargo_bin_cmd!("decree"))`, where `cargo_bin_cmd!` already returns an `assert_cmd::Command`. Section 11 counts 21 errors, all in `src/`. M0.1 originally allowed only `cargo fmt` to touch test files; it now allows clippy fixes in `tests/`, and all three were rewritten to `cargo_bin_cmd!("decree")`.
- **C2. `decree process` ignores SIGTERM.** `commands/process.rs` `register_signal_handlers` registers SIGINT twice and SIGTERM never, though its comment says it forwards SIGTERM. SIGTERM therefore kills decree by the default action, and the routine, which runs in its own process group, keeps running. Section 6 says to reuse 0.4.2's group signalling, and M2.2 and M4.2 require SIGTERM to stop the child within 10 s, so that code needs a SIGTERM handler, not just reuse.
- **C3. No SIGKILL escalation.** Both executors send SIGTERM to the group and then call `child.wait()` with no deadline. Section 6 requires waiting up to 10 s and then sending SIGKILL.
- **C4. Three more spawn paths outside the executor.** Hooks, the precheck and the AI router command all run through `bash` with `.output()`. They get no process group, no timeout, and are not stopped on a signal. Section 6 requires one executor with `Command::new(path)` and no `bash` wrapper. Hooks and the precheck go in M5.3; the router command moves in M3.3.
- **C5. Inbox order is LIFO.** `commands/process.rs` `select_next_message` takes the alphabetically last file, or the highest `seq` in the current chain (depth first). `commands/daemon.rs` takes `inbox.last()`. Section 4 (Claim) and Q8 require first-in, first-out by filename. M4.1 and M4.4 change this.
- **C6. The daemon never runs migrations.** `commands/daemon.rs` never calls `unprocessed_migrations`. It marks a message's `migration:` processed on success, and has no token-exhaustion handling. Section 8 says the daemon runs "next migration" through the same functions as `process`. This is item 19's duplicate pipeline, but its behaviour differs from `process`, not just its code.
- **C7. Literal "zero hits" in M5.3 and section 12 cannot hold for leaf names.** `rg -w` on `run`, `error`, `init`, `log`, `success`, `color`, `verify` and `discover` matches code that 0.5 keeps (every command's `run`, `DecreeError`, `decree init`, script logs). `routine` must keep matching, because section 1 rule 4 keeps `routine:` as an alias of `machine:`. Those greps need qualified patterns, such as the ones in this file.
- **C8. Compatibility alias outside the spec.** `config::RoutineEntry` accepts `max_retries` as an alias of `max_attempts` (`#[serde(alias = "max_retries")]`). The spec does not mention it. It goes away with `RoutineEntry` (item 3, M5.3).
- **C9. Non-interactive `init` overwrites `.decree/`.** Without a TTY, `commands/init.rs` (comment at line 227) proceeds over an existing `.decree/`. Section 8 requires it to refuse and exit 2. This is M0.5's scope.
