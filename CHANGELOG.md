# Changelog

All notable changes to decree are listed here. The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and decree follows [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html). The files decree reads and writes are versioned separately, in their schema path (`v1`), as [Versioning](docs/reference/README.md#versioning) states: within `v1` changes are additive only, and while decree is 0.x every change to `v1` is listed here.

## [Unreleased]

0.6.0, first as the release candidate 0.6.0-rc.1. Machines are shared as plugins, one file each, and each machine owns one folder, `.decree/machines/<name>/`. decree ships the official plugins built in; `decree init` adds `ai`, `order`, `prune` and `skill`, and the rest wait until a project adds them. Ordered work is order files, run by the `order` plugin at each start, in place of migrations. These changes break a 0.5.0 project, so this is a minor release while decree is 0.x: `person:` is `reply:` (and `ask:` is `notify:`), `.decree/lib/` is gone, the domain layout, `store:` is `state_files:`, migrations are order files, `decree process` is `decree daemon --once`, `decree plugin add|import|install` is `decree install`, `decree plugin list|export` is `decree list|export`, `decree event` is `decree reply`, and `decree prune` and `decree skill` are plugins. Each entry below says what to rewrite; [Converting an existing project](docs/reference/plugins.md#converting-an-existing-project) lists the steps.

### Added

- The official `order` plugin ([D86](docs/decisions.md#d86-machines-own-their-folders-order-replaces-migrations), [Order files](docs/reference/messages.md#order-files-run-in-order-at-each-start)), which `decree init` adds: at each daemon start it runs every machine's `order/*.md`, one at a time in file-name order, each only once `inbox/` is empty, and records `<file> <sha256>` in that machine's `state/order.git.txt`; an edited file runs again, and a failed one stops the rest until the next start. `ORDER_MAX` limits the files per start. It also carries `emit_if_changed.sh` and `emit_if_changed_git.sh`, which queue a message only when it differs from the last one under a key, the second with a record git tracks.
- The official `ai` plugin, a library with no machine: one `ai.sh`, which the plugins that ask AI need and source. The official `skill` plugin: the decree skill's files, written by `decree init` and copied at each daemon start into `.claude/skills/decree/` and `.github/skills/decree/`, only where they differ. `decree init` adds both.
- The official `prune` plugin ([D86](docs/decisions.md#d86-machines-own-their-folders-order-replaces-migrations)), which `decree init` adds: every Sunday at 03:00 it deletes the folders of finished runs older than `PRUNE_OLDER_THAN` (`30d`), but a child run whose parent is not finished and a run a process holds; `PRUNE_DRY_RUN=1` lists them.
- `{ machine: { message: <file> } }` ([Invoke](docs/reference/machines.md#invoke-the-states-function)): runs a message file, relative to the run's folder, as the child run, with that file's machine, params and body; any final state but `failed` is `done`.
- Machines run at once ([D89](docs/decisions.md#d89-machines-run-at-once-each-saying-how-many-of-itself), [Concurrency](docs/reference/machines.md#concurrency)): `decree daemon` (and `--once`) runs each run in its own thread, and a machine's `concurrency` (default 1) says how many of its runs may execute at once, across every process sharing the project. A run waiting for a reply, a timer or a child holds no slot. A machine at its limit keeps its messages queued, in order, while the others go on, so a slow machine no longer holds up the rest. Machines naming one `concurrency_group` share its slots: the official `develop` and its variants, `qa` and `infra` are in `worktree`, so one of them edits a checkout at a time; V20 refuses a machine that invokes one in its own group. A child run takes a slot of its own machine. Output of runs executing at once is behind `[<id's last six characters>] `, and `decree status` shows each machine's executing runs against its limit (`executing` in JSON). `lease` takes 16 at once and the routers 4. The `order` plugin's next file waits, beside an empty inbox, for no other run to be executing or pending, and a lease's place in line is when its message was queued.
- A `reply` invoke takes `timeout_at` in place of `timeout` ([D88](docs/decisions.md#d88-a-wait-can-end-at-an-instant-a-script-wrote), [Invoke](docs/reference/machines.md#invoke-the-states-function)): the wait ends at an instant read from the run's folder when it starts, `<file>` holding an RFC 3339 instant or `<file>#<JSON Pointer>` into a JSON file, as the AWS Step Functions Wait state's `TimestampPath`. A reply queued before it still wins. With no instant to read, the state's event is `error` at once, the transition's `error` saying why (`source: timeout`).
- `decree daemon --once` ([D86](docs/decisions.md#d86-machines-own-their-folders-order-replaces-migrations), [cli.md](docs/reference/cli.md)): start (fire `@reboot` cron files), deliver replies, continue pending runs and drain the inbox, sleeping through `reply` timers with `attention: false`, then exit; with `--dry-run`, `--format`, `--retry <id>` and the machine filters.
- A file named `*.git.*` in a machine's `state/` (`order.git.txt`, `swap/box1.git.sh`) is committed: `decree init`'s `.gitignore` keeps it. Settings a project's owner writes for a plugin go there, seeded once by the plugin's `state:` key, so no install replaces them ([D87](docs/decisions.md#d87-what-can-be-leased-is-the-projects-and-the-registry-says-where-to-go)).
- The official `develop` variants `develop_rust`, `develop_node` and `develop_react` ([D84](docs/decisions.md#d84-develop-variants-are-separate-machines), `decree install develop_rust`): `develop`'s machine under its own name, with `develop`'s scripts but for the gate, the conventions its implement, fix and verify prompts read (`scripts/<variant>/conventions.md`), and the tools it declares in `scripts/<variant>/requirements` (`cargo`; `node` and `npm`). `develop_rust`'s gate runs `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test`. `develop_node`'s uses the package manager the lockfile names (npm, pnpm or yarn; npm without one), installs as it does for CI, then runs `lint`, `typecheck` and `test`, each only if `package.json` defines it, saying which it skipped; with none defined it names `pass` and says it checked nothing. `develop_react`'s runs `develop_node`'s checks, then `build`, and its prompts ask for component tests with the project's test runner and Testing Library. A missing tool is a non-zero exit that names it. `develop` is unchanged.
- The official `lease` plugin ([D83](docs/decisions.md#d83-leases-are-an-official-plugin-not-core), `decree install lease`): one holder per resource at a time, for a limited time, with the next holder picked to keep mode swaps rare. Ask with a message for machine `lease` (params `resource`, `mode`, optional `duration` and `holder`); the run id is the lease id, and the lease is held exactly while its run is in `held`. `decree reply <id> release` gives it back or leaves the line; `renew` extends a held lease only while nothing else waits. The rules are the project's `machines/lease/state/resources.git.txt` (`<name> <max_lease> <linger> <max_wait> [modes] [holders]`, seeded with no resources; a lease for a mode not listed fails at once, and `holders`, default 1, lets that many leases hold the resource at once in its current mode: shared within a mode, exclusive across modes): the current mode goes first, the resource lingers in its mode for `linger`, and `max_wait` is a time slice per mode from its swap. A mode is put in by `state/swap/<resource>.git.sh <from> <to>`, and its status is a file in the machine's state folder, so anything that reads the project checks on a lease with no command: `state/status/leases/<id>.json` says which run, what it holds, its place in line while it waits (`position`), until when (`expires`), and its `state` (`waiting`, `swapping`, `granted`, `held`, then `released`, `expired`, `failed` or `cancelled`): the lease holds the resource while `state` is `held` and the time is before `expires`. `state/status/resources/<resource>.json` gives each resource's mode, holders and line. With the param `callback`, an `http(s)` address, the lease POSTs its status there once when the hold starts, so the asker starts without looking; with no `2xx` after three tries, the lease fails (`failed`) and gives the resource back. A held lease waits on its `expires` and a waiting one sleeps until a lease leaves the line or the holders, or is granted, and wakes the one lease next to go, or until time alone could change its turn, at least once a minute ([D88](docs/decisions.md#d88-a-wait-can-end-at-an-instant-a-script-wrote)), so neither looks every second. It needs `bash`, `flock` and `jq`, and `decree daemon` (migration A12).
- The official `registry` plugin ([D87](docs/decisions.md#d87-what-can-be-leased-is-the-projects-and-the-registry-says-where-to-go), `decree install registry`): one table of where each service is, `machines/registry/state/services.git.txt` (`<server> <service> <url> [lease]`), with the lease to get before using it: a resource of this project's `lease` machine, or `<resource>@<address>` for another decree's. Its `check` probes each address at each daemon start and every five minutes (an answer below 500 is up; a 5xx or none is down) and writes `state/health.json`, which anything may read; `registry.sh resolve <service>` gives each place with its lease, live ones first and then the least loaded local lease, and `url`, `env` and `list` (`--json`) look things up. It only says where to go; it never takes a lease.
- A cron file can fire when the daemon starts ([D80](docs/decisions.md#d80-reboot-fires-when-the-daemon-starts), [Cron files](docs/reference/messages.md#cron-files)): `cron: "@reboot"`, Vixie cron's word, queues the message once each time `decree daemon` starts, at its first pass, through the same writer with `trigger: cron`, for the machines this daemon runs. It fires on every start, `--retry` included, and while the queue is held; a file added while the daemon runs waits for the next start, and `decree process` never fires it. `decree check` accepts it (M3). `decree status --cron` shows `daemon start` for it and now takes `--format json`, described by `cli/status.schema.json`: each file's `file`, `cron`, `machine`, `next` (null for `@reboot`) and `at_daemon_start` (migration A11).
- Plugins ([D78](docs/decisions.md#d78-a-machine-is-shared-as-one-plugin-file), [D85](docs/decisions.md#d85-a-plugin-carries-any-of-decrees-files-and-installs-only-when-asked), [plugins.md](docs/reference/plugins.md)): `.decree/plugins/<name>.md` holds any of decree's files as one file, described by `schema/v1/plugin.schema.json`: a machine (`machine`, without `name`; optional, so a plugin of scripts is a library others name in `needs`), the files of its `scripts/<name>/` (`scripts`), cron files installed into `cron/<name>/` (`cron`), migrations written to `migrations/` once (`migrations`), seeds written to `store/<name>/` once (`store`), the plugins it relies on (`needs`), and `x-` keys, which decree ignores and export keeps. Only `decree plugin install`, `add` and `import` install. `decree plugin install` with no name installs every plugin that is new or changed, removes a deleted plugin's copy (and the migrations it wrote that never started; its store stays), never overwrites an installed copy edited in place, names each conflict and exits 1 on one; with names it installs those over any edit. `process`, `daemon` and `check` install nothing: they say which plugins `install` would install or remove, and run what is installed, so a read-only `machines/` works; run `decree plugin install` after a clone or a pull that changes a plugin. The record of each install is in the gitignored `.decree/cache/plugins/`. `decree plugin export <name>` writes a plugin from the installed copy, flat scripts the machine runs included, keeping the file's migrations, store and `x-` keys; `decree plugin import <file|-> [--force]` checks one and installs it. Each takes `--format json` (`schema/v1/cli/plugin.schema.json`). `decree check` gains P1 (a plugin that fails its schema), P2 (a missing `needs`) and P3 (a plugin that changed over an edited copy), and warns about a machine no plugin installed in a project with `plugins/`. The daemon, `check` and `status --cron` read cron files one folder down, `cron/<folder>/*.md`, and `decree init`'s `.gitignore` lists `cron/*/`.
- The official `plugin_install` plugin (`decree install plugin_install`): runs `decree install` from a `@reboot` cron file, so plugins are installed each time `decree daemon` starts, for a project that wants that.
- A `reply` invoke takes `attention: false` for a wait that needs no person, one only programs answer, such as a short `timeout` used as a timer ([Invoke](docs/reference/machines.md#invoke-the-states-function)): the run gets no file in `.decree/attention/` and no `Waiting:` line from `process`, and its `waiting` event records `attention: false` (`machine.schema.json`, `events.schema.json`). `lease`'s `waiting` and `held` states use it, so leases never fill `.decree/attention/`.

### Changed

- Each machine owns a folder ([D86](docs/decisions.md#d86-machines-own-their-folders-order-replaces-migrations), [File layout](docs/reference/README.md#file-layout)): `machines/<name>.yml` is `machines/<name>/machine.yml`, `scripts/<name>/` is `machines/<name>/scripts/`, cron files are `machines/<name>/cron/*.md` (`machine:` defaults to the folder), and `decree graph` writes `machines/<name>/graph.md` and `.decree/system.md` in place of `graph/`. A plugin installs into that folder; replace `.decree/.gitignore` with the one `decree init` writes.
- `store` is `state` ([D86](docs/decisions.md#d86-machines-own-their-folders-order-replaces-migrations), [State](docs/reference/scripts.md#state)): the folder is `machines/<name>/state/`, the machine key `store:` is `state_files:`, and the plugin key `store` is `state`; `DECREE_STATE_DIR` names the folder. Move `store/<name>/` into the machine's folder as `state/`.
- The plugin key `migrations` is `order`: seeds for `machines/<name>/order/`, written once. An uninstalled plugin keeps its `state/`, `order/` and `graph.md`.
- `decree init` adds and installs the official `ai`, `order`, `prune` and `skill` plugins; delete a plugin's file to drop it.
- `decree plugin add`, `import` and `install` are one command, `decree install` ([plugins.md](docs/reference/plugins.md#installing)). With no argument it installs every plugin in `.decree/plugins/` as its file says, the step after a clone or a pull, and with a plugin piped on stdin it installs that one (`curl -fsSL <url> | decree install`); `decree install <name>...` installs those, copying an official plugin that `plugins/` lacks from decree first; `decree install <file|->` installs a plugin file. In `cli/plugin.schema.json`, `add` is `install` (its `kept` status is `installed`), and the no-name `install` is `sync`.
- `decree plugin list` and `decree plugin export` are `decree list` and `decree export`, and `decree plugin` is gone. `decree list` lists the project's plugins first, each marked `official` (with `differs` when the file is not this decree's copy) or `own`, and `not installed`, `edited`, `conflict` or `invalid` when it is not installed as its file says; then the machines no plugin installed; then the official plugins the project does not have, which is also what `decree init` ends with. Its JSON is `plugins` (`name`, `description`, `official`, `differs`, `state`), `unplugged` and `available`.
- `decree event` is `decree reply`: it only ever answered a run waiting in a `reply` state. `cli/event.schema.json` is `cli/reply.schema.json`.
- `decree upgrade` asks `Run the install line now (…)? [y/N]` after printing, and runs the README's `curl … | sh` only on `y`; `--yes` runs it without asking. Then, in a project, it offers to run the new copy's `decree install` there. Its after-steps are `decree install` in each project, `decree list` and `decree install --force <name>` (were `decree plugin add --force skill` and `decree schema`) ([D90](docs/decisions.md#d90-decree-install-writes-the-schemas-and-ends-an-upgrade)).
- `decree init` and every `decree install` that succeeds write `.decree/schema/`, as `decree schema` does, so a project has the schemas of the decree that last installed into it ([D90](docs/decisions.md#d90-decree-install-writes-the-schemas-and-ends-an-upgrade)). It stays ignored by git.
- The official plugins that ask AI (`develop` and its variants, `infra`, `qa`, `develop_by_size`) no longer carry a copy of `ai.sh`: they need the `ai` library plugin and source `.decree/machines/ai/scripts/ai.sh`. A plugin with no machine lists the first line of its body as its description.
- The `person` invoke is now `reply`, and its `ask` script is `notify` ([D82](docs/decisions.md#d82-the-invoke-that-waits-for-a-reply-is-reply), [Invoke](docs/reference/machines.md#invoke-the-states-function)). Nothing behaves differently; only names change, and the `v1` files change in a way that is not additive, which decree allows while it is 0.x. What to rewrite: in a machine, `invoke: { person: { question, ask, timeout? } }` becomes `invoke: { reply: { question, notify, timeout? } }`; a machine that still says `person:`, or `ask:` inside `reply:`, fails `decree check` under V19 with ``person: is now reply: (and its ask: is notify:)``, and there is no alias. A tool that reads `events.jsonl` sees `source: "reply"` where it saw `source: "person"`, and `kind: "reply"` on the `decision` event; the trace span is `decision reply <state>`. `machine.schema.json` accepts `reply` with `notify` and rejects `person`; `events.schema.json` lists `reply` as a `source` and a decision `kind`. Graphs label the edges `(reply)` and the note `reply: <notify script>`, and the V8, V12, V16, V18 and V19 messages and SARIF rule texts name `reply` and `notify`. The script environment (`DECREE_WAIT_ID`, `DECREE_QUESTION`, `DECREE_CHOICES`, `DECREE_RECEIVED`) is unchanged. `examples/project`'s `ask_person` script is `notify_person` (migration A11b).
- Official plugins, built into decree and all opt-in ([D79](docs/decisions.md#d79-official-plugins-are-built-in-and-opt-in), [plugins.md](docs/reference/plugins.md#official-plugins)). The repository's `plugins/<name>.md` (`develop`, `infra`, `qa`, `router`, and the examples' `newsletter`, `comfy`, `develop_by_size`, `gliner_router` and `llm_router`) are compiled into the binary. `decree init` installs none: it writes an empty `.decree/plugins/`, a `.gitignore` that also lists `machines/` and `scripts/`, a `.env.example` (`AI_CLI` from `--ai`) and the skill, then lists the official plugins. `decree plugin list` lists them, marked `added` and `differs`; `decree plugin add <name>... [--force]` copies them and every plugin they need into `plugins/` and installs them, `--force` printing the edits it drops. `decree plugin export` with no name exports every plugin whose installed copy differs from its file (`--dry-run` names them), `export` keeps a plugin file's `needs`, and `cli/plugin.schema.json` gains the `list`, `add` and no-name `export` shapes. `ai.sh` and the router's `ask.sh` pick the AI CLI when they run (the run's `ai_cli` data, else `AI_CLI`, else the first of `claude`, `opencode` and `copilot` on `PATH`), so no installed file names the backend, and the router's script is `ask`. `commit` exports edited plugins before it commits, so a run's edits to an installed copy are in its commit, except a conflict (an edited copy whose plugin file changed since it was installed, as after a pull), which `export` with no name names and leaves to merge by hand (`conflicts` in its JSON); `keep` holds the queue on a failed run's unexported edits. Each plugin carries every file it uses, so `clean_tree`, `commit`, `keep` and `ai.sh` are copies in each, and there are no flat shared scripts. `decree upgrade` adds `decree plugin list` and `decree plugin add --force <name>` to its after-steps. `examples/` keeps only what is not a plugin; this repository and `examples/project` commit their machines as plugins only. An existing project converts with `decree plugin export <name>` per machine, two `.gitignore` lines and `git rm -r --cached .decree/machines .decree/scripts`; decree never edits an existing `.gitignore` (migration A10). The paths and the opt-in default here are rc.1's: D86 moved each machine's files into `machines/<name>/` and has `decree init` add `order` and `prune` (above).
- `infra`'s `run.sh check` and `run.sh apply` treat every machine's `requirements` (now `.decree/machines/*/scripts/requirements`) as one list, `infra`'s own first, then the others in name order, and end each line they report with the file it came from (`missing  command cargo (scripts/develop/requirements)`). `infra`'s `declare` still edits only `scripts/infra/requirements`, and `develop`'s `precheck` runs the same check (migration A08, [D77](docs/decisions.md#d77-a-machines-files-live-with-its-scripts)). The paths and the opt-in default here are rc.1's: D86 moved each machine's files into `machines/<name>/` and has `decree init` add `order` and `prune` (above).

### Removed

- Migrations ([D86](docs/decisions.md#d86-machines-own-their-folders-order-replaces-migrations)): `.decree/migrations/`, `processed.md`, the `migration` trigger and frontmatter key, `decree check`'s M1 and its warning about an inserted name, and naming a run by a migration's file. Move each file into the `order/` of the machine it names and write that machine's `state/order.git.txt` from `processed.md`, one `<file> <sha256>` line each (`sha256sum`), so none runs again.
- `decree process`: run `decree daemon --once`, which takes the same flags; `--retry` now needs a run id.
- `decree prune`: the official `prune` plugin deletes old runs (`echo "Prune." | decree emit --machine prune` now; `PRUNE_OLDER_THAN` for the age).
- `decree skill`: the official `skill` plugin, which `decree init` adds, writes the skill at init and refreshes it at each daemon start; after an upgrade, `decree install --force skill`. `cli/skill.schema.json` is gone.
- Flat `.decree/scripts/` and `.decree/cron/`: a script resolves only in its machine's `scripts/`, and code several machines share is a library machine they source by path.
- `.decree/lib/` and `DECREE_LIB`: decree no longer defines, creates, exports or checks either, and `decree init` writes nothing into `lib/`. A machine's helpers, config and data sit beside its scripts in `scripts/<machine>/`: `ai.sh` is a copy in `scripts/develop/`, `scripts/infra/` and `scripts/qa/`; infra's `requirements`, `run.sh` and `kinds/` are in `scripts/infra/`; qa's `qa.sh`, `invariants.md` and `wrenches.md` are in `scripts/qa/`. A project that used `$DECREE_LIB` moves those files and changes `"$DECREE_LIB/<file>"` to a path from the project root, the scripts' working directory (`. .decree/scripts/develop/ai.sh`), or from the script's own location. A `DECREE_LIB` in `.decree/.env` is reserved like any other `DECREE_*` key. A project may still keep a shared folder of its own; decree does not look at it (migration A08, [D77](docs/decisions.md#d77-a-machines-files-live-with-its-scripts)). The paths and the opt-in default here are rc.1's: D86 moved each machine's files into `machines/<name>/` and has `decree init` add `order` and `prune` (above).

### Fixed

- A reply queued before a `person` wait's deadline lost to the timeout when `process` or `daemon` got to it after the deadline, since timeouts were delivered before the inbox was read. A reply to that wait (its wait id or the run id) whose id time is at or before `timeout_at` is now delivered first, and the timeout only if none is ([D81](docs/decisions.md#d81-a-reply-queued-before-the-deadline-wins), [Replies](docs/reference/messages.md#replies), step 5). A reply queued after the deadline still loses (migration A11a).
- A rejected reply (unknown run, run not waiting, stale wait id, unknown option) held the queue: its `invalid_message` run's file in `.decree/attention/` had `machine: ''`, which decree's own reader rejects, so no run started until a person deleted it. The file now names the machine of the run the reply was addressed to, has no `machine` when that run does not exist, and always has `holds: false`. `attention.schema.json` (still `v1`) makes `machine` optional for a run's file (migration A11a).

## [0.5.0] - 2026-10-19

decree 0.5 is a rewrite. A project is three building blocks: **messages** (markdown with YAML frontmatter), **machines** (YAML statecharts that follow W3C SCXML) and **scripts** (executables). A message names its machine, the machine names scripts and decisions, and every run is recorded in `.decree/runs/<id>/events.jsonl`. A `model` decision is answered by a router machine through `request.json` and `reply.json`, and a `person` decision by a reply message. The contract is described in the [reference](docs/reference/README.md), with the reasoning in the [decision log](docs/decisions.md). There is no upgrade path from 0.4.

The entries below are the changes made to the 0.5 contract since migration 70 (`decree prune`), one per migration. Each is described in its decision log entry.

### Added

- `decree upgrade [--format <text|json>]` prints how to upgrade decree, as `rustup self update` and `uv self update` are reached from the binary, but runs nothing and makes no network call: the running version, the README's install line, the same line pinned with `| sh -s -- <tag>`, for a copy from `cargo install` the line `cargo install --git https://github.com/jtmckay/decree --tag <tag> --force` and a note to remove the other copy when `which -a decree` lists two, and what to run in each project after, `decree skill` and `decree schema`. It works with or without a `.decree/`. `--format json` is described by the new `cli/upgrade.schema.json`, written by `decree schema`; a test checks the line it prints is the README's (migration A05).
- `decree check` warns about each pending migration whose filename sorts before the last one in `processed.md`, which runs next, after work that sorts later: ``migration <file> sorts before <last>, which already ran; it runs next``. Inserting one stays allowed, so it is a warning, like the store warnings, in text, `--format json` and `--format sarif` (`level: "warning"`); the exit code is unchanged.
- `events.jsonl` (still `v: 1`): the claim (`claim` or `invalid_message`) and every `retry` event gain `decree_version`, the version of the decree that started or retried the run, so a run retried after an upgrade records which version ran which part. `events.schema.json` gains it as an optional string on `transition` events, so runs recorded without it stay valid, and `decree status <id>` shows it on those rows.
- `process` and `daemon` take `--machine <m>` or `--exclude-machine <m>` (repeatable, comma-separated; both together exit 2), or `DECREE_MACHINES` and `DECREE_EXCLUDE_MACHINES` from the shell or `.decree/.env` (a flag beats both, the shell beats `.env`), so several processes can share one project folder, each running its own machines. It writes `.decree/attention/manual-stop.md` (`kind: manual-stop`, `since`, `holds: true`), which holds the queue: the run going now finishes its step loop, then `process` exits 1 and `daemon` waits; deleting the file resumes, with no daemon restart. A file with `holds: true`, or any `.md` file there decree cannot read, stops `process` and `daemon`. `process` ends with `<n> run(s) need attention: .decree/attention/`, `decree status` starts with `Attention:`, and `status --format json` gains `attention` (`cli/status.schema.json`). Keys are checked by V16; `machine.schema.json` gains `env` (migration 94).

The default must be in the `enum` (V14); `decree emit`, `decree check` (M1–M3, V16) and the claim reject a `params` value outside it, naming the param, the value and the allowed values. ### Changed

- Bare `decree` prints a synopsis of the README's quick start (`src/templates/synopsis.md`) and exits 0, inside a project or not; it no longer runs `decree process`, and reads, writes and runs nothing. Run the queue with `decree process` ([D76](docs/decisions.md#d76-bare-decree-prints-a-synopsis), migration A07).
- `max_depth` defaults to 10 and can be changed: `DECREE_MAX_DEPTH`, a whole number of at least 1, from the shell or `.decree/.env` (the shell wins), sets it for `decree emit`, `machine:` child runs and `model` router runs alike. Every script gets the value in effect as `DECREE_MAX_DEPTH`, so an emit inside a `process` or `daemon` run uses that process's limit. A refused emit says how to change it, `depth 11 exceeds max_depth 10 (set DECREE_MAX_DEPTH to change it): run <id> is at depth 10`; the event stays `max_depth <n> reached`. Any other value is refused before anything runs: `process`, `daemon` and `emit` exit 1 naming the variable and its value, and `decree check` reports it as E1 at its `.decree/.env` line. `.decree/.env` may set it beside `DECREE_MACHINES` and `DECREE_EXCLUDE_MACHINES`; a machine's `env_file` still may set no `DECREE_*` key. Finding a run's root no longer stops at 10 parents, so a deeper chain, or one recorded under a higher limit, still finds it. Run folders, events and schemas are unchanged ([D75](docs/decisions.md#d75-max_depth-is-a-variable-with-a-default)).
- `decree emit` takes a whole message on stdin. Stdin that starts with frontmatter is the new message's frontmatter and body, less the keys decree sets (`id`, `state`, `trigger`, `arrived_as`, `migration`); `--machine` and `--param` override it, and `--machine` may be left out when the frontmatter names a machine. So `decree emit < .decree/migrations/01-a.md` queues a migration's work again as a new inbox run, leaving the migration and `processed.md` as they are, where before the frontmatter landed inside the body. Frontmatter that is not valid is refused with the errors `decree check` gives, at their stdin line, and nothing is queued; stdin without frontmatter is the body, as before. The message guidance gains a "Run a message again" recipe ([D74](docs/decisions.md#d74-decree-emit-reads-a-whole-message)).
- A migration's run has a time id like every other run, where its id was the file's stem, so runs list in the order they were made and a migration's numbering no longer sorts its run apart. Its `runs/<id>/message.md` records the file as `migration: <file>`, which is decree's alone like `id`: a file placed in `inbox/` loses it, so a copy of a migration's run is not a run of that migration. What a migration's run decides is unchanged: it runs once, in order, and a failed, interrupted or waiting one blocks later migrations. Wherever a person names a run, `decree process --retry`, `decree daemon --retry`, `decree status <id>`, `decree tail <id>` and `decree event <id>`, the migration's file name or stem (`01-a.md`, `01-a`) works and means its newest run. Status lines, `process`, `daemon` and `tail` lines, `Waiting:` lines, `--retry`'s notice and `prune` show the run as `<id> (<file>)`, `decree status <id>` prints `migration: <file>` (and `--format json` adds `migration`), and the built-in `commit` titles a migration's commit `<heading> (<file>)`. Run folders named by a stem from before are never renamed and still count as their migration's runs, and `decree prune` still keeps a failed migration's run. `message.schema.json` gains `migration` as an optional string, as do a run in `cli/status.schema.json` and `cli/prune.schema.json`. The examples' recorded runs and the test fixtures use time ids for their migration runs ([D73](docs/decisions.md#d73-migration-runs-get-time-ids-like-every-other-run)).
- Every inbox message runs in the order it arrived, whoever wrote it. A file in `inbox/` not named `<id>.md` by an id decree made (or whose `id` is not that id, or already has a run) gets a fresh id the first time `process` or `daemon` sees it, as `decree emit` would have given it, and is renamed `inbox/<id>.md`; files first seen together go by modification time, then name. Its old name is kept as the new frontmatter key `arrived_as`, in `runs/<id>/message.md` too, and is the claim event's `file`. `id`, `state`, `trigger` and `arrived_as` are decree's alone: a file placed in `inbox/` gets decree's own, so a copy of a migration or of a run's `message.md` runs again as a new run, where before a copy failed because its `id` had a run and a hand-written `01-hi.md` ran ahead of everything emitted. Replies are ordered the same way. Files starting with `.` are still ignored. `message.schema.json` gains `arrived_as` as an optional string ([D72](docs/decisions.md#d72-every-inbox-message-gets-a-time-id-as-it-arrives)).
- `decree check`'s inserted-migration warning ends with how to keep the order: ``To keep the order, pad numbers to the width the project needs (`001-`) or continue with a letter prefix (`A01-`), which sorts after digits``. The skill, its `reference/messages.md` and [messages.md](docs/reference/messages.md#writing-a-message) say the same where they say how to name a migration. Migrations still run in byte order of filename ([D71](docs/decisions.md#d71-migration-names-keep-their-order-by-padding-then-a-letter-prefix)).
- decree's guidance on writing a message has a rule beside "one concern per migration": **describe the outcome, not the steps**. A message says what is true when it is done and why (observable behaviour, the public contract, what must not change), and leaves out which functions, modules or files to change, in what order; a sentence a different correct implementation would fail is a step. The body's shape is `## Overview`, `## Outcome`, `## Constraints`, `## Acceptance Criteria`, shown in the skill, its `reference/messages.md` and [messages.md](docs/reference/messages.md#writing-a-message), with a step-written sentence from migration 110 and its outcome-written form. Every example message follows it, and `qa`'s triage writes each bug report as the broken invariant and the expected behaviour, proposing no fix. decree never reads the body, so a message with other headings, `## Requirements` included, runs as before ([D70](docs/decisions.md#d70-a-message-describes-the-outcome-not-the-steps)).
- `clean_tree` names the run that left the changes it found: each run that passed `clean_tree` and is now `interrupted` or `failed` (an interrupted run never reaches `keep`, so nothing named it), read from `decree status --all --format json` with `jq`, with its id, first heading, `decree process --retry <id>` and `git stash push --include-untracked -m "decree <id>" -- .`. It writes the same lines to the run's `leftovers`, which decree includes in the run's file in `.decree/attention/`, as it does `hold`. With no such run, or no `jq`, the message is as before. decree runs no git command.
- `decree status` starts with what stops the queue (`Held:`, `Blocked:` and the `--retry` command), leaves out statuses with no runs, counts runs finished in a state other than `failed` instead of listing them, and lists the last 5 runs of each status and the first 5 queued files; `--all` lists everything. `--format json` adds `blocked`.
- The switch `lib/ai.sh`'s `ai` reads is `AI_CLI`, and a machine's data entry for it is `ai_cli`: beta.7's `DECREE_AI` and `agent` are gone, and `DECREE_*` is again decree's alone, in a script's environment and in `.env` files ([D66](docs/decisions.md#d66-one-ai-helper-with-every-backend-a-capped-limit-wait-and-a-nudge)). `.decree/ai-use.md`'s `agent` column is `cli`.
- `qa`'s triage names Rust's `#[should_panic]` among the strict expected-failure markers, beside Python's, Playwright's and Jest's.
- The `project` and `route-by-complexity` examples ask AI through `lib/ai.sh` (`AI_CLI` per attempt) instead of calling `claude` and `opencode` directly, and every example's `.decree/.gitignore` lists `HOLD`, `process.log`, `cache/` and `ai-use.md`.
- `develop`'s scripts keep `progress.md`, `plan.md`, `gaps.md`, `gate.log` and `STOP` in the root run's folder (`DECREE_ROOT_RUN_DIR`, the run's own in a top-level run), so a child machine whose steps are develop's scripts shares them.
- Every built-in prompt says scratch files go in the run folder, never outside the project. The skill adds two rules: call AI only through `ai`, and keep a step's previous output until it has a new one.
- `lib/ai.sh` holds every backend (`ai_claude`, `ai_opencode`, `ai_copilot`); `ai` calls the one the run's data entry `ai_cli` names (a message's or a parent's `params`), else the one `AI_CLI` names, else the one `init` chose. Every call is logged to `.decree/ai-use.md`, and a call that leaves `STOP` returns 0. Claude's usage-limit wait is capped by `AI_LIMIT_WAIT` (default `6h`), past which it writes `STOP`; OpenCode takes `OPENCODE_MODEL` and is nudged back, up to `AI_NUDGES` times, when a rejected write ends its session ([D66](docs/decisions.md#d66-one-ai-helper-with-every-backend-a-capped-limit-wait-and-a-nudge)).
- `decree init --permissions` writes OpenCode's `"external_directory": "deny"` and `"share": "manual"` (`autoshare` is deprecated).
- A failed `develop`, `infra` or `qa` run keeps its changes in the work tree: the shared `keep` script replaces `stash` as `failed`'s `onentry`, and writes `.decree/HOLD` so no other run starts on them. `clean_tree`'s message lists at most 20 paths and says how to continue the run that left them ([D65](docs/decisions.md#d65-a-failed-run-keeps-its-changes-and-holds-the-queue)).
- `visits` count from a run's last retry, so a retried run gets all the rounds of a `check` on `visits` again ([D64](docs/decisions.md#d64-a-retry-is-the-runs-next-attempt-with-fresh-visits)).
- `develop`'s `precheck` runs `lib/infra/run.sh check` instead of looking for the AI's command, which `lib/infra/requirements` lists ([D61](docs/decisions.md#d61-the-environment-is-declared)).
- A person answers a `STOP` in the run's `plan.md`, which the next step follows.
- `process` and `daemon` read the machines and `.env` files again before each run, so an edit applies to the next run without a restart; they loaded the machines once at start. A machine edit that fails `decree check` is not used: the machines last loaded keep running, and the errors are printed once ([D59](docs/decisions.md#d59-machines-are-read-again-before-each-run)).
- A script that writes `done` to `$DECREE_EVENT_FILE` gets `done`, the same as writing nothing; it got `error`, as `done` was reserved. `error`, `unsure`, `done.*` and `error.*` stay reserved ([D60](docs/decisions.md#d60-a-script-may-name-done)).
- Docs: [`process` or `daemon`](docs/reference/cli.md#process-or-daemon) says which to run: `process` is one pass that exits while a run waits for a person or a `timeout`, `daemon` is for unattended work. The reference and the skill say how to write prose with `: ` in a machine.
- **Breaking:** script logs no longer mark stderr lines with `[stderr] `; stdout and stderr interleave unmarked, so an `output` condition or a router's `input` sees the lines as written. A log is `NNNN-<state>.log` when its script is named as its state (`0004-gate.log`, not `0004-gate-gate.log`); `tail` headers and the observability regex follow ([D58](docs/decisions.md#d58-process-shows-its-runs-and-logs-do-not-mark-stderr)).
- **Breaking:** variables for scripts come from gitignored `.env` files. `.decree/.env` replaces `.decree/env`, and a machine's new root key `env_file: .env.<name>` names a file only that machine's scripts get, over `.decree/.env` and the process environment; a child machine, router or emitted message never gets another machine's file. `decree init`'s `.decree/.gitignore` lists `.env*` and `!.env.example`, the committed template decree never reads. E1 covers every `.env` file, V14 checks the `env_file` name, and `decree check` warns about a missing `env_file` and a `.gitignore` without `.env*`. The invoke `env:` map is removed from machines and `machine.schema.json` (a per-state value is now a two-line wrapper script). The `newsletter` example ships `.decree/.env.example`. To upgrade: rename `.decree/env` to `.decree/.env`, add `.env*` and `!.env.example` to `.decree/.gitignore`, and replace each invoke `env:` ([D57](docs/decisions.md#d57-gitignored-env-files-one-per-machine-if-needed)).
- decree describes itself as **durable state-machine workflows from plain files, for scripts, AI agents and people** (the crate description, `--help`, the README and the reference), in place of "AI orchestrator for structured, reproducible workflows": durability and the state machine are the core, and AI is optional.
- **Breaking (machines):** every machine key has one shape. `invoke` is a map with one key naming its kind (`script`, `check`, `model`, `person`, `machine`), a check reads a named `output` state's output, its events are `true` and `false`, and function settings sit inside `invoke`. Old shapes fail `decree check` (V19) with a message naming the new one (migration 71, [D44](docs/decisions.md#d44-one-shape-per-machine-key)).
- `mock/` became examples by topic: `examples/feature/`, `examples/sort-documents/` and `examples/observability/` (migration 73, [D46](docs/decisions.md#d46-no-04-compatibility-and-examples-by-topic)).
- `tmux-services` scripts are named for what they do: `use_<service>` starts or uses a service, `without_<service>` frees the GPU of it (migration 77). They keep both servers up and free GPU memory by unloading models through the Ollama and ComfyUI APIs, instead of ending sessions (migration 78).
- **Breaking (scripts):** a script names its event by writing it to `$DECREE_EVENT_FILE`, not by printing `{"event": …}` last on stdout. In `events.jsonl`, its `transition` source is `script` (was `stdout`) (migration 79, [D48](docs/decisions.md#d48-scripts-name-their-event-in-decree_event_file)).
- **Breaking (machines and CLI):** one duration format everywhere, a whole number and `s`, `m`, `h` or `d`: a machine's `timeout` (was `timeout_s` in seconds), `decree prune --older-than` and `decree daemon --interval` (migration 80, [D49](docs/decisions.md#d49-one-duration-format)).
- **Breaking (schema location):** the schemas moved from `.decree/schema/` to `.decree/schema/v1/`, and machines point at `../schema/v1/machine.schema.json`. `decree check` warns about any other file in `.decree/schema/`, and `decree schema` removes it (migration 81).
- `events.jsonl`: a child run's claim event leaves `file` out instead of writing `null`, since a child run has no file (migration 81).
- **Breaking (CLI):** `decree process --retry [<id>] [--state <s>]` replaces `decree retry <id>`. Without an id it continues the migration that blocks the queue; with one, any run. It writes the same `retry` transition and then processes the run and everything queued after it in the same invocation. The failure messages of `process`, `daemon` and `decree status` print the exact command. `decree retry` is gone (an unknown command, exit 2), and with it `retry --format json` and `.decree/schema/v1/cli/retry.schema.json`; `events.jsonl` is unchanged (migration 85, [D53](docs/decisions.md#d53-decree-process---retry-continues-a-run)).
- **Breaking (machines):** `attempts` replaces `max_attempts` in a script invoke. `attempts: 3` is three attempts, as `max_attempts: 3` was; `attempts: [local, local, claude]` runs the script once per entry, in order, until one does not end in `error`, with the entry in the new `DECREE_ATTEMPT_VALUE` (and the whole list in `DECREE_ATTEMPT_VALUES`). `max_attempts` fails `decree check` (V19) naming the replacement; there is no alias. `events.jsonl` (still `v: 1`): `script` events and `source: "attempt"` transitions gain `attempt_value`. `decree graph` notes a state's attempt list (migration 88).
- `route-by-complexity` retries with Claude through an attempt list: `local_first` runs one `implement` script with `attempts: [local, local, claude]`, and each attempt runs the tests, so local work that fails them moves to Claude in the same state (`claude_only` runs `[claude, claude]`). `implement_local`, `implement_claude`, `verify` and `tried_claude` are gone. `text-to-media` is one `comfy` machine in place of three: the message names the workflow in `method`, and `build`, `submit`, `await` and `fetch` wait for the render and save it at the repo path in `output`. `COMFY_URL` replaces the `api_url` param (migration 89).
- The decree skill writes the simplest machine first: one script state each, in a straight line, and adds `attempts`, events, decisions or child machines only when the user asks or a run shows the need, cheapest fix first. Its rule "Machines decide, scripts work" became "Scripts choose how, machines choose what runs next", and its worked example grows a `develop` machine in three steps (migration 90).
- `examples/project`, three simple machines (`hello`, `develop` with `attempts: [local, claude]`, and `deploy`), replaces `examples/feature`, whose one machine used every building block at once. Its recorded runs: a migration whose `local` attempt fails and `claude` attempt succeeds, a `deploy` run waiting for a person with the reply queued, and an interrupted cron run. The reference shows nesting, decisions and `emits` as short fragments; the tests that need them use `tests/fixtures/feature/` (migration 92).
- `decree process` keeps draining `inbox/` after a run from it ends in `failed`: it reports the run with `decree process --retry <id>`, goes on with the next file, lists every failed run once the queue is empty, and exits 1. A failed migration still stops it at once, as migrations are ordered; `decree daemon` already went on (migration 93).
- **Breaking (built-in machines):** one `develop` machine with a gate script replaces `develop` and `rust_develop`. `decree init` writes `precheck` → `implement` → `gate` → `verify`, with `fix` and `final_gate` only when the gate fails. `scripts/develop/gate.sh` holds the project's own checks: as written it runs nothing and says so, with commented lines for cargo, npm and Go. `implement`, `fix` and `verify` log steps in the run's `progress.md` and write `STOP` instead of guessing, run-directory conventions now documented in `scripts.md` with `gate.log` and `plan.md`. The `ai` function and Claude's usage-limit wait live once in `.decree/lib/ai.sh`, which the scripts source, instead of a copy in each script (migration 96).
- `request.json`: `reply_schema.properties` lists `reason` before `event` (then `confidence` and `probabilities`); `required` is unchanged. A constrained decoder (llama.cpp, Ollama's `format`) emits properties in schema order, so the model now reasons before it commits to a pick, instead of picking first and arguing after (migration 97).
- Docs: guidance from real runs. `docs/routers.md` says where GLiNER fits (wording, not judging; few options; `check` states first) and to put the reasoning field first; `route-by-complexity` adds `llm_router`, a local model held to `reply_schema` through Ollama's `/api/chat` `format`, and says when to use which router; GLiNER installs as `gliner2[local,train]`; `docs/services.md` and `tmux-services` prepare a waiting resource in an invoked state with a `timeout` (`drain_comfy`), keeping `onentry` for quick steps; `docs/reference/machines.md` keeps a child machine's final states few and generic; `docs/reference/messages.md` explains batching by resource across migrations; `text-to-media` keeps its workflows in `.decree/lib/comfy/`, and its fragment uses one `build` with `env: { METHOD: … }` per state and `enum` on `method`; the skill gains the `lib/` and `env`, "never delete runs" and "prep with a timeout" rules (migration 97).
- Docs: an attempt list moves on only after `error` (a non-zero exit or a timeout); `done` or a named event such as `stop` ends it at once. To have a stronger model answer a weaker one's `STOP`, transition to a child machine: `docs/reference/machines.md` and the skill show the `escalate` fragment, which the docs test checks as a whole machine (migration 101).
- **Breaking (built-in machines):** `develop`'s gate names `pass` or `fail`. `scripts/develop/gate.sh` runs the checks itself, tees their output to `gate.log` and writes `pass` (all passed) or `fail` (one failed) to `$DECREE_EVENT_FILE`, exiting 0; unconfigured, it says so and names `pass`. A missing tool (each commented cargo, npm and Go line has its `command -v` line), or anything else that stops the checks from running, is a non-zero exit: `error`, which ends the run in `failed` without `fix`, so the AI no longer tries to fix code that is fine. `develop.yml`: `gate` goes `pass` → `verify`, `fail` → `fix`; `final_gate` goes `pass` → `verify`, `fail` → `failed`. `lib/ai.sh` runs the agent with `DECREE_EVENT_FILE=/dev/null`, so a gate the agent runs (as `fix` asks) cannot name `implement`'s or `fix`'s event (migration 102).
- Schemas are hosted, and the local copy is optional. Their single source moved from `src/templates/schema/` to `schema/` at the repository root, and each `$id` is now `https://raw.githubusercontent.com/jtmckay/decree/main/schema/v1/<path>`. `decree init` no longer writes `.decree/schema/`, its machines no longer start with a `# yaml-language-server: $schema=…` line (they keep `# Graph: …`), and its `.decree/.gitignore` lists `schema/`. `decree schema` writes the same files as before, for agents and offline editors; `decree check` warns about them only when `.decree/schema/` exists. Editors apply the machine schema by path through a SchemaStore entry (to be submitted once 0.5.0 is on `main`), a `yaml.schemas` setting, or the per-file line, which still works: see `docs/editors.md`. The skill says to run `decree schema` before reading a schema. The examples and this repository no longer commit `.decree/schema/` (migration 105, [D55](docs/decisions.md#d55-hosted-schemas-found-by-path)).

### Removed

- `.decree/HOLD`: the `keep` script writes the run's `hold` instead, and the run's file in `.decree/attention/` holds the queue; `.decree/.gitignore` lists `attention/` in its place ([D67](docs/decisions.md#d67-the-attention-folder-says-what-needs-a-person)).
- `decree init` no longer writes `git_baseline` and `snapshot`. No built-in machine used them, `clean_tree` already records the commit a run started from, and `snapshot`'s stashes were easy to confuse with a failed run's work. Projects keep the copies they have.
- The Docker image (`Dockerfile`, `.dockerignore`, its GHCR workflow) and `examples/docker/`: the image did not carry the tools machines need (it had no Rust toolchain), and projects that want decree in a container can build their own.
- Everything 0.4: the upgrade script and its fixtures, the `config.yml` error, and the `routine:` alias for `machine:` (migration 73, [D46](docs/decisions.md#d46-no-04-compatibility-and-examples-by-topic)).
- The statement of work at the repository root: decree 0.4's pitch, written around routines and `config.yml` (migration 86).
- The `business-eval`, `sort-documents`, `text-to-speech`, `whisper-transcribe` and `decree` examples: other examples cover what they showed, so fewer examples stay current with the API (migration 91). `sort-documents`' escalation ladder and its recorded run are now the test fixture `tests/fixtures/escalation/`, and `docs/routers.md` shows the ladder.
- The `tmux-services` example: GPU sharing keeps the servers running and unloads their models through each API, so supervising the services in tmux sessions added nothing. Its API unloading is in `docs/services.md`, "Freeing VRAM through the APIs" (migration 99).

### Fixed

- `decree process` exited 0 and printed nothing when a migration waited for a child run that was `interrupted`, since a child never continues its parent by itself. It now stops with ``migration <file> waits for child run <id>, interrupted in `<s>`; later migrations are blocked. Fix the cause, then run `decree process --retry`.``, exit 1, and `--retry` alone continues that child; `decree status` shows the same under `Blocked:`.
- `decree process` also exited 0 without a word when the first pending migration, or a child run it waits for, was active in another process, and named a child's wait without saying it held the migrations. It now ends with `Held back:` and why, and `decree status` shows the same line.
- SIGINT or SIGTERM during a child run's script made `decree process` exit 0 instead of 130.
- `ai` let `AI_CLI` win over a run's data entry `ai_cli`, so with `AI_CLI` set in `.decree/.env`, a message's or a parent's `params: { ai_cli: … }` was ignored and the escalation ladder's Claude round ran the project's default. The run's data entry now wins.
- `clean_tree`, `commit` and the old `stash` touched the whole repository; `clean_tree`, `commit` and `keep` now touch only the project folder (`-- .`). In a decree project inside a larger repository, a change in a sibling folder stopped every run, and `done` committed it, staged or not, under the run's title.
- `lib/ai.sh` empties the calling step's event file after the agent returns. An agent in a beta run found the run's `.event` file and ran the gate into it, so `fix` ended in the gate's `pass`, which it has no transition for.
- A `: ` inside a plain YAML value (`description: Step one: build`) is reported as ``line 3: mapping values are not allowed in this context: a value with `: ` in it must be quoted (…) or written as a block (…)``, with the line once; it gave serde's message with the position twice.
- Messages queued in the same second run in the order they were queued. An id is now `YYYYMMDDTHHMMSS.ffffffZ-xxxxxx`, the UTC time to the microsecond, and one process never makes an id with an earlier time than its last; ids were to the second, with a hex suffix that ordered same-second messages at random. `message.schema.json` describes the new form ([D56](docs/decisions.md#d56-ids-to-the-microsecond-in-the-order-they-were-made)). Found by a script that queued image jobs, then speech jobs, so the GPU switches models once.
- `decree event` exits 1 when a reply to the same wait is already queued in `inbox/`, naming that file. It accepted the second reply, which then became a failed `invalid_message` run on delivery, so a caller such as an HTTP front door was told it succeeded. Found by decree-go-rest's approval endpoint.
- The built-in machines' Claude calls recognise Claude's current limit messages ("You've hit your session limit · resets 1:10am", weekly and 5-hour limits, a reset time without minutes) and wait for the reset. They matched only "usage limit … reset at 10:00 PM", so a session limit used up every attempt in seconds and failed the run.
- `decree status <id>` for an unknown id exits 1 with `error: no run <id> in .decree/runs/`, like `decree event`; it exited 0. The `process` and `daemon` help lines now say what they do.
- A script no longer inherits `DECREE_*` variables from a decree run that started its decree (a test suite run by a gate script), and the built-in machines' Claude calls pass `--permission-mode` (default `auto`, set `CLAUDE_PERMISSION_MODE` to change it) instead of inheriting your interactive default, under which `plan` mode changed nothing. Found by the first real run of 0.5.
- `docs/reference/runs.md` documents the fields of `run_finished` again, the fields of each kind of `waiting` event, and when a `model` decision has no `child_run` or `pick` (migration 81).
- The documents and examples agree with decree 0.5 again, and `tests/docs_api_test.rs` keeps them so (migration 87): the reference's settings table names "Retries" instead of 0.4's `max_retries`; `docs/services.md`'s systemd example uses `use_comfy` and `use_ollama`, as `examples/tmux-services/` does; a claimed message gains `id` and `trigger`, not `parent` (README, `decree help`); `events.jsonl` puts `run_id` and `machine` on every line, but `state` only on events about a state (README, `examples/feature/` and `examples/observability/`, which also named a `router` event type that does not exist); `decree graph` takes no machine argument (`examples/feature/`, `graph.md`); a script names its event in `$DECREE_EVENT_FILE` rather than printing it (the `feature` machine's comment, the skill); the skill lists V1–V21 and warns about stale schemas too; `decree graph` and `decree tail` document their exit code 1; three error messages in `cli.md` and `graph.md` render as code again; `docs/routers.md`'s `local_model` fragment shows its options; and `runs.md` shows four recorded `events.jsonl` lines.
- `develop`'s `verify` can fail: it asks the AI to end its reply with `VERDICT: pass` or `VERDICT: fail` and names that event, and a reply without one fails the attempt. It asked the AI to exit 1, but `claude -p` exits 0 whatever the model concludes, so `verify` always passed (migration 96).
