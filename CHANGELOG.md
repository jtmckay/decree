# Changelog

All notable changes to decree are listed here. The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and decree follows [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html). The files decree reads and writes are versioned separately, in their schema path (`v1`), as [Versioning](docs/reference/README.md#versioning) states: within `v1` changes are additive only, and while decree is 0.x every change to `v1` is listed here.

## [0.5.0] - Unreleased

decree 0.5 is a rewrite. A project is three building blocks: **messages** (markdown with YAML frontmatter), **machines** (YAML statecharts that follow W3C SCXML) and **scripts** (executables). A message names its machine, the machine names scripts and decisions, and every run is recorded in `.decree/runs/<id>/events.jsonl`. A `model` decision is answered by a router machine through `request.json` and `reply.json`, and a `person` decision by a reply message. The contract is described in the [reference](docs/reference/README.md), with the reasoning in the [decision log](docs/decisions.md). There is no upgrade path from 0.4.

The entries below are the changes made to the 0.5 contract since migration 70 (`decree prune`), one per migration. Each is described in its decision log entry.

### Added

- Prometheus metrics without an exporter: `examples/observability/config.alloy` derives `decree_runs_total` and `decree_run_duration_milliseconds` from `run_finished` events with Alloy's `stage.metrics`, and `docs/reference/observability.md` has a Metrics section with alert queries.
- A JSON Schema (draft 2020-12) for machines and message frontmatter, written by `decree schema` and by `decree init`. Every machine starts with a `# yaml-language-server: $schema=…` line, so editors complete keys and underline mistakes; `decree check` warns when the schemas are missing or stale (migration 72, [D45](docs/decisions.md#d45-json-schema-for-shape-decree-check-for-meaning)).
- `reply_schema` in `request.json`: the exact JSON Schema of the reply, which a typed router hands to a constrained decoder. Docs and examples for typed routers (GLiNER2.5-Decide, Ollama with `format`) and untyped ones, and the `route-by-complexity` example (migration 74, [D47](docs/decisions.md#d47-typed-routers-for-routing-untyped-models-for-the-work)).
- The `tmux-services` example: services in tmux sessions, with GLiNER beside ComfyUI and Ollama sharing a GPU (migration 75). Its ComfyUI jobs run in the background, and the queue is drained only before ComfyUI's GPU memory is needed (migration 76).
- The `newsletter` example: RSS and Atom feeds gathered weekly by cron, picked and summarised to your taste by a local model through Ollama, and written as one markdown issue, with an optional ntfy ping; three scripts in a straight line, and a README table of what to add once a real issue shows the need (migration 98).
- A versioned schema for every file decree reads or writes: `events.schema.json` (one line of `events.jsonl`), `request.schema.json` and `reply.schema.json`, beside the machine and message schemas, all in `.decree/schema/v1/`. The versioning rule is in [Versioning](docs/reference/README.md#versioning). Tests validate every recorded event, request and reply, and every line the property test writes (migration 81, [D50](docs/decisions.md#d50-a-versioned-schema-for-every-file)).
- This changelog (migration 81).
- `--format json` on `check`, `status`, `emit`, `event`, `retry`, `prune`, `graph`, `schema` and `process --dry-run`: one JSON document on stdout, described by a new schema in `.decree/schema/v1/cli/<command>.schema.json`, with exit codes unchanged; and `decree check --format sarif`, a SARIF 2.1.0 log for GitHub code scanning, GitLab and Azure DevOps (migration 82, [D51](docs/decisions.md#d51-json-output-for-every-report-and-sarif-for-decree-check)).
- W3C Trace Context and OpenTelemetry traces: every run has a trace id, from its message's `traceparent` frontmatter key or random, and writes each span as it ends (the run, each script, decision and wait) to `runs/<id>/traces.jsonl`, one OTLP/JSON request per line, for the OpenTelemetry Collector's `otlp_json_file` receiver. Scripts get `TRACEPARENT` and `TRACESTATE`, child runs get `traceparent` in their `message.md`, and `decree emit` carries the script's `TRACEPARENT` into the new message. `events.jsonl` (still `v: 1`): every event gains `trace_id`; `script`, `decision` and `received` events gain `span_id`, as do the claim (with `parent_span_id` when the message names a parent) and `retry` transitions. `message.schema.json` gains `traceparent` and `tracestate`. A Collector configuration is in `examples/observability/` (migration 83, [D52](docs/decisions.md#d52-traces-as-files-and-environment-variables-not-an-exporter)).
- CI: a GitHub Actions workflow, `.github/workflows/ci.yml`, runs the gate (`cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`) on every push to `main` and `v0.5` and every pull request, and uploads `decree check --format sarif` for the root project and every example to GitHub code scanning (migration 84).
- A security policy, `SECURITY.md`: supported versions, private vulnerability reporting, decree's security model as it is (scripts run with your permissions and no sandbox, a message is a prompt, the built-in machines call Claude with `--permission-mode auto`) and recommendations. The README and [Execution](docs/reference/scripts.md#execution) link it, and the README says there is no upgrade path from 0.4 (migration 86).
- `.decree/lib/` for what scripts share but decree never runs (bash functions to source, config, data such as workflow files): `decree init` creates it with a one-line `README.md`, and every script gets `DECREE_LIB`, its absolute path. decree never resolves a script from it (migration 94).
- `.decree/env`, an optional, committed dotenv file (as Docker Compose's `env_file` and systemd's `EnvironmentFile` read it) whose variables every script gets. The process environment wins over it, so a deployment can override it; secrets belong in the process environment. `process` reads it at start and `daemon` before each pass. A malformed line or a reserved key (`DECREE_*`, `TRACEPARENT`, `TRACESTATE`) fails the new check E1 in `decree check`, and stops `process` and `daemon` from starting (migration 94).
- `env` on a script invoke, `script: { name: build, env: { METHOD: image_text } }`: variables for that invoke only, which win over the process environment and `.decree/env`, so several states can run one script with different values. Keys are checked by V16; `machine.schema.json` gains `env` (migration 94).
- `enum` on `string` data, `need: { type: string, enum: [plan, fix], default: fix }`, and a `number` data type (a JSON number: an int or a float), both from JSON Schema. The default must be in the `enum` (V14); `decree emit`, `decree check` (M1–M3, V16) and the claim reject a `params` value outside it, naming the param, the value and the allowed values. A `number` reaches scripts as `DECREE_DATA_<NAME>` in its shortest form (`0.5`, `2`), and conditions compare it numerically with ints and floats. `machine.schema.json` gains `enum` and `number`, and `params` in `machine.schema.json` and `message.schema.json` accept floats (migration 95).
- `DECREE_PARENT_RUN_DIR`, the parent run's folder in a child run, and `DECREE_ROOT_RUN_DIR`, the folder of the run at the top of the chain (`DECREE_RUN_DIR` in a top-level run) (migration 94).
- `store:`, what a machine remembers between runs: `.decree/store/<machine>/` holds it, every script gets the path as `DECREE_STORE` (a child machine's scripts the child's), and decree creates it before a script runs. It survives runs and `decree prune`, and `decree init`'s `.decree/.gitignore` lists `store/`. A machine declares what it keeps under the optional root key `store:`, a map of names (a file or folder directly in the store folder, `^[A-Za-z0-9][A-Za-z0-9._-]*$`) to non-empty descriptions, checked by V14; `machine.schema.json` gains `store`. `decree check` warns, without failing, about an undeclared file in a store folder and a store folder with no machine, and `decree graph` adds `store: <names>` to the machine's note. The `newsletter` example keeps `seen.tsv` in its store (migration 100).
- `${VAR}` interpolation in `.decree/env`, the subset of Docker Compose's `env_file` rules: `${VAR}`, `$VAR`, `${VAR:-default}`, `${VAR-default}` and `$$`; single-quoted values stay literal. `VAR` is looked up in decree's process environment, then in the lines above, so `HOST=box` and `COMFY_URL=http://${HOST}:8188` write a host once. An unknown variable is empty and `decree check` warns about it; an unterminated `${` or a malformed `${VAR:…}` is an E1 error. Invoke `env` values are not interpolated (migration 103).
- `decree skill [--ai <claude|copilot|opencode>] [--format <text|json>]`: refreshes the decree skill after an upgrade, overwriting decree's own files in `.claude/skills/decree/` or `.github/skills/decree/`, removing a `reference/` file decree no longer ships and keeping every other file; `unchanged` for files already identical; `--ai opencode` exits 1, as opencode reads no skills. `--format json` is described by the new `.decree/schema/v1/cli/skill.schema.json`. `docs/reference/cli.md` gains "Upgrading decree" (migration 104, [D54](docs/decisions.md#d54-decree-skill-refreshes-the-skill)).

### Changed

- decree describes itself as **durable state-machine workflows from plain files, for scripts, AI agents and people** (the crate description, `--help`, the README and the reference), in place of "AI orchestrator for structured, reproducible workflows": durability and the state machine are the core, and AI is optional.
- **Breaking (machines):** every machine key has one shape. `invoke` is a map with one key naming its kind (`script`, `check`, `model`, `person`, `machine`), a check reads a named `output` state's output, its events are `true` and `false`, and function settings sit inside `invoke`. Old shapes fail `decree check` (V19) with a message naming the new one (migration 71, [D44](docs/decisions.md#d44-one-shape-per-machine-key)).
- `mock/` became examples by topic: `examples/feature/`, `examples/sort-documents/` and `examples/observability/` (migration 73, [D46](docs/decisions.md#d46-no-04-compatibility-and-examples-by-topic)).
- `tmux-services` scripts are named for what they do: `use_<service>` starts or uses a service, `without_<service>` frees the GPU of it (migration 77). They keep both servers up and free GPU memory by unloading models through the Ollama and ComfyUI APIs, instead of ending sessions (migration 78).
- **Breaking (scripts):** a script names its event by writing it to `$DECREE_EVENT_FILE`, not by printing `{"event": …}` last on stdout. In `events.jsonl`, its `transition` source is `script` (was `stdout`) (migration 79, [D48](docs/decisions.md#d48-scripts-name-their-event-in-decree_event_file)).
- **Breaking (machines and CLI):** one duration format everywhere, a whole number and `s`, `m`, `h` or `d`: a machine's `timeout` (was `timeout_s` in seconds), `decree prune --older-than` and `decree daemon --interval` (migration 80, [D49](docs/decisions.md#d49-one-duration-format)).
- **Breaking (schema location):** the schemas moved from `.decree/schema/` to `.decree/schema/v1/`, and machines point at `../schema/v1/machine.schema.json`. `decree check` warns about any other file in `.decree/schema/`, and `decree schema` removes it (migration 81).
- `events.jsonl`: a child run's claim event leaves `file` out instead of writing `null`, since a child run has no file (migration 81).
- **Breaking (CLI):** `decree process --retry [<id>] [--state <s>]` replaces `decree retry <id>`. Without an id it continues the migration that blocks the queue; with one, any run. It writes the same `retry` transition and then processes the run and everything queued after it in the same invocation. The failure messages of `process`, `daemon` and `decree status` print the exact command. `decree retry` is gone (an unknown command, exit 2), and with it `retry --format json` and `.decree/schema/v1/cli/retry.schema.json`; `events.jsonl` is unchanged (migration 85, [D53](docs/decisions.md#d53-decree-process---retry-continues-a-run)).
- **Breaking (machines):** `attempts` replaces `max_attempts` in a script invoke. `attempts: 3` is three attempts, as `max_attempts: 3` was; `attempts: [local, local, claude]` runs the script once per entry, in order, until one does not end in `error`, with the entry in the new `DECREE_ATTEMPT_VALUE` (and the whole list in `DECREE_ATTEMPT_VALUES`). `max_attempts` fails `decree check` (V19) naming the replacement; there is no alias. `events.jsonl` (still `v: 1`): `script` events and `source: "attempt"` transitions gain `attempt_value`. `decree graph` notes a state's attempt list (migration 88).
- `route-by-complexity` retries with Claude through an attempt list: `local_first` runs one `implement` script with `attempts: [local, local, claude]`, and each attempt runs the tests, so local work that fails them moves to Claude in the same state (`claude_only` runs `[claude, claude]`). `implement_local`, `implement_claude`, `verify` and `tried_claude` are gone. `text-to-media` is one `comfy` machine in place of three: the message names the workflow in `method`, and `build`, `submit`, `await` and `fetch` wait for the render and save it at the repo path in `output`. `COMFY_URL` replaces the `api_url` param (migration 89).
- The decree skill writes the simplest machine first: one script state each, in a straight line, and adds `attempts`, events, decisions or child machines only when the user asks or a run shows the need, cheapest fix first. Its rule "Machines decide, scripts work" became "Scripts choose how, machines choose what runs next", and its worked example grows a `develop` machine in three steps (migration 90).
- `examples/project`, three simple machines (`hello`, `develop` with `attempts: [local, claude]`, and `deploy`), replaces `examples/feature`, whose one machine used every building block at once. Its recorded runs: a migration whose `local` attempt fails and `claude` attempt succeeds, a `deploy` run waiting for a person with the reply queued, and an interrupted cron run. The reference shows nesting, decisions and `emits` as short fragments; the tests that need them use `tests/fixtures/feature/` (migration 92).
- `decree process` keeps draining `inbox/` after a run from it ends in `failed`: it reports the run with `decree process --retry <id>`, goes on with the next file, lists every failed run once the queue is empty, and exits 1. A failed migration still stops it at once, as migrations are ordered; `decree daemon` already went on (migration 93).
- **Breaking (built-in machines):** one `develop` machine with a gate script replaces `develop` and `rust_develop`. `decree init` writes `precheck` → `implement` → `gate` → `verify`, with `fix` and `final_gate` only when the gate fails. `scripts/develop/gate.sh` holds the project's own checks: as written it runs nothing and says so, with commented lines for cargo, npm and Go. `implement`, `fix` and `verify` log steps in the run's `progress.md` and write `STOP` instead of guessing, run-directory conventions now documented in `scripts.md` with `gate.log` and `plan.md`. The `ai` function and Claude's usage-limit wait live once in `.decree/lib/ai.sh`, which the scripts source, instead of a copy in each script (migration 96).
- `request.json`: `reply_schema.properties` lists `reason` before `event` (then `confidence` and `probabilities`); `required` is unchanged. A constrained decoder (llama.cpp, Ollama's `format`) emits properties in schema order, so the model now reasons before it commits to a pick, instead of picking first and arguing after (migration 97).
- Docs: guidance from real runs. `docs/routers.md` says where GLiNER fits (wording, not judging; few options; `check` states first) and to put the reasoning field first; `route-by-complexity` adds `llm_router`, a local model held to `reply_schema` through Ollama's `/api/chat` `format`, and says when to use which router; GLiNER installs as `gliner2[local,train]`; `docs/services.md` and `tmux-services` prepare a waiting resource in an invoked state with a `timeout` (`drain_comfy`), keeping `onentry` for quick steps; `docs/reference/machines.md` keeps a child machine's final states few and generic; `docs/reference/messages.md` explains batching by resource across migrations; `text-to-media` keeps its workflows in `.decree/lib/comfy/`, and its fragment uses one `build` with `env: { METHOD: … }` per state and `enum` on `method`; the skill gains the `lib/` and `env`, "never delete runs" and "prep with a timeout" rules (migration 97).
- Docs: an attempt list moves on only after `error` (a non-zero exit or a timeout); `done` or a named event such as `stop` ends it at once. To have a stronger model answer a weaker one's `STOP`, transition to a child machine: `docs/reference/machines.md` and the skill show the `escalate` fragment, which the docs test checks as a whole machine (migration 101).
- **Breaking (built-in machines):** `develop`'s gate names `pass` or `fail`. `scripts/develop/gate.sh` runs the checks itself, tees their output to `gate.log` and writes `pass` (all passed) or `fail` (one failed) to `$DECREE_EVENT_FILE`, exiting 0; unconfigured, it says so and names `pass`. A missing tool (each commented cargo, npm and Go line has its `command -v` line), or anything else that stops the checks from running, is a non-zero exit: `error`, which ends the run in `failed` without `fix`, so the AI no longer tries to fix code that is fine. `develop.yml`: `gate` goes `pass` → `verify`, `fail` → `fix`; `final_gate` goes `pass` → `verify`, `fail` → `failed`. `lib/ai.sh` runs the agent with `DECREE_EVENT_FILE=/dev/null`, so a gate the agent runs (as `fix` asks) cannot name `implement`'s or `fix`'s event (migration 102).
- Schemas are hosted, and the local copy is optional. Their single source moved from `src/templates/schema/` to `schema/` at the repository root, and each `$id` is now `https://raw.githubusercontent.com/jtmckay/decree/main/schema/v1/<path>`. `decree init` no longer writes `.decree/schema/`, its machines no longer start with a `# yaml-language-server: $schema=…` line (they keep `# Graph: …`), and its `.decree/.gitignore` lists `schema/`. `decree schema` writes the same files as before, for agents and offline editors; `decree check` warns about them only when `.decree/schema/` exists. Editors apply the machine schema by path through a SchemaStore entry (to be submitted once 0.5.0 is on `main`), a `yaml.schemas` setting, or the per-file line, which still works: see `docs/editors.md`. The skill says to run `decree schema` before reading a schema. The examples and this repository no longer commit `.decree/schema/` (migration 105, [D55](docs/decisions.md#d55-hosted-schemas-found-by-path)).

### Removed

- The Docker image (`Dockerfile`, `.dockerignore`, its GHCR workflow) and `examples/docker/`: the image did not carry the tools machines need (it had no Rust toolchain), and projects that want decree in a container can build their own.
- Everything 0.4: the upgrade script and its fixtures, the `config.yml` error, and the `routine:` alias for `machine:` (migration 73, [D46](docs/decisions.md#d46-no-04-compatibility-and-examples-by-topic)).
- The statement of work at the repository root: decree 0.4's pitch, written around routines and `config.yml` (migration 86).
- The `business-eval`, `sort-documents`, `text-to-speech`, `whisper-transcribe` and `decree` examples: other examples cover what they showed, so fewer examples stay current with the API (migration 91). `sort-documents`' escalation ladder and its recorded run are now the test fixture `tests/fixtures/escalation/`, and `docs/routers.md` shows the ladder.
- The `tmux-services` example: GPU sharing keeps the servers running and unloads their models through each API, so supervising the services in tmux sessions added nothing. Its API unloading is in `docs/services.md`, "Freeing VRAM through the APIs" (migration 99).

### Fixed

- Messages queued in the same second run in the order they were queued. An id is now `YYYYMMDDTHHMMSS.ffffffZ-xxxxxx`, the UTC time to the microsecond, and one process never makes an id with an earlier time than its last; ids were to the second, with a hex suffix that ordered same-second messages at random. `message.schema.json` describes the new form ([D56](docs/decisions.md#d56-ids-to-the-microsecond-in-the-order-they-were-made)). Found by a script that queued image jobs, then speech jobs, so the GPU switches models once.
- `decree event` exits 1 when a reply to the same wait is already queued in `inbox/`, naming that file. It accepted the second reply, which then became a failed `invalid_message` run on delivery, so a caller such as an HTTP front door was told it succeeded. Found by decree-go-rest's approval endpoint.
- The built-in machines' Claude calls recognise Claude's current limit messages ("You've hit your session limit · resets 1:10am", weekly and 5-hour limits, a reset time without minutes) and wait for the reset. They matched only "usage limit … reset at 10:00 PM", so a session limit used up every attempt in seconds and failed the run.
- `decree status <id>` for an unknown id exits 1 with `error: no run <id> in .decree/runs/`, like `decree event`; it exited 0. The `process` and `daemon` help lines now say what they do.
- A script no longer inherits `DECREE_*` variables from a decree run that started its decree (a test suite run by a gate script), and the built-in machines' Claude calls pass `--permission-mode` (default `auto`, set `CLAUDE_PERMISSION_MODE` to change it) instead of inheriting your interactive default, under which `plan` mode changed nothing. Found by the first real run of 0.5.
- `docs/reference/runs.md` documents the fields of `run_finished` again, the fields of each kind of `waiting` event, and when a `model` decision has no `child_run` or `pick` (migration 81).
- The documents and examples agree with decree 0.5 again, and `tests/docs_api_test.rs` keeps them so (migration 87): the reference's settings table names "Retries" instead of 0.4's `max_retries`; `docs/services.md`'s systemd example uses `use_comfy` and `use_ollama`, as `examples/tmux-services/` does; a claimed message gains `id` and `trigger`, not `parent` (README, `decree help`); `events.jsonl` puts `run_id` and `machine` on every line, but `state` only on events about a state (README, `examples/feature/` and `examples/observability/`, which also named a `router` event type that does not exist); `decree graph` takes no machine argument (`examples/feature/`, `graph.md`); a script names its event in `$DECREE_EVENT_FILE` rather than printing it (the `feature` machine's comment, the skill); the skill lists V1–V21 and warns about stale schemas too; `decree graph` and `decree tail` document their exit code 1; three error messages in `cli.md` and `graph.md` render as code again; `docs/routers.md`'s `local_model` fragment shows its options; and `runs.md` shows four recorded `events.jsonl` lines.
- `develop`'s `verify` can fail: it asks the AI to end its reply with `VERDICT: pass` or `VERDICT: fail` and names that event, and a reply without one fails the attempt. It asked the AI to exit 1, but `claude -p` exits 0 whatever the model concludes, so `verify` always passed (migration 96).
